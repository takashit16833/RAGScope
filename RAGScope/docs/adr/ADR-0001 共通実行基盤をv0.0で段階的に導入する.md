# ADR-0001 — 共通実行基盤をv0.0で段階的に導入する

> [!important] 後続ADR
> 本ADRは[ADR-0002 — 共通実行基盤の契約とコンポーネント実装を分離する](<./ADR-0002 共通実行基盤の契約とコンポーネント実装を分離する.md>)によって置き換えられた。
> 以下は、当時の判断と背景を履歴として保持する。

## 背景

当初のロードマップでは、structured loggingとtimeout / retryをv0.5で整備する計画としていた。一方、v0.0の文書処理、AI推論サービスとの通信、PostgreSQL処理を個別に実装してから共通化すると、エラー表現、ログ、再試行判断が機能ごとに分かれ、後から広範囲な修正が必要になる可能性がある。

特に、文書読み込みの実装へ着手する前に、失敗をどのように正常結果と区別し、処理進行と失敗をどのように追跡するかを共通化する必要がある。

ただし、RS-0001の文書読み込みでは、存在しないファイル、不正なUTF-8、空本文など、直ちに再実行しても改善しない失敗を主に扱う。具体的な外部operationが存在しない段階で、回数や待機を備えた汎用retry executorまで先行実装すると、利用実態のない過剰設計になる。

## 決定

共通実行基盤をv0.0へ前倒しするが、設計と実装を次の段階へ分ける。

1. RS-0001より前に、共通エラー・構造化ログの設計とRAGScopeアプリケーションの最小基盤を整える。
2. retry / timeoutについては、RS-0001より前に次の共通原則を確定する。
   - retryは、一時的失敗かつ再試行安全な場合だけ適用する。
   - 具体的な利用箇所が存在しない汎用executorを先行実装しない。
   - operation固有のPolicyと実装は、そのoperationへ着手する段階で決定する。
3. 文書読み込みでは自動retryを行わず、その理由を文書処理設計へ記録する。
4. RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求するoperationへ着手する前に、そのoperationに必要なretry / timeoutの機能別設計を作成し、必要な最小範囲のexecutorを実装する。具体的な回数、待機、timeout、失敗分類、再試行安全性は、その設計と実装を正本とする。
5. 後続operationでは、副作用と再試行安全性に応じて個別に適用し、共通化できる実装だけを共通部品へ反映する。
6. ローカルの構造化ログをAWSで収集する検証はv0.1.5で扱う。将来のtracingへ拡張可能な境界は保つが、正確な相関情報と処理間関係の規則はv0.5を具体化する時点で決定する。

## 検討した選択肢

### すべてv0.5まで延期する

v0.0を小さく保てる一方、各機能が独自のエラー表現とログを持ち、後から広範囲な修正が必要になる可能性があるため採用しない。

### 各機能で個別実装し、v0.5で共通化する

具体的な利用例を得てから共通化できる一方、エラー・ログの互換性と追跡性がv0.0内でも分かれるため採用しない。

### エラー・ログ・汎用retry executorをすべてRS-0001より前に完成させる

共通化を最初から徹底できる一方、具体的な外部operationがない段階でretryの実装詳細を固定する過剰設計になるため採用しない。

### 変更しにくい契約と原則を先に定め、実装は利用箇所に合わせて段階導入する

エラー・ログの一貫性を確保しつつ、retry / timeoutは具体的なoperationに基づいて設計できるため採用する。

## 結果と影響

- v0.0の作業順は、共通エラー・ログ設計、RAGScopeアプリケーションの最小基盤、文書処理への適用、RS-0001の順になる。
- RS-0001は共通エラー・ログ基盤を利用するが、retry / timeoutの機能別設計やexecutorを前提としない。
- RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求するoperationは、operation固有のretry / timeout設計と最小executorの完成後に実装する。
- v0.0の範囲は増えるが、後続機能での独自実装と大規模な置き換えを抑えられる。
- retry / timeoutの共通原則は早期に固定する一方、具体的な実装値と方式は利用箇所が明確になるまで固定しない。
- tracingの正確な規則は本ADRでは決定せず、v0.5の具体化時に改めて判断する。
