# ADR-0002 — 共通実行基盤の契約とコンポーネント実装を分離する

## 背景

[ADR-0001](<./ADR-0001 共通実行基盤をv0.0で段階的に導入する.md>)では、共通エラー・構造化ログをv0.0へ前倒しし、Haskellの最小基盤を文書処理より先に整える方針を採用した。

その後、v0.0ではHaskell CLIとPython AI Serviceの双方が、同じ処理に関係するエラーとログを出力することが明確になった。一方のコンポーネントだけで共通基盤を整え、ほかのコンポーネントの契約と実装を各機能へ委ねると、serialized shape、相関情報、例外の公開範囲、logger失敗時の意味がコンポーネントごとに分かれる。

また、現在の言語名を共通契約の説明へ列挙すると、コンポーネントの追加、削除、実装言語の変更のたびに、契約自体が変わらなくても複数の文書を同期して修正する必要が生じる。変更しにくい意味とserialized shapeを技術非依存の契約として共通化し、型、例外変換、logger、sinkは契約を利用するコンポーネントごとに実装する必要がある。

retry / timeoutについては、ADR-0001で定めた「一時的失敗かつ再試行安全な場合だけ適用し、operation固有のPolicyは利用箇所で決める」という原則を引き続き維持する。

## 決定

1. v0.0の共通エラー・構造化ログは、複数のコンポーネントが利用できる技術非依存の契約として設計する。
2. 共通契約では、少なくとも次を定義する。
   - 共通エラーの意味、分類、安定したcodeの形式、公開情報と内部原因の境界
   - 構造化ログeventの共通field、category、variant、相関情報、機密情報の扱い
   - timestamp、ID、schema versionの表現
   - loggerのencodeまたはsinkが失敗した場合の共通の意味
3. serialized shapeの正本としてJSON Schemaを作成する。共通fieldと共通category、error codeの形式を対象とし、機能固有のerror codeを巨大な共通`enum`へ集約しない。
4. Schema適合・不適合の代表例としてfixtureを作成し、契約を利用する各実装から同じfixtureを用いて契約適合を確認する。fixtureはSchemaと同格の仕様正本ではなく、契約の代表的な検証入力とする。
5. 正確な型、例外変換、encoder、logger、sinkは各コンポーネントのコードを正本とし、実装を共有しない。
6. 共通設計はRS-0014で扱い、コンポーネント固有の共通基盤はRS-0014に依存する兄弟Ticketとして実装する。v0.0ではRS-0015がHaskell実装、RS-0018がPython実装を担当し、機能実装へ戻る前に共通エラー・構造化ログEpicを完了する。
7. `execution_id`は1回のCLI commandを単位とする。1回の文書取り込みcommand内、または1回の検索command内では同じ値を使用し、コンポーネント境界を越えて伝播する。別commandを同じ`execution_id`で束ねることは要求しない。
8. executionに属するevent、serviceのlifecycleに属するevent、health・readinessなどのdiagnostic requestを区別する。診断requestのaccess logをv0.0の共通application eventへ含めるかは、API設計とエラー・ログ設計で必要性を確認して決める。
9. HTTPでの正確なエラーschemaと`execution_id`の伝播方法は、RS-0012、RS-0003、RS-0004でOpenAPIと機能設計を正本として具体化する。
10. retry / timeoutはログとは別の実行制御とする。一時的失敗かつ再試行安全な場合だけ適用し、operation固有のPolicyとexecutorはRS-0016・RS-0017など具体的な利用箇所で設計・実装する。retry時は1回の論理operationと各試行を区別して追跡する。
11. PostgreSQL native logはv0.0の共通Schemaの対象外とする。アプリケーションが実行・観測するPostgreSQL operationの開始・成功・失敗をapplication eventとして扱う。
12. v0.0のsetup、起動、文書取り込み、検索command、終了方法が確定した時点で、RS-0010によりREADMEを更新する。

## ADR-0001からの変更と継続

本ADRはADR-0001全体を置き換えるが、すべての判断を変更するものではない。変更する判断と継続する判断は次のとおりとする。

### 変更する判断

- 共通エラー・構造化ログ基盤をHaskellの最小基盤として先行させる構成を、技術非依存の共通契約と、その契約を利用するコンポーネントごとの実装へ変更する。
- v0.0では、共通設計だけでなく、RS-0015とRS-0018が担当する現在の各コンポーネントの最小基盤までを、機能実装へ戻る前に完了する。
- コンポーネント境界を越える`execution_id`と失敗情報について、共通の意味はエラー・ログ設計、正確なHTTP表現は機能設計とOpenAPIを正本とする。

### 継続する判断

- retryは一時的失敗かつ再試行安全な場合だけ適用し、具体的な利用箇所がない汎用executorを先行実装しない。
- operation固有のretry / timeout Policyと実装は、そのoperationへ着手する段階で決定する。
- 文書読み込みでは自動retryを行わず、その理由を文書処理設計へ記録する。
- HaskellからPython AI Serviceへ文書チャンクのEmbeddingを要求するoperationは、operation固有のretry / timeout設計と必要な最小executorを整えてから実装する。
- ローカルの構造化ログをCloudWatchで収集・検索する検証はv0.1.5で扱う。
- tracingの正確な相関情報と処理間関係の規則はv0.5を具体化する時点で決定する。

## 検討した選択肢

### 一部のコンポーネントの共通基盤だけを先に完成させる

先行する機能実装へ早く戻れる一方、後続コンポーネントが機能ごとに独自の例外変換とログ形式を作る可能性があり、共通契約の意味が一部の実装だけで固定されるため採用しない。

### コンポーネントごとに設計も実装も独立させる

個別実装は単純になる一方、同じcommandに属するevent、エラーcode、serialized shapeを横断して確認できなくなるため採用しない。

### 1つの設計とSchemaを共有し、実装はコンポーネントごとに分ける

処理追跡に必要な意味とserialized shapeを共通化しつつ、各コンポーネントの型・例外・libraryへ自然に適合できるため採用する。

## 結果と影響

- v0.0の作業順は、共通設計、契約を利用する各コンポーネントの最小基盤、文書処理への適用、後続機能の順になる。
- RS-0014の完了時に、現在Haskell中心で記載されている`エラー・ログ設計.md`を技術非依存の共通契約へ改訂し、JSON Schemaとfixtureを追加する。
- 各実装Ticketは同じSchemaとfixtureへ適合するが、コンポーネント固有の実装詳細は共有しない。
- PythonのWeb framework、model、Tokenizer、AI library固有の例外mappingは、共通境界を実装するRS-0018ではなく、RS-0003やRS-0007などの機能Ticketで追加する。
- 文書処理固有のerror codeとeventは、RS-0011の再着手時に`文書処理設計.md`へ反映し、RS-0001・RS-0002で実装する。
- v0.0の範囲は増えるが、契約を利用する各コンポーネントが機能実装前に共通契約へ適合でき、後からの広範囲な置き換えを抑えられる。
- 新しいコンポーネントや実装言語を追加する場合は、共通契約の変更が必要かを確認したうえで、必要な実装Ticketを追加する。言語名の列挙だけを目的に共通契約や上位計画を書き換えない。
- 本ADRはADR-0001を置き換える。ADR-0001は履歴として保持し、`status: superseded`とする。
