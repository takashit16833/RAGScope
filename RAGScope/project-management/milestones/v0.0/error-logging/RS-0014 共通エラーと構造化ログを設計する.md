# RS-0014 共通エラーと構造化ログを設計する

## 目的

v0.0では、文書読み込み、Python AI Serviceとの通信、PostgreSQL処理など、異なる種類の処理と失敗を扱う。各実装Ticketが独自のエラー型、エラーコード、ログ項目、相関情報を決めると、処理全体を追跡できず、後から共通化する際に広範囲な修正が必要になる。

このTicketでは、RS-0015と後続機能の実装に先立ち、共通エラー契約と構造化ログの現在設計を`docs/design/エラー・ログ設計.md`として作成する。v0.0のローカル実行で必要な最小範囲を定義し、将来のHTTP、AWS収集、tracingへ拡張できる境界を保ちつつ、現時点で使用しない詳細は固定しない。

## 前提

- [ADR-0001 — 共通実行基盤をv0.0で段階的に導入する](<../../../../docs/adr/ADR-0001 共通実行基盤をv0.0で段階的に導入する.md>)が`accepted`である
- [v0.0 — 最小のdense検索を実行できる](../v0.0.md)に、共通エラーと構造化ログの最小基盤が対象として記載されている

## 完了条件

- [ ] `docs/design/エラー・ログ設計.md`が`note_type: design`の機能設計書として作成されている
- [ ] 共通エラー、CLIなどの利用者向けエラー表示、HTTPなどの境界で受け渡す失敗、構造化ログイベントの責務と変換境界が区別されている
- [ ] エラーの分類、安定したエラーコードの命名、利用者向けmessage、内部原因、追加contextの扱いが定義されている
- [ ] エラー分類とログlevelを別の概念として扱い、v0.0で使用するログlevelと意味が定義されている
- [ ] 構造化ログを、共通Envelope、実行Context、イベント固有Payloadに分ける方針が記載されている
- [ ] v0.0で必要な共通項目、event名の命名規則、schema version、時刻、level、component、operation、error codeの扱いが定義されている
- [ ] 1イベントを識別する情報と、同じローカル実行に属するイベントを識別する相関情報の生成・引き継ぎ規則が定義されている
- [ ] 該当しないoptional項目を無制限な`null`として出力せず、イベントごとの構造を保つ方針が記載されている
- [ ] ローカルでは正常出力をstdout、構造化ログをstderrへ分離し、1イベント1行のJSON Linesとして出力する方針が記載されている
- [ ] アプリケーションイベントの意味と具体的なsinkを分離し、stderr向けsinkとテスト用sinkを利用できる設計になっている
- [ ] 文書本文、prompt、secret、認証情報などを不用意にログへ出さないための記録・masking方針が記載されている
- [ ] HaskellとPython AI Serviceが失敗情報を受け渡す際に共有する意味と、正確なHTTP schemaをAPI設計・OpenAPIで具体化する境界が記載されている
- [ ] retry / timeoutは別の実行制御であり、共通エラーへoperation横断の単純な`retryable`判定を埋め込まない方針が記載されている
- [ ] CloudWatchの具体設定、tracingの正確な相関規則、batch・非同期job固有の情報は後続Milestoneで決定することが明記されている
- [ ] 正確なHaskell型とencoderはコード、具体的なテストケースはテストコードを正本とすることが明記されている
- [ ] 所属Epicの`関連文書`から`エラー・ログ設計.md`を参照できる状態になっている
- [ ] 関連する要求定義、システムアーキテクチャ、ADR、v0.0 Milestoneに矛盾しないことを確認できる

## 対象外

- Haskellの共通エラー型、logger、sink、JSON encoderの実装
- 文書処理、Embedding生成、DB処理など、各機能で発生する具体的なエラーとイベントの網羅
- Python AI Serviceの実装
- HTTP APIの正確なrequest / responseとエラーschemaの確定
- retry回数、待機、backoff、jitter、timeoutなどoperation固有の実行制御
- CloudWatchのlog group、保持期間、metric filter、alarmの設計
- tracingの正確な`trace_id`、`span_id`、親子関係、処理間Linkの規則
- 実験結果と処理状態のPostgreSQLへの永続化

## 実装メモ

- 設計書には、実装だけでは分かりにくい責務、契約、不変条件、処理フロー、変更時の注意を記載する。
- 正確な型定義やJSON encoderのコードをMarkdownへ複製しない。
- v0.0ではCLI実行を具体的なContextとして扱い、HTTPやbatchの完全なschemaを先回りして作らない。
- 将来のtracingへ拡張できる意図は残すが、現時点で`trace_id`やSpan構造を採用済みとして記載しない。
