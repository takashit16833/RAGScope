# 2. リトライ・タイムアウト基盤Epic

ログEpicの後に着手します。

理由は、リトライが次のイベントを記録するためです。

- retryを行うと判断した
    
- 次の試行まで何ms待つ
    
- 何回目の試行か
    
- retry後に成功した
    
- 最大試行回数へ達した
    
- total timeoutへ達した
    

リトライ基盤はログ基盤を利用しますが、別責務として実装します。

## Epicの能力案

> **一時的な失敗を、安全性と時間制限を確認したうえで再試行できる**

## Ticket 1：リトライ・タイムアウト・冪等性を設計する

主な成果物：

```text
docs/design/リトライ・タイムアウト設計.md
```

設計する内容：

- `Transient`
    
- `Permanent`
    
- `Indeterminate`
    
- retry対象と非対象
    
- `max_attempts`の意味
    
- exponential backoff
    
- jitter
    
- `per_attempt_timeout`
    
- `total_timeout`
    
- `Retry-After`
    
- retry判断とエラー分類の境界
    
- 冪等性の確認
    
- retry安全性の宣言
    
- operation別Policy
    
- retryログとの連携
    

冪等性については、共通の「魔法の冪等化」を設計するのではなく、各operationが次を明示する契約を作ります。

```text
operation
副作用
retry対象の失敗
retry安全性
冪等性の担保方法
business key
idempotency keyの要否
transaction境界
重複実行時の期待結果
```

担保方法は処理ごとに異なります。

- 純粋処理
    
- read-only処理
    
- unique constraint
    
- upsert
    
- transaction
    
- idempotency key
    
- 専用idempotency table
    

などから選びます。

このEpicでは、将来のBatch job用idempotency tableまでは作りません。必要になる条件と設計原則を残し、実際のtableはBatchやjobを導入するEpicで作ります。

## Ticket 2：Haskellの共通retry executorを実装する

主な成果物：

- `RetryPolicy`
    
- `RetryDecision`
    
- `RetrySafety`
    
- error classifier
    
- retry executor
    
- per-attempt timeout
    
- total timeout
    
- exponential backoff
    
- jitter
    
- retry event hook
    
- テスト可能なclock／sleep／random境界
    

概念的には、

```text

RAGScope.Retry.Timeout
RAGScope.Retry.Safety
```

のような内部共通moduleです。

重要なのは、retry executorへ単に処理を渡すだけではなく、

> なぜ再実行して安全なのか

を一緒に渡させることです。

## Ticket 3：retry基盤の安全性を検証する

確認内容：

- `max_attempts`を超えて実行しない
    
- permanent errorを再試行しない
    
- retry安全性がない操作を再試行しない
    
- backoffが設定どおり増える
    
- jitterが範囲内になる
    
- per-attempt timeoutが働く
    
- total timeoutが働く
    
- retry前後のログが同じ`run_id`で追跡できる
    
- 最後に返すエラーが失われない
    
- retry後の成功を確認できる
    

この段階では、実際の文書読み込みにretryを無理に適用しません。共通executorはテスト用の一時失敗operationで検証できます。

## 規約はいつ更新するか

**規約は第1回で確認しますが、現時点では更新しない可能性が高い**です。

理由は、現在の規約ですでに、

- 現在のMilestoneだけをEpic・Ticketへ具体化する
    
- Epicの全体計画を先に確認する
    
- 共通設計が必要なら設計Ticketを先行させる
    
- 実装で具体化した内容を同じ設計書へ戻す
    

という今回必要な進め方を許容しているからです。

規約を変えるのは、たとえば確認の結果、

- 横断基盤Epicを現在の構造で正しく配置できない
    
- 設計書の責務や配置ルールが不足している
    
- 新しいFrontmatter propertyが本当に必要
    
- 複数Epicをまたぐ共通成果物の扱いが定義されていない
    

と判明した場合だけです。

今回の計画変更だけを理由に規約を変えるのは、規約をプロジェクト都合へ過剰適応させることになるので避けます。
