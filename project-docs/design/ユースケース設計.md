# ユースケース設計

> [!abstract] この文書の役割
> 利用者がRAGScopeへ依頼するトップレベルな操作と、操作ごとの入力・結果・主要な処理、1回の実行がどこからどこまでかを定義する。

## 1. ユースケースと実行境界

この文書では、利用者がRAGScopeへ依頼するトップレベルの操作をユースケースとする。Embedding生成、データベース検索、文書チャンク化など、ユースケースから呼び出す処理は、そのユースケースを構成する内部処理として扱う。

各ユースケースの「入力」には、RAGScope Applicationがユースケースを呼び出すときに渡す値を定義する。「結果」には、ユースケースがRAGScope Applicationへ返す値、またはRAGScope Applicationへ制御を戻す前に作る状態を定義する。

1回のユースケース実行は、RAGScope Applicationがユースケースを呼び出した時点で開始し、その呼び出しからRAGScope Applicationへ制御が戻った時点で終了する。RAGScope Applicationがユースケースを呼び出さなかった場合、ユースケース実行は発生しない。CLIやAPIによる入力の受け取りと変換、ユースケースの呼び出し終了後に行う表示やHTTPレスポンスへの変換は、ユースケース実行に含めない。

ユースケースが「結果」に定義した値をRAGScope Applicationへ返した場合、または「結果」に定義した状態を作ってからRAGScope Applicationへ制御を戻した場合を、そのユースケース実行の成功とする。どちらも行わずにユースケース実行が終了した場合を失敗とする。内部処理で失敗が発生しても、ユースケースが再試行または代替処理を行い、最終的に「結果」に定義した値を返すか状態を作った場合は成功とする。

ユースケースは、RAGScope Applicationとの呼び出し境界で成功と最終失敗を`Either`によって明示的な値として返す。最終失敗は`Left`、成功は`Right`として区別し、通常のユースケース失敗を例外によってRAGScope Applicationへ伝達しない。ユースケース内部で失敗を短絡的に伝播させる実装には`ExceptT`を使用できるが、その基底Monadはこの文書では固定しない。例外そのものの扱いは、この規則とは別に定義する。

各ユースケースは、そのユースケースが最終失敗として返し得る理由をユースケース固有の失敗型で表す。UseCase境界の失敗型として共通の`AppError`を使用しない。失敗型は、各失敗を表現しApplicationが扱うために必要な情報をconstructorごとに保持できるが、旧`AppError`の共通フィールドを一律に持たせることは要求しない。dense検索では、この失敗型を`DenseSearchFailure`とする。

ユースケースが`Left`で返す失敗型は`ToErrorType`を満たし、その失敗値だけから対応する`ErrorType`を一意に決定できる。`toErrorType`の変換にRAGScope Applicationの実行状況など追加のContextを要求しない。ここで`ErrorType`は[実行追跡・構造化ログ契約設計](./logging/実行追跡・構造化ログ契約設計.md)の`error_type`をHaskellで表す値であり、その内部表現と`ToErrorType`のmodule・package配置はこの文書では固定しない。

同じ利用者操作をCLI、APIなど異なるインターフェースから実行しても、同じユースケースとして扱う。

## 2. ユースケース

| ドメイン領域 | ユースケース | 利用者の目的 |
|---|---|---|
| 文書 | [文書を検索可能にする](#211-文書を検索可能にする) | Markdown文書をdense検索の検索対象として利用できる状態にする |
| 検索・回答生成 | [dense検索する](#221-dense検索する) | 質問に近い文書チャンクを順位付きで取得する |

### 2.1 文書

#### 2.1.1 文書を検索可能にする

| 項目 | 内容 |
|---|---|
| 目的 | Markdown文書をdense検索の検索対象として利用できる状態にする |
| 入力 | 取り込み対象のMarkdown文書 |
| 結果 | 文書チャンクとそのEmbeddingが保存され、dense検索で利用できる状態になる |

主要な処理は次のとおりである。文書の読み込み、空本文の判定、チャンク化の条件は[文書処理設計](./features/文書処理設計.md)に従う。

1. Markdown文書をUTF-8として読み込む。UTF-8として読み込めない場合、または読み込んだ本文のUnicodeコードポイント数が0件の場合は、文書チャンクを生成せず終了する。
2. 本文を1,000 Unicodeコードポイントごとに、チャンク間の重複範囲を設けず文書チャンクへ分割する。
3. 各文書チャンクのEmbeddingを生成する。
4. 文書チャンクとEmbeddingを保存し、dense検索で利用できる状態にする。

### 2.2 検索・回答生成

#### 2.2.1 dense検索する

| 項目 | 内容 |
|---|---|
| 目的 | 質問に近い文書チャンクを順位付きで取得する |
| 前提 | dense検索で利用できる検索対象データが保存済みである |
| 入力 | 空でない質問1件 |
| 結果 | 順位付きの文書チャンク。0件も正常な結果として扱う |

主要な処理は次のとおりである。

1. 質問のEmbeddingを生成する。
2. 質問Embeddingを使って保存済みの文書チャンクをexact vector searchする。
3. 検索結果を順位付きの文書チャンクとして返す。
