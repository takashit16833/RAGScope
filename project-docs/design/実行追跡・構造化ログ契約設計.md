# 実行追跡・構造化ログ契約設計

> [!abstract] この文書の役割
> RAGScopeで発生する処理を因果関係とドメイン上の識別子で追跡し、構造化ログ1件が表す事実、発生元、重要度、出来事、失敗情報を、実装言語と外部表現から独立して定義する。

## 1. 構造化ログ1件が表す事実

構造化ログ1件は、1つの出来事が1回発生したという事実を表す。同じレコードへ複数の出来事をまとめず、変化する値を出来事の識別子へ埋め込まない。

| 概念 | 必須 | 意味 |
|---|---|---|
| 発生時刻 | 必須 | 出来事が発生した時刻。 |
| 発生元 | 必須 | その出来事を観測して記録したRAGScopeのコンポーネント。必要な場合は同じコンポーネントの実行インスタンスも区別する。 |
| 重要度 | 必須 | その出来事を運用上どの程度重く扱うかを表す順序付き分類。 |
| 出来事 | 必須 | 発生した事実の種類を機械的に識別する安定した名称。 |
| メッセージ | 任意 | 人が読むための補足説明。機械判定には使用しない。 |
| 属性 | 任意 | その発生に固有の構造化された追加情報。 |
| 処理関係 | 任意 | この出来事が属する因果的な処理の連なりと現在の処理単位。 |
| ドメイン参照 | 任意 | 実験、評価問題など、RAGScopeが永続的に管理する対象への参照。 |
| 共通エラー | 任意 | 出来事が失敗を報告する場合の失敗理由。[共通エラー契約設計](./共通エラー契約設計.md)に従う。 |

発生元は出来事の種類とは別に保持する。同じ出来事がRAGScopeアプリケーションとAI推論サービスの両方から発生し得る場合でも、出来事名へコンポーネント名を埋め込んで発生元を表さない。

出来事の名称は出来事の種類を識別し、その発生ごとに変わる実験識別子、HTTPパス、エラーメッセージなどは属性またはドメイン参照として記録する。

## 2. 重要度、出来事、失敗の関係

RAGScopeの論理契約では、重要度を次の5段階として扱う。

| 重要度 | 意味 |
|---|---|
| `debug` | 通常運用では不要だが、処理内容を詳しく確認するときに利用する診断情報。 |
| `info` | 処理開始、完了、主要な進行など、正常な出来事。 |
| `warn` | 処理を継続できるが、通常とは異なる状態または注意が必要な出来事。 |
| `error` | 処理の一部または処理全体が成立しなかった出来事。 |
| `fatal` | 発生元のコンポーネントが処理を継続できない出来事。 |

重要度、出来事、処理結果、共通エラーは別の概念として保持する。

- 出来事名だけから重要度を導出しない。
- `warn`は処理失敗を意味しない。
- `error`または`fatal`のログが存在しても、より上位の処理全体が必ず失敗したとは限らない。
- 追跡対象の処理単位が失敗して終了したことを記録する場合は、重要度を`error`以上とし、共通エラーを必須とする。
- 共通エラーを持つログでは、失敗理由の機械判定をエラー種別で行い、メッセージ文字列や重要度から推測しない。

この分離により、途中で失敗を検出して別経路へ切り替えた処理と、最終的に失敗して終了した処理を同じ意味として扱わない。

## 3. 処理関係

### 3.1 共通の処理単位

RAGScopeは、因果関係を追跡する必要がある処理を「処理単位」として扱う。処理単位は共通の親子関係を持つが、意味の異なる処理を同一種類として扱わない。

| 種類 | 表すもの |
|---|---|
| `entrypoint` | 利用者または外部ツールからRAGScopeへ入った1回のCLI実行またはAPI request。 |
| `operation` | 実験、質問処理、検索段階、モデル呼び出しなど、RAGScopeが実行するまとまりのある処理。 |
| `request` | RAGScopeアプリケーションとAI推論サービスなどの間で行う1回の通信。 |
| `lifecycle` | コンポーネントの起動、準備、停止など、そのコンポーネント自身のライフサイクル処理。 |

CLI/API入口、ドメイン上の処理、HTTP request、コンポーネントライフサイクルは、それぞれ別の意味を持つ。これらは共通の処理関係を利用するが、種類を失って同じ概念へ統合しない。

### 3.2 因果関係

処理関係は次の3つの識別によって表す。

| 概念 | 意味 |
|---|---|
| trace | 1つの入口から派生する、コンポーネントをまたいだ因果的な処理の連なり。 |
| activity | 現在実行している1つの処理単位。 |
| parent activity | 現在の処理単位を直接開始した親の処理単位。根の処理単位には存在しない。 |

traceの識別子はW3C Trace Contextのtrace-idと同じ意味を採用する。HTTP境界では`traceparent`を使用してtraceと親処理の関係を伝播する。受信した有効なtrace contextがある場合はそのtraceを継続し、ない場合はRAGScope側で新しいtraceを開始する。

activityはW3C Trace Contextにおける処理位置と対応できる単位とし、HTTP requestを送る場合は現在のactivityを親として下位の処理を開始する。`tracestate`を扱う場合は外部トレーシング情報の伝播用として扱い、RAGScopeの実験識別子などドメイン情報を格納しない。

> [!important] traceとドメイン識別子を分ける
> traceは一時的な因果関係を追跡する識別であり、実験や評価問題などRAGScopeが管理する対象の識別子ではない。1つのドメイン対象が複数のtraceにまたがること、1つのtraceが複数のドメイン対象を参照することを許容する。

### 3.3 ドメイン参照

ログは、必要な場合に実験、評価問題などのドメイン対象への型付き参照を持つ。

ドメイン参照の識別子は各機能の正本が定義する。traceやactivityの識別子を、実験識別子、質問識別子、文書識別子などの代わりに使用しない。

これにより、次を別々に検索できる。

- 同じ因果的な処理に属するログ
- 同じ実験や評価問題に関係するログ
- 特定コンポーネントまたは特定種類の処理に属するログ

## 4. 処理の開始、進行、終了

追跡対象の処理単位は、少なくとも開始と終了を記録できる。

| 記録 | 必須情報 |
|---|---|
| 開始 | 処理単位の種類と名称、処理関係、必要なドメイン参照 |
| 進行 | 発生した出来事、必要な属性、処理関係 |
| 正常終了 | 終了した処理単位、成功したこと、必要な結果の要約 |
| 失敗終了 | 終了した処理単位、失敗したこと、共通エラー |

処理結果は`success`または`failure`として扱い、終了記録でのみ必須とする。途中のログ重要度から最終結果を推測しない。

処理時間をログへ記録する場合は、開始・終了時刻または計測した所要時間を属性として保持できる。実験結果として保存・評価する正確な処理時間の正本は、その処理結果を管理する機能設計とデータモデルに置く。

## 5. 外部標準との境界

| 標準 | RAGScopeで採用する意味 | 論理契約へ持ち込まないもの |
|---|---|---|
| OpenTelemetry Logs Data Model | 発生時刻、発生元、重要度、出来事、属性、trace contextを別の意味として扱う考え方。 | OpenTelemetry SDK、Collector、OTLPの導入や具体的なシリアライズ形式。 |
| W3C Trace Context | コンポーネントをまたぐtrace識別と親処理の伝播。 | vendor固有の`tracestate`内容をRAGScopeのドメイン契約として解釈すること。 |
| RFC 5424 | 重要度、発生元、構造化データ、本文を分離し、メッセージ内容と転送方式を分ける考え方。 | syslogのFacility値、PRI計算、syslog wire formatをRAGScope内部契約として採用すること。 |

RAGScopeの重要度はOpenTelemetryの同名範囲へ一意に投影できる。RFC 5424へ出力する場合は、その境界でsyslog Severityへ対応付ける。どちらの数値表現もRAGScopeの論理契約には含めない。

## 6. 外部表現への投影

この文書はJSON、TSV、syslog、OTLPなどの列名、階層、エンコーディングを定義しない。

外部表現は、次の意味を失わず独立に投影できなければならない。

- 出来事の発生時刻
- 発生元
- 重要度
- 出来事
- 必要な属性
- traceとactivityの関係
- 必要なドメイン参照
- 処理終了時の結果
- 失敗時の共通エラー

JSONとTSVへの具体的な投影は、RS-0020の後続検証で独立に作成する。
