# ログ・イベント設計

> [!abstract] この文書の役割
> RAGScopeで観測する情報をSpan、Span属性、OpenTelemetry LogsのEventRecord、通常のLogRecordのどこへ置くかと、同じ失敗を複数回記録しないための共通規則を定義する。

## 1. 基本方針

RAGScopeで新たに定義する名前付きイベントは、OpenTelemetry LogsのEventRecordとして記録する。RAGScope独自のSpan Eventは使用しない。

観測したい情報は次の基準で配置する。

| 情報 | 表現 |
|---|---|
| 開始から終了まで時間を持つ処理 | Span |
| そのSpanの処理を説明する値で、独立した時刻を持つ必要がない情報 | Span attributes |
| ある時点で起きた、名前を付けて検索・集計したい出来事や状態遷移 | EventRecord |
| 名前付きイベントにする必要がない診断メッセージ | 通常のLogRecord |

OpenTelemetry Semantic Conventionに該当する標準Eventや属性がある場合はそれを優先する。Spanの開始・終了・Status・属性だけで同じ事実を十分に確認できる場合、同じ事実を表すEventRecordを追加しない。

## 2. EventRecordを作成する条件

UseCaseや内部処理が具体的なerror typeで失敗を返したことだけでは、EventRecordを作成しない。retry、timeout、fallbackの途中で一度失敗したことだけでも、共通のEventRecordを自動生成しない。

Spanの最終結果を見るだけでは分からない出来事を、後から名前で検索・集計する必要がある場合にEventRecordを定義する。たとえば状態遷移そのものを独立した出来事として残す必要がある場合がこれに当たる。

RAGScope独自EventRecordが必要な場合、そのイベントを所有するUseCaseまたは内部処理の設計で少なくとも次を定義する。

- 何が起きたイベントか
- 記録する条件
- EventName
- timestampが表す時点
- Severity
- attributes
- 失敗イベントで`error.type`が必要な場合、どの具体的なerror typeからどの値へ変換するか

RAGScope独自EventNameは`ragscope.*`名前空間を使用する。文書ID、件数、error値など実行ごとに変わる値をEventNameへ埋め込まず、attributesへ置く。

## 3. Traceとの関連付けとSeverity

EventRecordと通常のLogRecordは、OpenTelemetryが保持する現在のTrace Contextを使って、対応するTrace / Spanへ関連付ける。TraceId / SpanIdを保持するRAGScope独自の仕組みは別に作らない。

SeverityはOpenTelemetryのSeverityNumberとして扱う。RAGScope共通の`debug` / `info` / `warn` / `error` / `fatal`という固定5段階契約は設けない。LogRecordのSeverityが高いことだけを理由に、Spanを`Error`へ変更したり、RAGScopeの処理自体を失敗扱いにしたりしない。

## 4. 失敗とException

Semantic Conventionに該当せずRAGScopeが用途を決めるSpanで、UseCaseや内部処理が返した具体的なerror typeがそのSpanの最終的な失敗になった場合は、まずSpan Statusと`error.type`でその失敗を表す。同じ失敗を示すEventRecordを自動では追加しない。

unexpected同期Exceptionが追跡対象の処理から外へ伝播する場合は、対応するSpanを`Error`として記録することに加えて、LogsへExceptionを表すEventRecordを1件だけ記録し、Exceptionを再throwする。

同じExceptionについて、UseCase Spanとentry Spanの両方でEventRecordを作るなど、複数の層で重複して記録しない。CLI / APIの入力・出力を扱うhandler相当の処理境界でも、同じExceptionを追加で記録しない。

OpenTelemetryの標準計装によって、そのExceptionが発生した処理に近い場所ですでに同じException EventRecordが記録されている場合は、上位の処理で重複して記録しない。

採用するHaskell SDKのSpan helperなどがExceptionを自動的にSpan Eventへ記録し、LogsのException EventRecordと同じ事実を二重に記録する場合は、OpenTelemetry Adapter側でそのSpan Eventを記録しないようにし、Logs側の1件だけを残す。

## 5. 外部表現と出力基盤

LogRecordのProcessor、Exporter、batching、flush / shutdown、送信はOpenTelemetry SDKへ委ねる。OpenTelemetry Logsとは別に、RAGScope共通のログ基盤として`LogRecord`型、Logging Runtime、Sink、JSON serializationを持たない。

RS-0021までに検討したRAGScope独自のログJSON SchemaやSQLite投影は、OpenTelemetry Logsとは別の共通ログ形式としては使用しない。将来、RAGScopeがOpenTelemetryとは別に安定した外部ログ形式を公開する要求が生じた場合は、その要求を持つ契約として別途設計する。
