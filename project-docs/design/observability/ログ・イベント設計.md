# ログ・イベント設計

> [!abstract] この文書の役割
> RAGScopeで観測する情報をSpan、Span属性、OpenTelemetry LogsのEventRecord、通常LogRecordのどこへ置くかと、同じ失敗を複数回記録しないための共通規則を定義する。

## 1. 基本方針

RAGScopeで新たに定義する名前付きイベントは、OpenTelemetry LogsのEventRecordとして記録する。RAGScope独自のSpan Eventは使用しない。

観測したい情報は次の基準で配置する。

| 情報 | 表現              |
|---|---|
| 開始から終了まで時間を持つ処理 | Span            |
| そのSpanの処理を説明する値で、独立した時刻を持つ必要がない情報 | Span attributes |
| ある時点で起きた、名前を付けて検索・集計したい出来事や状態遷移 | EventRecord     |
| 名前付きイベントにする必要がない診断メッセージ | 通常LogRecord     |

OpenTelemetry Semantic Conventionに該当する標準Eventや属性がある場合はそれを優先する。Spanの開始・終了・Status・属性だけで同じ事実を十分に確認できる場合、同じ事実を表すEventRecordを追加しない。

## 2. EventRecordを作成する条件

UseCaseや内部処理が具体的なerror typeで失敗を返したことだけでは、EventRecordを作成しない。retry、timeout、fallbackの途中で一度失敗したことだけでも、それらの失敗を一律に表すEventRecordを自動生成しない。

Spanの最終結果を見るだけでは分からない出来事を、後から名前で検索・集計する必要がある場合にEventRecordを定義する。たとえば状態遷移そのものを独立した出来事として残す必要がある場合がこれに当たる。

RAGScope独自EventRecordが必要な場合、そのEventRecordを定義するUseCaseまたは内部処理の設計で少なくとも次を定義する。

- 何が起きたイベントか
- 記録する条件
- EventName
- timestampが表す時点
- Severity
- attributes
- 失敗イベントで`error.type`が必要な場合、どの具体的なerror typeからどの値へ変換するか

RAGScope独自EventNameは`ragscope.*`名前空間を使用する。文書ID、件数、error値など実行ごとに変わる値をEventNameへ埋め込まず、attributesへ置く。

## 3. Traceとの関連付けとSeverity

EventRecordと通常LogRecordは、OpenTelemetryが保持する現在のTrace Contextを使って、対応するTrace / Spanへ関連付ける。TraceId / SpanIdはそのTrace Contextから得る。

RAGScopeのTelemetry利用境界では、Severityを`Debug`、`Info`、`Warn`、`Error`の4段階に限定する。

| Severity | 意味 |
|---|---|
| `Debug` | 診断や調査のための詳細情報 |
| `Info` | 正常な処理や出来事として残す情報 |
| `Warn` | 処理は継続できるが、注意が必要な異常や劣化を示す情報 |
| `Error` | 失敗を示す情報 |

OpenTelemetry Adapterは、この4段階を対応するOpenTelemetry `SeverityNumber`へ変換する。OpenTelemetryの24段階の`SeverityNumber`や任意の数値はRAGScopeの利用側へ公開しない。現在のRAGScopeには同じseverity range内の細かな段階を使い分ける規則がなく、それらを公開すると機能ごとに意味のない差を選べてしまうためである。

severityを指定しない状態はSeverityとは別に扱い、`Default`というSeverityは設けない。`Trace`や`Fatal`のような追加の段階は、RAGScopeでそれらを`Debug`または`Error`と区別して扱う具体的な要求が生じた場合に追加を検討する。

LogRecordのSeverityが高いことだけを理由に、Spanを`Error`へ変更したり、RAGScopeの処理自体を失敗扱いにしたりしない。

## 4. 失敗と例外

Semantic Conventionに該当せずRAGScopeが用途を決めるSpanで、UseCaseや内部処理が返した具体的なerror typeがそのSpanの最終的な失敗になった場合は、まずSpan Statusと`error.type`でその失敗を表す。同じ失敗を示すEventRecordを自動では追加しない。

例外が処理されないままSpanの外へ伝播する場合は、対応するSpanを`Error`として記録することに加えて、Logsへ例外を表すEventRecordを1件だけ記録し、例外を再throwする。

同じ例外を表すEventRecordを複数のSpanや処理から重複して記録しない。UseCase Spanで記録した例外をroot SpanやCLI / APIの入力・出力を扱う処理で追加記録する、といった重複をしない。

OpenTelemetryの標準計装が同じ例外を表すEventRecordをすでに記録している場合は、その例外を受け取った別の処理から追加で記録しない。

採用するHaskell SDKのAPIが例外を自動的にSpan Eventへ記録し、Logsで記録する例外のEventRecordと同じ事実が二重に残る場合は、OpenTelemetry Adapter側でその自動記録を無効にし、Logs側の1件だけを残す。

## 5. 出力基盤

LogRecordのProcessor、Exporter、batching、flush / shutdown、送信はOpenTelemetry SDKへ委ねる。
