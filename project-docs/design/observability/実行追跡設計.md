# 実行追跡設計

> [!abstract] この文書の役割
> 利用インターフェースからの1回の呼び出しをどのTrace・Spanで追跡するか、コンポーネント間でTrace Contextをどう引き継ぐか、各Spanの成功・失敗をどう表すかを定義する。

## 1. InvocationとTrace

[Invocation](../../RAGScope用語集.md#invocation)ごとに、他のInvocationから独立した1つのTraceを作成する。Invocationはユースケース実行より広く、入力検証などでUseCaseを呼ばず終了した場合も存在する。

```text
Invocation
└─ root Span
   ├─ 入力の受け取り・変換
   ├─ UseCase Span（UseCaseを呼び出した場合だけ）
   │  ├─ DB client Span
   │  └─ GenAI / HTTP client Span
   └─ 出力の変換
```

## 2. root Spanと子Span

Invocation全体を1つのroot Spanで追跡する。

- RAGScope API: HTTP server処理に適用できるSemantic Conventionに従うSERVER Spanをroot Spanとする。
- RAGScope CLI: CLIによる1回の呼び出しを表すExecutionのcallee Spanをroot Spanとする。

APIのHTTP SERVER SpanまたはCLIのExecution callee Spanとは別に、Invocation全体を包むRAGScope独自Spanは追加しない。入力の受け取り・変換から出力の変換までをまとめるためだけのSpanも追加しない。

RAGScopeアプリケーションがUseCaseを呼び出した場合、その実行範囲をroot Spanの子であるUseCase Spanとして追跡する。UseCaseを呼び出さない場合はUseCase Spanを作成しない。

PostgreSQL、HTTP client、GenAIなどOpenTelemetry Semantic Conventionが適用できる処理は標準Spanを利用する。GenAI Semantic Conventionで表す処理と、その処理のために送るHTTPリクエストの両方をSpanとして記録する場合は、同じSpanへ混ぜず、それぞれの処理を表すSpanを作って親子関係でつなぐ。

## 3. コンポーネント間のTrace Context

RAGScopeアプリケーションからAI推論サービスへ処理を依頼するときは、現在のTrace Contextを通信へ載せ（inject）、AI推論サービス側で取り出して（extract）、同じTraceを継続する。Trace Contextを通信上でどのHTTP headerなどへ載せるかは、採用するOpenTelemetry propagatorと通信実装・契約を正本とする。

RAGScope APIが外部callerからTrace Contextを受信しても、そのContextはRAGScopeのInvocation TraceのparentやSpan Linkには使用しない。

## 4. Span Status、Descriptionとerror.type

Semantic Conventionが対象SpanのStatus、Status Description、`error.type`を定める場合はその規則を優先する。Semantic Conventionに該当せず、RAGScopeが用途を決めるSpanでは、そのSpanが表す処理自身の終了状態だけを見てStatus、Status Description、`error.type`を決める。

| 処理自身の終了状態 | Span Status | Status Description | `error.type` |
|---|---|---|---|
| 成功 | `Unset` | 設定しない | 付与しない |
| UseCaseや内部処理が具体的なerror typeで失敗を返し、そのSpanの最終結果も失敗 | `Error` | 設定しない | error typeの種類から決まる値 |
| retry / fallback途中で失敗したが最終成功 | `Unset` | 設定しない | 付与しない |
| 例外が処理されないままSpan外へ伝播（中断・キャンセルを除く） | `Error` | 例外メッセージ | canonical exception class name |
| 意図された中断・キャンセルで処理が終了 | `Unset` | 設定しない | 付与しない |

子Spanが失敗したことだけを理由に親Spanを`Error`へ変更しない。親処理が子の失敗を処理し、自身の最終結果として成功した場合、親Spanは成功として扱う。

UseCaseや内部処理が返した具体的なerror typeから、その種類に対応する`error.type`へ直接変換する。ID、ファイル名、エラーメッセージなど実行ごとに変わる値は`error.type`へ含めず、同じ種類のエラーなら同じ値になるようにする。通常の失敗ではStatus Descriptionへ詳細な失敗理由や元のerror messageを複製しない。

Telemetry用の`error.type`へ変換しても、UseCaseや内部処理が持つ元のerror値を、その`error.type`で置き換えない。詳細な値やcauseは元のerror値に残す。

## 5. 例外と中断

UseCaseなどが具体的なerror typeで返す通常の失敗ではなく、例外が処理されないままSpanの外へ伝播する場合は、そのSpanを`Error`とする。Status Descriptionには採用するruntime / SDKで例外メッセージとして表現される値を設定し、`error.type`にはcanonical exception class name（採用するSDK / runtimeでその例外の種類を表す名前）を設定する。例外は再throwし、上位へ伝播させる。Logsへ記録する例外のEventRecordは[ログ・イベント設計](./ログ・イベント設計.md)に従う。

意図された中断やキャンセルは、ここで扱う例外には含めず、UseCaseなどが返す通常の失敗とも別に扱う。Span Statusは`Unset`のままとし、Status Descriptionと`error.type`を設定せず、exception Span Eventとして記録しない。処理自身の失敗とruntimeによる実行制御を同じエラーとして数えないためである。必要なcleanupと、Telemetryを安全に終了するために必要な処理を行ったうえで、元の中断・キャンセルを上位へそのまま伝播させる。

HaskellやPythonなど各runtimeで、どの型や機構を意図された中断・キャンセルとして判定するかは、各コンポーネントのコードとテストを正本とし、Observability共通設計では固定しない。ただし、意図された停止と判定できない例外やruntime failureは中断・キャンセルへ含めず、前段の未処理例外の規則に従う。

## 6. 実行識別子

実行追跡にはOpenTelemetryのTraceId / SpanIdを使用する。実験、評価データ、文書などの識別子は、それぞれのドメインデータとして扱う。
