# 実行追跡設計

> [!abstract] この文書の役割
> 利用インターフェースからの1回の呼び出しをどのTrace・Spanで追跡し、コンポーネント境界でContextをどう引き継ぎ、各Spanの成功・失敗をどう表すかを定義する。

## 1. InvocationとTrace

RAGScope APIまたはRAGScope CLIなどの利用インターフェースからRAGScopeへ行われた1回の外部呼び出しから、その呼び出しの処理が完了するまでを`Invocation`とする。1つのInvocationにつき、他のInvocationから独立した1つのTraceを作成する。

Invocationとユースケース実行は同じ範囲ではない。ユースケース実行はRAGScopeアプリケーションがUseCaseを呼び出してから制御が戻るまでであり、Invocationはその前後の入力・出力変換も含む。入力検証などでUseCaseを呼ばず終了した場合もInvocationは存在する。

```text
Invocation
└─ entry Span
   ├─ 入力の受け取り・変換
   ├─ UseCase Span（UseCaseを呼び出した場合だけ）
   │  ├─ DB client Span
   │  └─ GenAI / HTTP client Span
   └─ 出力の変換
```

## 2. entry Spanと子Span

Invocationを観測するroot Spanをentry Spanと呼ぶ。entry SpanはRAGScope内での役割名であり、OpenTelemetry独自のSpan種別ではない。

- RAGScope API: HTTP server処理に適用できるSemantic Conventionに従うSERVER Spanをentry Spanとする。
- RAGScope CLI: CLIによる1回の呼び出しを表すExecutionのcallee Spanをentry Spanとする。

Invocationだけを表す追加Spanは作成しない。CLI / APIの入力変換から出力変換までをまとめた独自のhandler Spanも作成しない。

RAGScopeアプリケーションがUseCaseを呼び出した場合、その実行範囲をentry Spanの子であるUseCase Spanとして追跡する。UseCaseを呼び出さない場合はUseCase Spanを作成しない。

PostgreSQL、HTTP client、GenAIなどOpenTelemetry Semantic Conventionが適用できる処理は標準Spanを利用する。GenAIの論理処理と、そのためのHTTPリクエストを両方計装する場合は同一Spanへ混ぜず、それぞれ該当する処理を表すSpanとして親子関係を構成する。

## 3. コンポーネント間のTrace Context

RAGScopeアプリケーションからAI推論サービスへ処理を依頼するときは、現在のTrace Contextを通信境界へinjectし、AI推論サービスでextractして同じTraceを継続する。具体的なHTTP headerなどの表現は、採用するOpenTelemetry propagatorと通信実装・契約を正本とする。

RAGScope APIが外部callerからTrace Contextを受信しても、そのContextをRAGScopeのInvocation Traceのparentにはしない。現在の要求では外部callerとの分散TraceをRAGScopeのInvocationへ接続する必要がないため、Span Linkも追加しない。

## 4. Span Statusとerror.type

Semantic Conventionが対象SpanのStatusや`error.type`を定める場合はその規則を優先する。RAGScope独自Spanでは、そのSpanが表す処理自身の最終結果だけで決定する。

| 処理自身の最終結果 | Span Status | `error.type` |
|---|---|---|
| 成功 | `Unset` | 付与しない |
| typed failureで失敗確定 | `Error` | 具体的なerror typeから導出する低cardinalityな値 |
| retry / fallback途中で失敗したが最終成功 | `Unset` | 付与しない |
| unexpected同期ExceptionがSpan外へ伝播 | `Error` | canonical exception class name |

子Spanが失敗したことだけを理由に親Spanを`Error`へ変更しない。親処理が子の失敗を処理して自身の結果として成功した場合、親Spanは成功として扱う。

RAGScope共通の`RAGScopeError`、`ErrorType`、`ErrorClassifier`を介して`error.type`を決定しない。具体的なUseCaseまたは内部処理のerror typeから直接変換する。詳細な値やcauseは元のerror表現で保持し、`error.type`へ埋め込まない。

## 5. Exceptionと中断

unexpected同期Exceptionが追跡中の処理から外へ伝播する場合、その処理のSpanを`Error`とし、`error.type`にcanonical exception class nameを設定したうえでExceptionを再throwする。Logsへ記録するException EventRecordは[ログ・イベント設計](./ログ・イベント設計.md)に従う。

async interruptionやcancellationはtyped failureやunexpected同期Exceptionと同じ共通分類へまとめない。必要なcleanupとTelemetry終了処理を行ったうえで再throwする。個別runtimeのcancellation表現をObservability共通設計で固定しない。

## 6. 実行識別子

RAGScope独自の`execution_id`を、Traceと並行する共通実行追跡IDとして維持しない。実行追跡にはOpenTelemetryのTraceId / SpanIdを使用する。実験、評価データ、文書などドメイン上必要な識別子は、それぞれのドメインデータとして扱い、Telemetryの実行識別子とは混同しない。
