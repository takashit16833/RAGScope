# 実行追跡設計

> [!abstract] この文書の役割
> 利用インターフェースからの1回の呼び出しをどのTrace・Spanで追跡するか、コンポーネント間でTrace Contextをどう引き継ぐか、各Spanの成功・失敗をどう表すかを定義する。

## 1. InvocationとTrace

[Invocation](../../RAGScope用語集.md#invocation)ごとに、他のInvocationから独立した1つのTraceを作成する。Invocationはユースケース実行より広く、入力検証などでUseCaseを呼ばず終了した場合も存在する。

```text
Invocation
└─ entry Span
   ├─ 入力の受け取り・変換
   ├─ UseCase Span（UseCaseを呼び出した場合だけ）
   │  ├─ DB client Span
   │  └─ GenAI / HTTP client Span
   └─ 出力の変換
```

## 2. entry Spanと子Span

Invocationを観測するroot Spanをentry Spanと呼ぶ。entry SpanはRAGScope内での役割名であり、OpenTelemetry独自のSpan種別ではない。

- RAGScope API: HTTP server処理に適用できるSemantic Conventionに従うSERVER Spanをentry Spanとする。
- RAGScope CLI: CLIによる1回の呼び出しを表すExecutionのcallee Spanをentry Spanとする。

Invocationだけを表す追加Spanは作成しない。CLI / APIの入力変換から出力変換までをまとめた独自のhandler Spanも作成しない。

RAGScopeアプリケーションがUseCaseを呼び出した場合、その実行範囲をentry Spanの子であるUseCase Spanとして追跡する。UseCaseを呼び出さない場合はUseCase Spanを作成しない。

PostgreSQL、HTTP client、GenAIなどOpenTelemetry Semantic Conventionが適用できる処理は標準Spanを利用する。GenAIの論理処理と、そのためのHTTPリクエストの両方をSpanとして記録する場合は、同じSpanへ混ぜず、それぞれの処理を表すSpanを作って親子関係でつなぐ。

## 3. コンポーネント間のTrace Context

RAGScopeアプリケーションからAI推論サービスへ処理を依頼するときは、現在のTrace Contextを通信へ載せ（inject）、AI推論サービス側で取り出して（extract）、同じTraceを継続する。Trace Contextを通信上でどのHTTP headerなどへ載せるかは、採用するOpenTelemetry propagatorと通信実装・契約を正本とする。

RAGScope APIが外部callerからTrace Contextを受信しても、そのContextをRAGScopeのInvocation Traceのparentにはしない。現在の要求では外部callerとの分散TraceをRAGScopeのInvocationへ接続する必要がないため、Span Linkも追加しない。

## 4. Span Statusとerror.type

Semantic Conventionが対象SpanのStatusや`error.type`を定める場合はその規則を優先する。Semantic Conventionに該当せず、RAGScopeが用途を決めるSpanでは、そのSpanが表す処理自身の最終結果だけを見てStatusと`error.type`を決める。

| 処理自身の最終結果 | Span Status | `error.type` |
|---|---|---|
| 成功 | `Unset` | 付与しない |
| UseCaseや内部処理が具体的なerror typeで失敗を返し、そのSpanの最終結果も失敗 | `Error` | error typeの種類から決まる値 |
| retry / fallback途中で失敗したが最終成功 | `Unset` | 付与しない |
| unexpected同期ExceptionがSpan外へ伝播 | `Error` | canonical exception class name |

子Spanが失敗したことだけを理由に親Spanを`Error`へ変更しない。親処理が子の失敗を処理し、自身の最終結果として成功した場合、親Spanは成功として扱う。

`error.type`を決めるためだけのRAGScope共通`RAGScopeError`、`ErrorType`、`ErrorClassifier`は作らない。UseCaseや内部処理が返した具体的なerror typeから、その種類に対応する`error.type`へ直接変換する。ID、ファイル名、エラーメッセージなど実行ごとに変わる値は`error.type`へ含めず、同じ種類のエラーなら同じ値になるようにする。

Telemetry用の`error.type`へ変換しても、UseCaseや内部処理が持つ元のerror値を、その`error.type`で置き換えない。詳細な値やcauseは元のerror値に残す。

## 5. Exceptionと中断

UseCaseなどが具体的なerror typeで返す通常の失敗ではなく、unexpected同期Exceptionが追跡中の処理から外へ伝播する場合は、その処理のSpanを`Error`とする。`error.type`にはcanonical exception class name（採用するSDK / runtimeでそのExceptionの種類を表す名前）を設定する。Exceptionは再throwし、上位へ伝播させる。Logsへ記録するException EventRecordは[ログ・イベント設計](./ログ・イベント設計.md)に従う。

async interruptionやcancellationは、UseCaseなどが返す通常の失敗やunexpected同期Exceptionと同じ種類へまとめない。必要なcleanupと、Telemetryを安全に終了するために必要な処理を行ったうえで再throwする。HaskellやPythonなど各runtimeがcancellationをどう表すかは、Observability共通設計では固定しない。

## 6. 実行識別子

RAGScope独自の`execution_id`を、Traceと並行する共通実行追跡IDとして維持しない。実行追跡にはOpenTelemetryのTraceId / SpanIdを使用する。実験、評価データ、文書などドメイン上必要な識別子は、それぞれのドメインデータとして扱い、Telemetryの実行識別子とは混同しない。
