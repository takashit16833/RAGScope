# 利用者操作詳細設計

> [!abstract] この文書の役割
> [利用者操作基本設計](./利用者操作基本設計.md)で定義する`OperationResult`をRAGScopeアプリケーションのHaskell実装でどう表現し、UseCase前・UseCase・UseCase後の具体的なfailureを利用者操作全体の失敗としてどう保持・受け渡すかを定義する。
>
> 利用者操作の実行境界と`OperationSuccess`・`OperationFailure`の意味は[利用者操作基本設計](./利用者操作基本設計.md)、UseCase境界とUseCase固有failureは[ユースケース詳細設計](./ユースケース詳細設計.md)、具体的なfailureから共通`ErrorType`への変換は[ErrorType変換詳細設計](./ErrorType変換詳細設計.md)を正本とする。正確なHaskell型・constructor・関数・moduleは実装コードを機械可読な正本とする。

## 1. `OperationResult`のHaskell表現

1回の利用者操作全体のHaskell境界では、概念上の`OperationResult`を次の形で表す。

```haskell
Either operationFailure result
```

- `Right result`を`OperationSuccess`として扱う。
- `Left operationFailure`を`OperationFailure`として扱う。
- `OperationSuccess`・`OperationFailure`という結果区分を表すためだけの共通`OperationResult` ADTは導入しない。

UseCase境界の`Either useCaseFailure result`と利用者操作境界の`Either operationFailure result`は、どちらもHaskellの`Either`を使うが表す処理範囲が異なる。UseCase境界はUseCase自身の結果だけを表し、利用者操作境界はUseCase前後を含む操作固有処理全体の結果を表す。

```text
UseCase境界
Either useCaseFailure result

利用者操作境界
Either operationFailure result
```

## 2. 操作固有failureの構造

`operationFailure`には、すべての利用者操作で共用する汎用failure型を使用しない。各トップレベルな利用者操作は、その操作で実際に発生し得る具体的なfailureだけを列挙した操作固有failure型を持つ。

たとえばdense検索操作に入力処理、dense検索UseCase、結果処理の3種類の失敗源がある場合、概念的には次のように表す。

```haskell
data DenseSearchOperationFailure
  = DenseSearchInputFailure InputFailure
  | DenseSearchUseCaseFailure DenseSearchFailure
  | DenseSearchOutputFailure OutputFailure
```

この宣言は構造を示す概念例であり、正確な型名・constructor名・保持する型は対象インターフェースの実装コードを正本とする。

次のような共通のパラメータ化failure型は導入しない。

```haskell
data OperationFailure pre useCase post
  = PreFailure pre
  | UseCaseFailure useCase
  | PostFailure post
```

操作固有failure型は、UseCase前・UseCase・UseCase後という固定された3区分を共通化することではなく、その操作がどの具体的な理由で成立しなかったかを型として保持することを目的とする。UseCaseを呼び出さない操作や、前後処理に複数種類のfailureがある操作でも、その操作に実際に存在するfailureだけをconstructorとして持つ。

## 3. UseCase failureの受け渡し

UseCaseが`Left useCaseFailure`を返した場合、利用者操作側はその具体的なUseCase failure値を操作固有failureの対応するconstructorで包む。`ErrorType`や別の共通failureへ変換してから保持しない。

```text
DenseSearchFailure
        ↓ 操作固有constructorで包む
DenseSearchUseCaseFailure DenseSearchFailure
```

このラップによって、UseCaseが返した具体的なfailure値を失わずに、利用者操作全体では「この操作がUseCaseの失敗によって成立しなかった」ことを表せる。

UseCase前・UseCase後のfailureも同様に、それぞれを所有する処理の具体的なfailure値を操作固有failureのconstructorで保持する。UseCase外のfailureをUseCase固有failureへ変換しない。

## 4. 所有者とmodule配置

操作固有failure型は、そのトップレベルな利用者操作を組み立てる利用インターフェース側が所有する。Featureや`ragscope-error`は所有しない。

同じUseCaseをCLIとAPIから呼び出しても、入力処理や結果処理などUseCase前後の処理が異なり得るため、CLI操作とAPI操作のfailure型をUseCaseが同じであることだけを理由に共有しない。

moduleは対象インターフェースと操作を表すnamespaceの下に置く。概念例は次のとおりである。

```text
RAGScope.CLI.<Operation>.Failure
RAGScope.API.<Operation>.Failure
```

正確なmodule名は各インターフェースの実装構成とコードを正本とする。ただし、操作固有failure型をFeature moduleや共通`ragscope-error` packageへ置かないという依存方向は維持する。

操作固有failure型を定義するlibraryは、保持するUseCase固有failure型のmoduleと`RAGScope.ErrorType`をimportする。Feature側から利用インターフェース側の操作固有failureへ依存させない。

## 5. `ToErrorType`との接続

root `span`などで操作全体のfailureを`error_type`として観測できるよう、操作固有failure型にも`ToErrorType` instanceを定義する。

操作固有failureが既に`ToErrorType` instanceを持つ具体的なfailureを包んでいる場合、外側のinstanceはconstructorを判別して中のfailureを取り出し、そのfailure自身の`toErrorType`へ変換を委ねる。

```haskell
instance ToErrorType DenseSearchOperationFailure where
  toErrorType = \case
    DenseSearchInputFailure failure ->
      toErrorType failure
    DenseSearchUseCaseFailure failure ->
      toErrorType failure
    DenseSearchOutputFailure failure ->
      toErrorType failure
```

この`case`はfailureごとに別の分類規則を再定義するためではなく、操作固有の直和型から内包する具体的なfailureを取り出すために使用する。

UseCase failureを包んだconstructorでは、Feature側で定義済みのUseCase failureの`ToErrorType` instanceをそのまま利用する。このため、同じUseCase failureがUseCase実行`span`とroot `span`の両方を失敗させる場合、それぞれの境界から同じ具体的なfailureに対応する同じ`ErrorType`を得られる。

## 6. 現在固定していない詳細

次はまだこの設計で固定しない。

- 同期Exceptionをどの境界で捕捉し、どの条件で通常のtyped failureへ変換するか。
- 非同期Exceptionのcleanupと再throwをどの境界で行うか。
- logging基盤自身のfailureを`OperationResult`へどう反映するか。
- `OperationFailure`とlogging failureが同時に発生した場合の最終結果と保持する失敗情報。

これらを決める際も、利用者操作の通常failureを表す操作固有failure型と、観測基盤自身のfailureを理由なく同じ型へ混在させない。
