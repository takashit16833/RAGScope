# 利用者操作詳細設計

> [!abstract] この文書の役割
> [利用者操作基本設計](./利用者操作基本設計.md)で定義する`OperationResult`をRAGScopeアプリケーションのHaskell実装でどう表現し、UseCase前・UseCase・UseCase後で生じた通常のtyped failureを利用者操作全体の`OperationFailure`としてどう返すかを定義する。
>
> 利用者操作の実行境界と`OperationSuccess`・`OperationFailure`の意味は[利用者操作基本設計](./利用者操作基本設計.md)、UseCase境界とUseCase固有failureは[ユースケース詳細設計](./ユースケース詳細設計.md)、具体的なfailure値に`toErrorType`を適用して`ErrorType`を得る規則は[ErrorType変換詳細設計](./ErrorType変換詳細設計.md)を正本とする。正確なHaskell型・constructor・関数・moduleは実装コードを機械可読な正本とする。

## 1. `OperationResult`のHaskell表現

1回の利用者操作全体のHaskell境界では、概念上の`OperationResult`を次の形で表す。

```haskell
Either OperationFailure result
```

- `Right result`を`OperationSuccess`として扱う。
- `Left operationFailure`を`OperationFailure`として扱う。
- `OperationSuccess`・`OperationFailure`という結果区分を表すためだけの共通`OperationResult` ADTは導入しない。

UseCase境界の`Either useCaseFailure result`と利用者操作境界の`Either OperationFailure result`は、どちらもHaskellの`Either`を使うが表す処理範囲が異なる。UseCase境界はUseCase自身の結果だけを表し、利用者操作境界はUseCase前後を含む操作固有処理全体の結果を表す。

```text
UseCase境界
Either useCaseFailure result

利用者操作境界
Either OperationFailure result
```

## 2. `OperationFailure`の構造

すべてのトップレベルな利用者操作は、同じ`OperationFailure`型を使用する。`OperationFailure`は、`ToErrorType` instanceを持つ具体的なfailure値を1つ保持する。

概念的なHaskell表現は次のとおりである。

```haskell
data OperationFailure where
  OperationFailure
    :: ToErrorType failure
    => failure
    -> OperationFailure
```

`OperationFailure failure`を構築した後も、`failure`値そのものは保持される。ただし`OperationFailure`を受け取る側は、その値を`DenseSearchFailure`や`InputFailure`などの具体型としてpattern matchしない。`OperationFailure`が保証するのは、保持している`failure`値に`toErrorType`を適用できることである。

`OperationFailure`には、失敗した処理段階を表すためだけのconstructorを追加しない。たとえば次のような構造にはしない。

```haskell
data OperationFailure
  = InputFailure ...
  | UseCaseFailure ...
  | OutputFailure ...
```

また、利用者操作ごとに次のような型も定義しない。

```haskell
data DenseSearchOperationFailure
  = DenseSearchInputFailure InputFailure
  | DenseSearchUseCaseFailure DenseSearchFailure
  | DenseSearchOutputFailure OutputFailure
```

入力処理、UseCase、結果処理のどこで失敗したかは、その処理を実行して`failure`値を受け取った場所では既知である。その場所では、具体的なfailure型を必要とするOperation固有の処理を必要に応じて行える。観測用表現やログ表現への変換は、その表現を必要とする側が、failure型の所有側が提供する変換規則を使って行う。利用者操作を失敗として終了する場合は`OperationFailure failure`を構築し、Operation境界の外側へ処理段階を表す別のconstructorを持ち出さない。

## 3. 具体的なfailureの受け渡し

UseCaseが`Left useCaseFailure`を返した場合、利用者操作側はその`useCaseFailure`値を受け取る。利用者操作も失敗として終了する場合は次の値を返す。

```haskell
Left (OperationFailure useCaseFailure)
```

`useCaseFailure`を先に`ErrorType`へ変換してから`OperationFailure`へ入れない。`OperationFailure`は具体的な`useCaseFailure`値を保持し、その型の`ToErrorType` instanceも一緒に利用できる状態にする。`ErrorType`や構造化ログなど別の表現が必要な処理は、必要になった場所で対応する変換規則を利用する。

UseCase前の入力変換・検証などで`inputFailure`を受け取った場合も、利用者操作を失敗として終了するなら次の値を返す。

```haskell
Left (OperationFailure inputFailure)
```

UseCase後の結果処理で`outputFailure`を受け取った場合も同じである。

```haskell
Left (OperationFailure outputFailure)
```

UseCase外のfailureをUseCase固有failureへ変換しない。それぞれの処理は、自身が受け取った具体的なfailure値をその場所で扱い、利用者操作の最終結果として失敗を返すときだけ`OperationFailure`で包む。

## 4. 所有者と依存

`OperationFailure`はすべてのトップレベルな利用者操作で使用するApplication側の共通型とし、`ragscope` packageの`ragscope-application` libraryが所有する。Featureや共通`ragscope-error` packageには置かない。正確なmodule名はApplication実装時にコードで確定する。

`OperationFailure`を定義するlibraryは、constructorの`ToErrorType failure`制約と`ToErrorType OperationFailure` instanceを定義するため、`RAGScope.ErrorType`をimportし、`ragscope-error`へ依存する。

`OperationFailure`の定義は`DenseSearchFailure`など個別のUseCase固有failure型を参照しない。そのため、新しいUseCase固有failure型を追加しても、そのfailure型に`ToErrorType` instanceがあれば`OperationFailure failure`として保持でき、`OperationFailure`の型定義を変更しない。

個々の利用者操作を実装するmoduleは、呼び出すUseCaseの結果型や、その操作の入力・結果処理に必要な型を参照できる。Feature側から`OperationFailure`へ依存させない。

## 5. `ToErrorType OperationFailure`

`OperationFailure`自身にも`ToErrorType` instanceを定義する。instanceは`OperationFailure`から中の`failure`値を取り出し、その値に`toErrorType`を適用して結果を返す。

```haskell
instance ToErrorType OperationFailure where
  toErrorType (OperationFailure failure) =
    toErrorType failure
```

たとえばUseCaseが返した`useCaseFailure`によってUseCase実行`span`とroot `span`の両方が失敗する場合、UseCase実行`span`で`ErrorType`を必要とする処理は`toErrorType useCaseFailure`を適用する。root `span`で`ErrorType`を必要とする処理は`OperationFailure useCaseFailure`を受け取り、`toErrorType operationFailure`を適用する。`ToErrorType OperationFailure`の実装が中の同じ`useCaseFailure`値に`toErrorType`を適用するため、両方で同じ`ErrorType`を得る。

## 6. logging failureと`OperationResult`

logging基盤自身のfailureは、利用者が依頼した結果を成立させられたかを表す`OperationResult`へ含めない。利用者操作本体が成功していれば、同じ操作中のログ記録が失敗しても`OperationSuccess`を維持する。利用者操作本体が失敗していれば、ログ記録の成否にかかわらず、その操作本体のfailureを保持した`OperationFailure`を返す。

| 利用者操作本体 | logging | `OperationResult` |
|---|---|---|
| 成功 | 成功 | `OperationSuccess` |
| 失敗 | 成功 | `OperationFailure` |
| 成功 | 失敗 | `OperationSuccess` |
| 失敗 | 失敗 | `OperationFailure` |

logging failureを`OperationFailure`の中へ保持せず、logging failureだけを理由に`Left OperationFailure`へ変更しない。利用者操作本体とloggingの両方が失敗した場合も、利用者操作境界の`Either OperationFailure result`は操作本体のfailureだけを表す。logging failureはLogging側の独立したfailure境界で通知・保持する。

`RAGScope.Logging`の公開`record`はlogging failureをtyped resultとしてOperation / Featureへ返さず、`record :: Logger m event -> event -> m ()`の形を維持する。Logging RuntimeまたはSinkで発生したfailureをどの内部境界へ通知・保持するかはLogging側の設計で定め、失敗した同じlogging経路へ再帰的に記録しない。

同期Exceptionや非同期Exceptionがlogging処理中に発生した場合の捕捉・変換・再throwは、この節のlogging failureと同一視せず、Exception境界の設計に従う。

## 7. 現在固定していない詳細

次はまだこの設計で固定しない。

- 同期Exceptionをどの境界で捕捉し、どの条件で通常のtyped failureへ変換するか。
- 非同期Exceptionのcleanupと再throwをどの境界で行うか。
- logging基盤自身のfailureをどのLogging内部境界へ通知・保持するか。

この節で扱う通常のtyped failureについては、`ToErrorType` instanceを持つ具体的なfailure値を`OperationFailure`で保持する。logging failureは`OperationFailure`へ入れず、Exceptionは上記の未決定事項を決めるまで通常のtyped failureと同じ扱いを前提にしない。
