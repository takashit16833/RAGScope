# 利用者操作詳細設計

> [!abstract] この文書の役割
> [利用者操作基本設計](./利用者操作基本設計.md)で定義する`OperationResult`をRAGScopeアプリケーションのHaskell実装でどう表現し、UseCase前・UseCase・UseCase後で生じた通常のtyped failureを利用者操作全体の`OperationFailure`としてどう返すかを定義する。
>
> 利用者操作の実行境界と`OperationSuccess`・`OperationFailure`の意味は[利用者操作基本設計](./利用者操作基本設計.md)、UseCase境界とUseCase固有failureは[ユースケース詳細設計](./ユースケース詳細設計.md)、具体的なfailure値を`ErrorClassifier`で`ErrorType`へ分類する規則は[ErrorType変換詳細設計](./ErrorType変換詳細設計.md)を正本とする。正確なHaskell型・constructor・関数・moduleは実装コードを機械可読な正本とする。

## 1. `OperationResult`のHaskell表現

1回の利用者操作全体のHaskell境界では、概念上の`OperationResult`を次の形で表す。

```haskell
Either OperationFailure result
```

- `Right result`を`OperationSuccess`として扱う。
- `Left operationFailure`を`OperationFailure`として扱う。
- `OperationSuccess`・`OperationFailure`という結果区分を表すためだけの共通`OperationResult` ADTは導入しない。

UseCase境界の`Either useCaseFailure result`と利用者操作境界の`Either OperationFailure result`は、どちらもHaskellの`Either`を使うが表す処理範囲が異なる。UseCase境界はUseCase自身の結果だけを表し、利用者操作境界はUseCase前後を含む操作固有処理全体の結果を表す。

```text
UseCase境界
Either useCaseFailure result

利用者操作境界
Either OperationFailure result
```

## 2. `OperationFailure`の構造

すべてのトップレベルな利用者操作は、同じ`OperationFailure`型を使用する。`OperationFailure`は、具体的なfailure値と、そのfailure型を`ErrorType`へ分類する`ErrorClassifier failure`を1組保持する。

概念的なHaskell表現は次のとおりである。

```haskell
data OperationFailure where
  OperationFailure
    :: failure
    -> ErrorClassifier failure
    -> OperationFailure
```

`OperationFailure failure classifier`を構築した後も、`failure`値そのものは保持される。failureがconstructor引数として数値・文字列などの詳細値を保持する場合も、その詳細値を含むfailure値全体を保持する。`ErrorType`へ先に変換してから`OperationFailure`へ入れる構造にはしない。

`OperationFailure`を受け取る側は、その値を`DenseSearchFailure`や`InputFailure`などの具体型としてpattern matchしない。`OperationFailure`が保証するのは、中の具体failure値を失わず、その値に対応するClassifierを使って`ErrorType`を得られることである。

`OperationFailure`には、失敗した処理段階を表すためだけのconstructorを追加しない。たとえば次のような構造にはしない。

```haskell
data OperationFailure
  = InputFailure ...
  | UseCaseFailure ...
  | OutputFailure ...
```

また、利用者操作ごとに次のような型も定義しない。

```haskell
data DenseSearchOperationFailure
  = DenseSearchInputFailure InputFailure
  | DenseSearchUseCaseFailure DenseSearchFailure
  | DenseSearchOutputFailure OutputFailure
```

入力処理、UseCase、結果処理のどこで失敗したかは、その処理を実行して`failure`値を具体型として受け取った場所では既知である。その場所では、具体failureのconstructor引数を構造化ログeventなどへ反映する処理を含め、具体型を必要とするOperation固有処理を行える。利用者操作を失敗として終了する場合は、同じfailure値と対応Classifierを`OperationFailure`へ入れ、Operation境界の外側へ処理段階を表す別constructorを持ち出さない。

## 3. 具体的なfailureの受け渡し

UseCaseが`Left useCaseFailure`を返した場合、利用者操作側はその`useCaseFailure`値を具体型のまま受け取る。利用者操作も失敗として終了する場合は、UseCase所有側が提供する対応Classifierとともに次の値を返す。

```haskell
Left
  (OperationFailure
    useCaseFailure
    useCaseErrorClassifier)
```

`useCaseFailure`を先に`ErrorType`へ分類してから`OperationFailure`へ入れない。`OperationFailure`は具体的な`useCaseFailure`値と対応Classifierを保持する。failureが保持する詳細値をログ属性などに使う必要がある場合は、その具体failureを扱える場所でeventへ反映できる。Classifierは`error_type`の分類だけを担当し、failureの詳細値を代替しない。

UseCase前の入力変換・検証などで`inputFailure`を受け取った場合も、利用者操作を失敗として終了するなら、そのfailure所有側のClassifierとともに包む。

```haskell
Left
  (OperationFailure
    inputFailure
    inputErrorClassifier)
```

UseCase後の結果処理で`outputFailure`を受け取った場合も同じである。

```haskell
Left
  (OperationFailure
    outputFailure
    outputErrorClassifier)
```

UseCase外のfailureをUseCase固有failureへ変換しない。それぞれの処理は、自身が受け取った具体的なfailure値をその場所で扱い、利用者操作の最終結果として失敗を返すときだけ、対応Classifierとともに`OperationFailure`で包む。

## 4. 所有者と依存

`OperationFailure`はすべてのトップレベルな利用者操作で使用するApplication側の共通型とし、`ragscope` packageの`ragscope-application` libraryが所有する。UseCase側や共通`ragscope-error` packageには置かない。正確なmodule名はApplication実装時にコードで確定する。

`OperationFailure`を定義するlibraryは`ErrorClassifier`をconstructorで保持し、`operationFailureErrorClassifier`を定義するため、`RAGScope.ErrorType`をimportし、`ragscope-error`へ直接依存する。

`OperationFailure`の定義は`DenseSearchFailure`など個別のUseCase固有failure型を参照しない。そのため、新しいfailure型を追加しても、そのfailure型に対応する名前付き`ErrorClassifier failure`があれば同じ`OperationFailure`へ保持でき、`OperationFailure`の型定義を変更しない。

個々の利用者操作を実装するmoduleは、呼び出すUseCaseの結果型や、その操作の入力・結果処理に必要な型を参照できる。`OperationFailure`を構築する場所では、その具体failureの所有側が提供する名前付きClassifierも参照する。UseCase failureの場合は`RAGScope.<UseCase>.ErrorClassification`のClassifierを使用する。UseCase側から`OperationFailure`へ依存させない。

各Operationは、そのOperationが実行時に必要とする能力だけを、そのOperationが所有する依存recordへまとめて受け取る。Application全体の環境をOperationへ渡して必要な能力を取り出させる構造にはしない。

たとえば、ある検索Operationがroot `span`の観測、利用インターフェース固有eventの記録、検索UseCaseの実行を必要とする場合、概念上は次のような依存recordを持つ。

```haskell
data SearchOperationDependencies m =
  SearchOperationDependencies
    { observability
        :: Observability m OperationFailure
    , logger
        :: Logger m SearchInterfaceEvent
    , runSearch
        :: SearchInput
        -> m (Either SearchFailure SearchResult)
    }
```

これは具体的なOperation名を固定するための型定義ではなく、Operation依存recordが保持する責務を示す概念例である。正確な型名、field名、module名は各Operationの実装で確定する。

UseCaseを呼び出すOperationへは、UseCase所有の依存recordそのものを渡さない。Application composition rootが先にUseCase依存recordを構築し、その値をUseCase実行関数へ適用して、Operationから見たUseCase実行能力へ閉じる。

```haskell
runSearchForOperation =
  runSearch searchDependencies
```

Operation依存recordには、このように依存を閉じたUseCase実行関数を格納する。これによりOperationは、UseCase内部が必要とするObservability、Logger、データアクセスなどの依存構造を知らず、UseCaseへ入力を渡して結果を受け取る能力だけを利用する。

Operation依存recordへ入れるのは、Operationの実行時構成によって差し替える意味がある能力とする。`Observability m OperationFailure`、`Logger m event`、UseCase実行関数などは、本番compositionとOperation単体テストで異なる値を渡せるためrecordから受け取る。

一方、failureから`ErrorType`への分類規則はruntime依存recordへ入れない。各failure型に対する名前付き`ErrorClassifier failure`は、そのfailure所有側が定義する採用済みの純粋な分類規則であり、Operationごと・実行ごとに差し替える能力ではない。`OperationFailure`を構築するOperation moduleは、必要なClassifierを`RAGScope.<UseCase>.ErrorClassification`などの所有moduleから静的にimportして利用する。

Classifierを依存recordから任意に差し替えられる構造にすると、同じfailure型についてUseCase `span`、root `span`、構造化ログが別々の分類規則を使える余地が生じる。現在設計では同じfailure型について所有側の同じ名前付きClassifierを共有するため、Classifierをruntime依存として注入しない。

現在のRAGScopeではApplication全体の長寿命環境を表す`AppEnv`は導入しない。将来、実際のApplication実行構造から長寿命依存をまとめる必要が生じた場合でも、その値自体をOperationやUseCaseへ渡すことを前提にせず、composition側で各Operation・UseCaseが必要とする依存recordへ必要な能力だけを取り出して渡す。

## 5. `operationFailureErrorClassifier`

root `span`などで`OperationFailure`から`ErrorType`を得るため、Application側は`ErrorClassifier OperationFailure`を提供する。

```haskell
operationFailureErrorClassifier
  :: ErrorClassifier OperationFailure

operationFailureErrorClassifier =
  ErrorClassifier $ \(OperationFailure failure classifier) ->
    classifyError classifier failure
```

このClassifierは`OperationFailure`から中の具体failure値と対応Classifierを取り出し、その同じfailure値へClassifierを適用する。

たとえばUseCaseが返した`useCaseFailure`によってUseCase実行`span`とroot `span`の両方が失敗する場合、UseCase実行`span`用Observabilityは`useCaseErrorClassifier`で`useCaseFailure`を分類する。root `span`用Observabilityは`operationFailureErrorClassifier`で`OperationFailure useCaseFailure useCaseErrorClassifier`を分類する。後者も保存された同じClassifierを同じfailure値へ適用するため、両方で同じ`ErrorType`を得る。

`operationFailureErrorClassifier`は具体failure型を列挙せず、`OperationFailure`に保存されたClassifierへ処理を委譲する。

## 6. logging failureと`OperationResult`

logging基盤自身のfailureは、利用者が依頼した結果を成立させられたかを表す`OperationResult`へ含めない。利用者操作本体が成功していれば、同じ操作中のログ記録が失敗しても`OperationSuccess`を維持する。利用者操作本体が失敗していれば、ログ記録の成否にかかわらず、その操作本体のfailureを保持した`OperationFailure`を返す。

| 利用者操作本体 | logging | `OperationResult` |
|---|---|---|
| 成功 | 成功 | `OperationSuccess` |
| 失敗 | 成功 | `OperationFailure` |
| 成功 | 失敗 | `OperationSuccess` |
| 失敗 | 失敗 | `OperationFailure` |

logging failureを`OperationFailure`の中へ保持せず、logging failureだけを理由に`Left OperationFailure`へ変更しない。利用者操作本体とloggingの両方が失敗した場合も、利用者操作境界の`Either OperationFailure result`は操作本体のfailureだけを表す。logging failureはLogging側の独立したfailure境界で通知・保持する。

`RAGScope.Logging`の公開`record`はlogging failureをtyped resultとしてOperation / UseCaseへ返さず、`record :: Logger m event -> event -> m ()`の形を維持する。Logging RuntimeまたはSinkで発生したfailureをどの内部境界へ通知・保持するかはLogging側の設計で定め、失敗した同じlogging経路へ再帰的に記録しない。

同期Exceptionや非同期Exceptionがlogging処理中に発生した場合の捕捉・変換・再throwは、この節のlogging failureと同一視せず、Exception境界の設計に従う。

## 7. 現在固定していない詳細

次はまだこの設計で固定しない。

- `OperationFailure`を置く正確なmodule名。型の保持構造と`operationFailureErrorClassifier`の責務は固定する。
- 同期Exceptionをどの境界で捕捉し、どの条件で通常のtyped failureへ変換するか。
- 非同期Exceptionのcleanupと再throwをどの境界で行うか。
- logging基盤自身のfailureをどのLogging内部境界へ通知・保持するか。

この節で扱う通常のtyped failureについては、具体的なfailure値と対応`ErrorClassifier failure`を`OperationFailure`で保持する。logging failureは`OperationFailure`へ入れず、Exceptionは上記の未決定事項を決めるまで通常のtyped failureと同じ扱いを前提にしない。
