# 共通エラー契約設計

> [!abstract] この文書の役割
> RAGScopeアプリケーション、AI推論サービス、CLI、HTTP APIの各境界で共有するエラーの意味を定義する。内部例外、HTTPレスポンス、CLI表示、構造化ログの表現方法はこの契約から分離する。

## 1. 共通エラーが表すもの

共通エラーは、処理が成立しなかった理由を、利用境界や実装言語に依存せず機械的に識別するための失敗情報である。

| 概念 | 必須 | 意味 |
|---|---|---|
| エラー種別 | 必須 | 同じ失敗理由を同じ意味で識別する安定した識別子。HTTPステータス、例外クラス名、ログ重要度を兼用しない。 |
| 公開メッセージ | 必須 | その発生について利用者または呼び出し側へ示してよい説明。機械判定には使用しない。 |
| 公開詳細 | 任意 | 呼び出し側が対処または表示に利用できる構造化された追加情報。項目の意味はエラー種別ごとに定義する。 |

エラー種別は失敗の意味を表す。通信方式や表示先が変わっても同じ失敗理由へ別の意味を割り当てない。

公開メッセージと公開詳細には、CLIまたはHTTP APIへ返してよい情報だけを含める。例外のスタックトレース、ライブラリ固有の例外値、SQL、認証情報など、内部診断だけに必要な情報は共通エラーへ含めない。

## 2. 実装境界との関係

各コンポーネントは、自身が利用するライブラリ、OS、モデル、データベースなどの失敗を、そのコンポーネントの境界で共通エラーへ変換する。

共通エラーは次の情報を所有しない。

- HTTPステータスコード
- CLIの終了コードや表示書式
- ログ重要度
- 再試行回数、待機時間、再試行可否などの実行制御
- 例外クラス名やスタックトレース

これらは、共通エラーを利用する境界または実行制御が、それぞれの責務で決定する。

> [!important] エラーと失敗した処理を分ける
> 共通エラーは「なぜ失敗したか」を表す。どの処理が失敗したか、RAGScopeが管理するどの対象に関係するかは、[実行追跡・構造化ログ契約設計](./実行追跡・構造化ログ契約設計.md)の処理関係とドメイン参照で記録する。

## 3. 利用境界への投影

| 利用境界 | 共通エラーから利用する情報 | 境界が追加して決める情報 |
|---|---|---|
| CLI | エラー種別、公開メッセージ、必要な公開詳細 | 終了コード、表示形式、表示先 |
| HTTP API | エラー種別、公開メッセージ、必要な公開詳細 | HTTPステータス、Problem Detailsの`type`・`title`・`instance`、必要な拡張項目 |
| 構造化ログ | エラー種別、公開メッセージ、必要な公開詳細 | ログ重要度、イベント、発生元、処理関係、ログ専用の診断情報 |

HTTP APIのエラー表現にはRFC 9457 Problem Detailsを使用する。API境界は、エラー種別をproblem typeへ対応付け、HTTPステータスをそのAPIの意味に基づいて決定する。`detail`へは公開メッセージを使用できるが、呼び出し側が機械判定する情報はproblem typeまたは拡張項目として表現する。内部実装のデバッグ情報をProblem Detailsへ出力しない。

共通エラーとHTTP Problem Detailsは同じ責務ではない。共通エラーはRAGScope内部で共有する失敗の意味を定義し、Problem Detailsはその失敗をHTTP境界で表現する。

## 4. 変更時に維持する規則

- エラー種別の既存値へ別の意味を割り当てない。
- 表示文言だけを根拠にエラー種別を判定しない。
- 外部ライブラリの例外名やHTTPステータスを、そのまま共通エラー種別の意味として扱わない。
- 公開してよい情報と内部診断情報を同じ項目へ混在させない。
- 新しい利用境界を追加しても、共通エラーへその境界固有の表現項目を追加しない。

正確なエラー種別の一覧、各境界での項目名・型・必須条件は、対応する機能設計と機械可読な契約を正本とする。
