# 構造化ログ基本設計

> [!abstract] この文書の役割
> RAGScopeの各コンポーネントが、処理中の出来事を**同じJSON契約で記録**し、1回の実行に属するログイベントを追跡するための、実装技術に依存しない共通設計を定義する。
>
> 具体的な`operation`、`event`、観測点、イベント固有情報は各機能設計を正本とし、正確なJSON項目、型、必須条件は[`log-event.schema.json`](../../contracts/logging/v1/log-event.schema.json)を正本とする。RAGScopeアプリケーションのHaskell実装構造は[構造化ログ詳細設計](./構造化ログ詳細設計.md)で定義する。

## 1. ログイベントの基本構造

RAGScopeの構造化ログは、1つの出来事を1つのJSONオブジェクト（`LogEvent`）として記録する。[ADR-0003](<../adr/ADR-0003 構造化ログのJSON構造をログモデルの型構造と整合させる.md>)に従い、イベントの意味を表す情報は`spec`としてまとめ、内部のログモデルとJSON契約で同じ意味上の構造を保つ。

```text
LogEvent
├── 共通項目（Envelope）
├── context
└── spec
    ├── operation
    ├── event
    ├── level
    ├── payload
    └── error（失敗時のみ）
```

| 領域 | キー | 意味 |
|---|---|---|
| Envelope | `schema_version` | ログ契約のバージョン |
| | `event_id` | ログイベント1件の識別子 |
| | `timestamp` | 記録したUTC時刻 |
| | `component` | 生成元のコンポーネント |
| Context | `context` | 実行またはサービスとの関連情報 |
| EventSpec | `spec.operation` | 追跡する意味のある処理種別 |
| | `spec.event` | `operation`について起きた出来事 |
| | `spec.level` | 処理への影響の大きさ |
| | `spec.payload` | イベント固有の安全な情報 |
| | `spec.error` | 処理失敗時の安全なエラー情報 |

`operation`と`event`の組で、「何の処理について何が起きたか」を表す。具体的な組と意味は各機能設計で定義する。

## 2. 共通の不変条件

### 2.1 失敗イベント

- `spec.event = failed`の場合は必ず`spec.error`を含め、`spec.level = error`とする。
- それ以外のイベントには`spec.error`を含めない。
- 通常の機能処理から、この相関を任意に崩せる形でログイベントを組み立てさせない。

`spec.error`へ渡せる情報は[エラー設計](./エラー設計.md)に従い、`cause`、元の例外メッセージ、スタックトレースを含めない。

### 2.2 任意項目と`null`

- 通常イベントでは`spec.error`を`null`にせず、キー自体を省略する。
- エラー固有の安全な補助情報がない場合は、`spec.error.context`を`null`にせず、キー自体を省略する。
- `spec.payload`とエラーの`context`へ格納する値には`null`を使用しない。情報が不要な場合は項目自体を省略する。

任意項目の正確な必須条件と許可される値はJSON Schemaを正本とする。

### 2.3 実行との関連付け

| `context` | 意味 |
|---|---|
| `scope = execution` | 1回のCLIコマンドに属するログイベント |
| `scope = service` | サービスの起動・終了などの状態変化 |

`execution_id`は1回のCLIコマンドを識別する。最も外側の境界で最初のログイベントより前に1回生成し、同じコマンドではコンポーネント境界を越えて引き継ぐ。別のCLIコマンドには別の`execution_id`を使用する。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、v1の共通アプリケーションログイベントへ含めない。

### 2.4 情報保護

記録してよい情報を各機能設計で先に定義する許可リスト方式とし、後から正規表現で伏せ字にする方法だけへ依存しない。

| 対象 | そのまま記録しないもの | 代わりに使用する情報 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

`debug`を有効にしても情報保護の規則は変えない。安全性を確認できない値は、伏せ字にするより項目自体を省略する。

## 3. 出力と失敗時の扱い

### 3.1 ローカル出力

| 出力 | 規則 |
|---|---|
| 正常なCLI結果 | 標準出力へ出力する |
| 構造化ログ | 標準エラー出力へ出力する |
| 出力単位 | 1ログイベントを1行のJSONとして出力する |

標準エラー出力へ、JSON以外の接頭辞、色制御文字、説明文、通常テキスト形式のエラーを混ぜない。

### 3.2 ログ基盤自身が失敗した場合

- ログ基盤自身の失敗は、元の機能処理の失敗と区別できる形で呼び出し側へ返す。
- 失敗した同じログ経路へ新しいログイベントを書き戻さない。
- 元の処理が成功し、必須ログイベントの出力に失敗した場合は、外側のアプリケーション実行を失敗とする。
- 元の処理とログ基盤の両方が失敗した場合、元の処理のエラーをログ基盤の失敗で上書きしない。
- v0.0では、壊れたJSONやプレーンテキストによる代替出力を行わない。

RAGScopeアプリケーションでは、完成した`LogEvent`からJSONへの変換をtotalな純粋変換とし、通常の入力値に対する回復可能なJSON変換失敗経路を設けない。契約不適合は型、JSON変換テスト、Schema適合テストで検出し、JSON生成後の標準エラー出力などで発生するIO失敗だけをSinkの失敗として扱う。具体的な実装境界は[構造化ログ詳細設計](./構造化ログ詳細設計.md)を正本とする。

## 4. 責務分担

| 定義・実装する場所 | 担当する内容 |
|---|---|
| 本設計 | `LogEvent`の意味、実行との関連付け、不変条件、出力・情報保護・失敗時の共通規則 |
| JSON Schema | 正確なJSON項目、型、必須条件、共通列挙値、形式 |
| 各機能設計 | 具体的な`operation`、`event`、観測点、`payload`、通常時の`level`、機能固有の記録禁止情報 |
| 各コンポーネントの詳細設計・コード | 共通契約を成立させる型、logger、JSON変換、Sinkと実行時の流れ |
