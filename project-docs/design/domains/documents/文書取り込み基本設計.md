# 文書取り込み基本設計

> [!abstract] この文書の役割
> MarkdownまたはTXTの技術文書を取り込み、文書集合・文書・文書バージョンの関係を保ったまま、正規化済み本文を持つ追跡可能な版として保存する機能の責務と境界を定義する。
> 具体的な処理順序、検証、失敗時の扱い、不変条件は[文書取り込み詳細設計](./文書取り込み詳細設計.md)で定義する。

## 1. 目的と適用範囲

文書取り込みは、外部の技術文書をRAGScope内の文書バージョンとして保存し、後続処理が同じ正規化済み本文を参照できる状態を作る。

| 扱うこと | 扱わないこと |
|---|---|
| Markdown / TXT文書を取り込み、形式を検証する | PDF、OCR、画像、複雑なレイアウトを解析する |
| 文書集合、文書、文書バージョンの関係を保って保存する | 文書を文書チャンクへ分割する |
| 同じ文書の内容が変わった場合に、新しい文書バージョンとして区別する | 過去の文書バージョンを上書きする |
| 後続処理が位置を参照するときの基準となる正規化済み本文を確定する | 検索用データを生成する、検索する、回答を生成する |

この機能は`REQ-DOC-001`と`REQ-DOC-004`を実現し、`REQ-DOC-003`と`REQ-NF-TRACE-002`に必要な追跡の起点を作る。

## 2. 責務と境界

文書取り込みは、対象の技術文書から内容を取得し、UTF-8の文字列へ変換して採用済みの正規化規則を適用し、文書集合・文書・文書バージョンの関係を保って保存するところまでを担当する。

文書チャンク化、検索用データ生成、検索、回答生成は担当しない。

```mermaid
flowchart LR
    Source["Markdown / TXT文書"]
    Ingest["文書取り込み"]
    Version["保存済みの文書バージョン<br>正規化済み本文"]
    Chunk["文書チャンク化"]

    Source --> Ingest --> Version --> Chunk
```

## 3. 概念上の入出力

| 区分 | 内容 |
|---|---|
| 入力 | 取り込むMarkdown / TXTの技術文書と、その文書を文書集合・文書として識別するために必要な情報 |
| 前提 | 対象の技術文書を取得でき、文書集合・文書として扱うために必要な情報がそろっている |
| 成功結果 | 文書集合と文書に関連付けて保存した文書バージョン |
| 失敗結果 | 文書取り込みを完了できないことを表す処理失敗 |
| 後続処理への入力 | 保存済みの文書バージョン |

ファイルパス、バイト列、文字列、読み取り処理などのどの形で入力を渡すかは、この基本設計では決めない。CLI / APIなど利用インターフェース固有の入力形式も、対応するユースケース、インターフェース契約、実装の正本で具体化する。

## 4. 主要な設計

### 4.1 文書と版を区別する

文書は、同じ技術文書の複数の版を継続して関連付ける単位として扱う。内容が変わった場合は過去の文書バージョンを書き換えず、新しい文書バージョンとして区別する。

文書集合の中で文書を一意に識別する具体的な識別子と一意性制約は、この基本設計では決めない。

### 4.2 正規化済み本文を共通の参照基準にする

各文書バージョンは1つの正規化済み本文を保持する。文書チャンクと正解根拠は、この正規化済み本文を共通の位置参照の基準として使用する。

採用する具体的な正規化規則は未決定である。決定状態と具体的な処理規則は[文書取り込み詳細設計](./文書取り込み詳細設計.md)で扱う。

## 5. 文書チャンク化への受け渡し

文書チャンク化へは、保存済みの文書バージョンを渡す。文書チャンク化は、その文書バージョンが保持する正規化済み本文を使用し、元の入力から本文を作り直さない。

文書バージョンをどの型や識別子として渡すかは、この基本設計では固定しない。正確な型と識別子は、実装時のコード、migration、テストを正本とする。

## 6. 詳細設計と機械可読な正本

具体的な処理順序、文書バージョンの再利用、正規化済み本文の検証、保存単位、失敗時の扱い、Observability、不変条件は[文書取り込み詳細設計](./文書取り込み詳細設計.md)を正本とする。

正確な型、識別子、一意性制約、トランザクション境界、利用インターフェースの入力形式は、コード、migration、OpenAPIなど実装時に追加する機械可読な正本で定義する。
