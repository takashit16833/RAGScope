# 検索対象設計

> [!abstract] この文書の役割
> 検索開始時に使用する具体的な文書バージョン集合を確定し、検索方式に必要な検索用データが準備済みであることを確認する契約を定義する。

## 1. 検索対象の指定

検索は、質問だけでなく、どの文書と検索条件を使うかを明示して実行する。

文書の指定は次の2方式を持つ。

| 指定 | 用途 |
|---|---|
| 文書集合に属する文書の現在の文書バージョン | 通常の検索。文書集合を指定し、検索開始時点の各文書の現在の文書バージョンを使う |
| 固定文書バージョン集合 | 実験・再現。使用する文書バージョンを明示する |

文書集合に属する文書の現在の文書バージョンを使用する場合、RAGScopeアプリケーションは検索開始時に文書集合の所属文書と各文書の現在の文書バージョンを読み取り、そのInvocationで使用する文書バージョン集合として固定する。検索中に現在の文書バージョンが更新されても、そのInvocationの対象は変更しない。

固定文書バージョン集合を使用する場合は、指定された文書バージョンをそのまま使用し、現在の文書バージョンへ置き換えない。

## 2. 検索方式と必要な検索用データ準備単位

検索方式ごとに、次の検索用データを要求する。

| 検索方式 | 必要な準備済みデータ |
|---|---|
| 全文検索 | 各対象文書バージョンについて、同じ分割条件・PostgreSQL text search configurationの全文検索の検索用データ準備単位が`ready` |
| dense検索 | 各対象文書バージョンについて、同じ分割条件・EmbeddingプロファイルIDのdense検索の検索用データ準備単位が`ready` |
| hybrid検索 | 上記の全文検索とdense検索の両方 |

検索用データ準備単位と`ready`の意味は[検索用データ準備設計「2. 検索用データ準備単位と完了状態」](<../documents/検索用データ準備設計.md#2. 検索用データ準備単位と完了状態>)を正本とする。

検索要求は、検索方式に応じて次を持つ。

- 分割条件。
- 全文検索またはhybrid検索ではPostgreSQL text search configuration。
- dense検索またはhybrid検索ではEmbeddingプロファイルID。
- 正の`topK`。

## 3. 準備完了の確認

検索開始前に、対象となるすべての文書バージョンについて必要な検索用データ準備単位が`ready`であることを確認する。

1つでも`ready`でない場合は検索対象未準備として検索を失敗させる。

次の動作は行わない。

- 現在の文書バージョンが未準備だからという理由で以前の文書バージョンの検索用データへフォールバックする。
- 未準備の文書だけを検索対象から除外して処理を続ける。
- 異なる分割条件、全文検索configuration、Embeddingプロファイルのデータを混ぜる。
- `preparing`または`failed`の検索用データ準備単位に属する個別データを直接検索する。

文書集合が空で、対象文書バージョン集合が0件の場合は、検索対象自体は準備済みとして扱い、検索結果0件を正常結果にできる。

## 4. 現在の文書バージョン更新との関係

文書更新と検索用データ準備は別操作であるため、次の状態を許容する。

```text
文書の現在の文書バージョン = V2
V2の検索用データ = 未準備
V1の検索用データ = ready
```

文書集合に属する文書の現在の文書バージョンを対象に検索した場合、この状態ではV1へフォールバックせず検索対象未準備として失敗する。

V1を明示した固定文書バージョン集合を対象に検索した場合は、V1に必要な検索用データ準備単位が`ready`であれば検索できる。

## 5. dense検索のEmbedding互換性

dense検索では、文書チャンクのEmbeddingと質問Embeddingを同じ[Embedding生成設計](../../Embedding生成設計.md)のプロファイルIDで生成する。

質問Embeddingのresponseで得た`profile_fingerprint`が、検索対象の文書チャンクEmbeddingに保存されたfingerprintと一致しない場合は検索を実行しない。

## 6. 境界

この設計は、検索対象と準備済みデータの利用可否を定義する。

全文検索のquery生成とranking、vector distance、hybrid結果の統合、`reranking`、回答生成用文書チャンク選択は、それぞれを具体化する検索・回答生成側の機能設計で定義する。
