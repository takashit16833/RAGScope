# 構造化ログ設計

> [!abstract] この文書の役割
> RAGScopeで記録する構造化ログについて、共通に扱う情報、通常イベントと失敗イベントで常に成立させる条件、CLI実行またはサービス状態との関連付け、記録してよい情報を定義する。

## 1. `LogEvent`が表す情報と共通構造

構造化ログでは、1つの出来事を1つの`LogEvent`として扱う。`LogEvent`は次の情報を持つ。

```text
LogEvent
├── 契約バージョン
├── イベント識別子
├── 記録時刻
├── 生成元
├── EventContext
│   ├── CLI実行
│   └── サービス状態
└── EventSpec
    ├── Operation
    ├── Payload
    └── イベント種別
        ├── 通常イベント: EventName + NormalLevel
        └── 失敗イベント: LogError
```

| 情報 | 表す内容 |
|---|---|
| 契約バージョン | 利用する構造化ログ契約のバージョン |
| イベント識別子 | ログイベント1件を識別する値 |
| 記録時刻 | ログイベントを記録した時刻 |
| 生成元 | ログイベントを生成したRAGScopeのコンポーネント |
| EventContext | ログイベントが1回のCLI実行に属するか、サービス自身の状態変化に属するか |
| EventSpec | どの処理で何が起きたかと、その出来事に付随する情報 |
| Operation | ログで追跡する処理種別 |
| EventName | 1つの`Operation`について観測した通常の出来事 |
| NormalLevel | 通常イベントの重要度。`debug`、`info`、`warn`を使用する |
| Payload | イベント固有の安全な補助情報 |
| LogError | 失敗について記録してよい安全なエラー情報 |

`Operation`と`EventName`の組で、どの処理についてどの通常イベントを観測したかを識別する。使用できる組と、そのイベントを記録する処理上の位置は各機能設計で定義する。

## 2. 通常イベントと失敗イベント

`EventSpec`は`Operation`と`Payload`を共通部分として持ち、通常イベントと失敗イベントのどちらかを表す。

| 種類 | 保持する情報 | 常に成立させる条件 |
|---|---|---|
| 通常イベント | `EventName`、`NormalLevel` | `NormalLevel`は`debug` / `info` / `warn`のいずれかとし、`LogError`を持たない |
| 失敗イベント | `LogError` | `LogError`を必須とし、失敗を表す共通イベント名と`error`レベルは失敗イベントであることから決まる |

失敗イベントであることから決まるイベント名と`error`レベルは、呼び出し側が別々に指定する値として扱わない。構造化ログを生成する実装は、通常イベントと失敗イベントの区別と上記の条件を崩さない型・データ構造を使用する。

この区別を採用した理由は[ADR-0004](<../../adr/ADR-0004 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する.md>)に記録する。

## 3. ログイベントをCLI実行・サービス状態へ関連付ける

| 種類 | 関連付ける対象 | `execution_id` |
|---|---|---|
| CLI実行 | 1回のCLIコマンド | 必須 |
| サービス状態 | サービスの起動・終了など、特定のCLIコマンドに属さない状態変化 | 持たない |

CLIコマンドの処理を開始する境界で、最初のログイベントを記録する前に`execution_id`を1回生成する。同じCLIコマンドに属するすべてのログイベントには同じ`execution_id`を使用し、別のCLIコマンドには別の値を使用する。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、v1の構造化ログで定義するイベントの対象に含めない。

## 4. ログへ記録してよい情報

各機能設計で`Payload`と`LogError`へ記録してよい情報を定め、ログイベントにはその情報だけを含める。記録した後に正規表現で伏せ字にする処理だけを、情報保護の手段にはしない。

| 対象 | そのまま記録しないもの | 代わりに使用する情報 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

`debug`を有効にしても記録できる情報は増やさない。安全性を確認できない値は記録しない。

## 5. 定義・実装の分担と正本

| 内容 | 定義・正本 |
|---|---|
| `LogEvent`が表す共通情報、通常・失敗イベントの条件、CLI実行・サービス状態との関連付け、記録してよい情報 | 本設計 |
| 機能固有の`Operation`、通常イベント、記録する処理上の位置、`Payload`、通常時のレベル、機能固有の記録禁止情報 | 各機能設計 |
| RAGScopeアプリケーションでのログ型、ログ受付、実行時処理、出力 | [RAGScopeアプリケーション構造化ログ設計](./RAGScopeアプリケーション構造化ログ設計.md)。正確なHaskellのログ型は[`RAGScope.Logging.Core`](../../../ragscope-app/logging-src/RAGScope/Logging/Core.hs) |
| `LogError`へ記録する情報と、機能処理・必須ログ記録の失敗を扱う規則 | [エラー設計](../エラー設計.md) |
| `LogEvent`をv1のJSONへ表現する規則 | [構造化ログJSON表現設計](./構造化ログJSON表現設計.md) |
| v1 JSONの正確な項目、型、必須条件、通常・失敗イベントの許可形 | [`log-event.schema.json`](../../../contracts/logging/v1/log-event.schema.json) |
