# 構造化ログ設計

> [!abstract] この文書の役割
> RAGScopeの各コンポーネントが、処理中の出来事を同じ意味で記録し、1回の実行に属するログイベントを追跡するための共通設計を定義する。
>
> 本設計は実装技術、コンポーネント固有の内部構造、外部表現の形式から独立させる。具体的な`operation`、通常イベント名、観測点、イベント固有情報は各機能設計を正本とする。

## 1. ログイベントの意味モデル

構造化ログでは、1つの出来事を1つの`LogEvent`として扱う。`LogEvent`は、出来事そのものの意味と、実行をまたいで追跡するための共通情報を分けて保持する。

```text
LogEvent
├── Envelope
│   ├── 契約バージョン
│   ├── イベント識別子
│   ├── 記録時刻
│   └── 生成コンポーネント
├── EventContext
│   ├── Execution
│   └── Service
└── EventSpec
    ├── Operation
    ├── Payload
    └── EventKind
        ├── NormalEvent(EventName, NormalLevel)
        └── FailedEvent(LogError)
```

| 概念 | 意味 |
|---|---|
| Envelope | ログイベント自身を識別し、いつ・どのコンポーネントで記録されたかを表す共通情報 |
| EventContext | ログイベントが属する実行上の文脈 |
| Operation | 追跡する意味のある処理種別 |
| EventName | 1つの`Operation`について観測した通常の出来事 |
| NormalLevel | 通常イベントの重要度。`debug`、`info`、`warn`を使用する |
| Payload | イベント固有の安全な補助情報 |
| LogError | 失敗について記録してよい安全なエラー情報 |

`Operation`と`EventName`の組で、「何の処理について何が起きたか」を表す。具体的な組と意味は各機能設計で定義する。

## 2. 通常イベントと失敗イベント

通常イベントと失敗イベントは、`event`、`level`、`error`に相当する値を独立に組み合わせた状態ではなく、意味の異なる2種類のイベントとして扱う。[ADR-0004](<../../adr/ADR-0004 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する.md>)に従い、各コンポーネントの内部モデルもこの区別を崩さない形で表現する。

| 種類 | 保持する意味 | 導出される意味 |
|---|---|---|
| NormalEvent | 通常イベント名、`debug` / `info` / `warn`のいずれか、Payload | なし |
| FailedEvent | Payload、安全なLogError | 失敗を表す共通イベント名、`error`レベル |

- NormalEventはLogErrorを持たない。
- FailedEventはLogErrorを必須とする。
- FailedEventで固定的に決まるイベント名とログレベルを、独立した入力として重複保持しない。
- 通常の機能処理から、通常・失敗の相関を任意に崩せる形でLogEventを組み立てさせない。
- 外部表現や特定コンポーネントの都合を理由に、この意味上の不変条件を弱めない。

LogErrorへ渡せる情報は[エラー設計](../エラー設計.md)に従い、内部原因、元の例外メッセージ、スタックトレースを含めない。

## 3. 実行との関連付け

EventContextは、ログイベントが1回の実行に属するか、サービス自身の状態変化に属するかを区別する。

| 文脈 | 意味 |
|---|---|
| Execution | 1回のCLIコマンドに属するログイベント |
| Service | サービスの起動・終了などの状態変化 |

Executionには`execution_id`を必須とする。`execution_id`は最も外側の実行境界で最初のログイベントより前に1回生成し、同じCLIコマンドではコンポーネント境界を越えて引き継ぐ。別のCLIコマンドには別の値を使用する。

Serviceは特定のCLIコマンドへ属さないため`execution_id`を持たない。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、v1の共通アプリケーションログイベントへ含めない。

## 4. 情報保護

記録してよい情報を各機能設計で先に定義する許可リスト方式とし、後から正規表現で伏せ字にする方法だけへ依存しない。

| 対象 | そのまま記録しないもの | 代わりに使用する情報 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

`debug`を有効にしても情報保護の規則は変えない。安全性を確認できない値は、伏せ字にするより記録しない。

## 5. ログ記録が失敗した場合

必須ログ記録の結果は、元の機能処理の結果とは独立した事実として扱う。

- ログ基盤自身の失敗は、元の機能処理の失敗と区別して扱う。
- 失敗した同じログ経路へ新しいログイベントを書き戻さない。
- 元の処理が成功しても必須ログ記録に失敗した場合は、外側の実行を成功として扱わない。
- 元の処理と必須ログ記録の両方が失敗した場合は、元の処理の失敗をログ基盤の失敗で上書きしない。

各コンポーネントは、この意味を保ったまま自身の実行モデルへ組み込む。

## 6. 責務分担

| 定義・実装する場所 | 担当する内容 |
|---|---|
| 本設計 | LogEventの意味、通常・失敗イベントの不変条件、実行との関連付け、情報保護、必須ログ記録失敗の共通の意味 |
| 各機能設計 | 具体的なOperation、通常イベント名、観測点、Payload、通常時のレベル、機能固有の記録禁止情報 |
| 各コンポーネントの設計・コード | 共通の意味と不変条件を成立させる内部モデル、ログ受付、実行時の流れ、出力境界 |
| 外部表現の設計・機械可読な契約 | LogEventの意味を外部へ表現する形式と、その形式固有の制約 |

正確な内部型は各コンポーネントのコード、正確な外部形式は対応する機械可読な定義を正本とする。本設計では、それらの具体的な構造を共通の意味モデルへ逆流させない。
