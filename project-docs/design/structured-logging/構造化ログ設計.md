# 構造化ログ設計

> [!abstract] この文書の役割
> RAGScopeアプリケーションとAI推論サービスが記録する`LogEvent`について、両コンポーネントで共通に扱う情報、通常イベントと失敗イベントで常に成立させる条件、CLI実行またはサービス状態との関連付け、記録してよい情報を定義する。
>
> 具体的な`Operation`、通常イベント名、観測点、`Payload`は各機能設計を正本とする。RAGScopeアプリケーションとAI推論サービスがコード内部で使用する正確な型・データ構造は各コンポーネントのコード、v1のJSON表現は[構造化ログJSON表現設計](./構造化ログJSON表現設計.md)とJSON Schemaを正本とする。

## 1. `LogEvent`が表す情報と共通構造

構造化ログでは、1つの出来事を1つの`LogEvent`として扱う。`LogEvent`は、ログイベント自身を識別する共通情報、そのログイベントが属するCLI実行またはサービス状態、記録する出来事を次の構造で表す。

```text
LogEvent
├── イベント共通情報
│   ├── 契約バージョン
│   ├── イベント識別子
│   ├── 記録時刻
│   └── ログイベントを生成したコンポーネント
├── EventContext
│   ├── Execution
│   └── Service
└── EventSpec
    ├── Operation
    ├── Payload
    └── EventKind
        ├── NormalEvent(EventName, NormalLevel)
        └── FailedEvent(LogError)
```

| 概念 | 表す内容 |
|---|---|
| イベント共通情報 | ログイベント自身の識別子、記録時刻、ログイベントを生成したコンポーネントなど、すべてのイベントが持つ情報 |
| EventContext | ログイベントが1回のCLI実行に属するか、サービス自身の状態変化に属するか |
| EventSpec | どの処理で何が起きたかと、その出来事に付随する情報 |
| Operation | ログで追跡する処理種別 |
| EventName | 1つの`Operation`について観測した通常の出来事 |
| NormalLevel | 通常イベントの重要度。`debug`、`info`、`warn`を使用する |
| Payload | イベント固有の安全な補助情報 |
| LogError | 失敗について記録してよい安全なエラー情報 |

`Operation`と`EventName`の組で、どの処理についてどの通常イベントを観測したかを識別する。使用できる組と、そのイベントを記録する処理上の位置は各機能設計で定義する。

## 2. 通常イベントと失敗イベント

`EventSpec`は`Operation`と`Payload`を共通部分として持ち、`EventKind`で通常イベントと失敗イベントを区別する。[ADR-0004](<../../adr/ADR-0004 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する.md>)に従い、RAGScopeアプリケーションとAI推論サービスがコード内部で使用するログイベントの型・データ構造も、この2種類を区別する。

| 種類 | `EventKind`が保持する値 | 常に成立させる条件 |
|---|---|---|
| NormalEvent | `EventName`、`NormalLevel` | `NormalLevel`は`debug` / `info` / `warn`のいずれかとし、`LogError`を持たない |
| FailedEvent | `LogError` | `LogError`を必須とし、失敗を表す共通イベント名と`error`レベルは`FailedEvent`から導出する |

`Payload`は通常イベントと失敗イベントのどちらでも`EventSpec`が保持する。

RAGScopeアプリケーションとAI推論サービスのコード内部では、通常イベントに`LogError`や`error`レベルを設定できない形でログイベントを表現する。失敗イベントでは`LogError`を必須とし、失敗イベントであることから一意に決まるイベント名と`error`レベルを、呼び出し側から別々に指定させない。

正確な型と生成方法は各コンポーネントのコードを正本とする。

`LogError`へ渡せる情報は[エラー設計](../エラー設計.md)に従い、内部原因、元の例外メッセージ、スタックトレースを含めない。

## 3. ログイベントをCLI実行・サービス状態へ関連付ける

`EventContext`は、ログイベントが1回のCLIコマンドに属するか、サービス自身の状態変化に属するかを区別する。

| `EventContext` | 表す対象 |
|---|---|
| Execution | 1回のCLIコマンドに属するログイベント |
| Service | サービスの起動・終了など、特定のCLIコマンドに属さない状態変化 |

Executionには`execution_id`を必須とする。CLIコマンドの処理を開始する境界で、最初のログイベントを記録する前に`execution_id`を1回生成する。同じCLIコマンドから呼び出すコンポーネントには同じ`execution_id`を渡し、別のCLIコマンドには別の値を使用する。

Serviceは特定のCLIコマンドに属さないため`execution_id`を持たない。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、v1の共通アプリケーションログイベントへ含めない。

## 4. ログへ記録してよい情報

ログを記録する各機能の設計では、`Payload`と`LogError`へ記録してよい情報をあらかじめ定義する。RAGScopeアプリケーションとAI推論サービスは、その許可された情報だけをログイベントへ渡す。記録した後に正規表現で伏せ字にする処理だけを、情報保護の手段にはしない。

| 対象 | そのまま記録しないもの | 代わりに使用する情報 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

`debug`を有効にしても記録できる情報は増やさない。安全性を確認できない値は記録しない。

## 5. ログ記録自体が失敗した場合

必須ログ記録処理は、ログ記録の成功または失敗を、元の機能処理の結果とは別の結果として呼び出し元へ返す。

ログ基盤自身が失敗した場合、その失敗を記録するために同じログ記録処理を再度呼び出さない。機能処理の結果と必須ログ記録の結果からアプリケーション実行結果を決定する規則は、[エラー設計「3.1 機能処理と必須ログ記録の結果合成」](<../エラー設計.md#3.1 機能処理と必須ログ記録の結果合成>)を正本とする。

## 6. どこで何を定義・実装するか

| 定義・実装する場所 | 担当する内容 |
|---|---|
| 本設計 | `LogEvent`が表す共通情報、通常・失敗イベントで常に成立させる条件、CLI実行・サービス状態との関連付け、記録してよい情報の共通規則 |
| 各機能設計 | 具体的な`Operation`、通常イベント名、イベントを記録する処理上の位置、`Payload`、通常時のレベル、機能固有の記録禁止情報 |
| RAGScopeアプリケーションとAI推論サービスの設計・コード | 共通規則を満たすコード内部のログ型・データ構造、ログ受付、実行時の処理、外部表現への変換と実際の出力 |
| [エラー設計](../エラー設計.md)とアプリケーション実行境界 | 機能処理結果と必須ログ記録結果の合成、元の機能処理失敗の保持 |
| [構造化ログJSON表現設計](./構造化ログJSON表現設計.md)とJSON Schema | `LogEvent`をv1のJSONへ表現する規則と、正確な項目・型・必須条件 |

正確な定義は次を正本とする。

| 内容 | 正本 |
|---|---|
| RAGScopeアプリケーションの内部ログ型と生成時の条件 | [`RAGScope.Logging.Core`](../../../ragscope-app/logging-src/RAGScope/Logging/Core.hs) |
| v1のJSON項目、型、必須条件、通常・失敗イベントの許可形 | [`log-event.schema.json`](../../../contracts/logging/v1/log-event.schema.json) |
