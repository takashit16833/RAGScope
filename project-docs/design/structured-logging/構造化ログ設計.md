# 構造化ログ設計

> [!abstract] この文書の役割
> RAGScopeの構造化ログについて、プロジェクト全体が従う共通の意味と保証を定義する。

## 1. 構造化ログ1件から確認できる情報

RAGScopeは、観測した1つの出来事を構造化ログ1件として記録する。

| 確認できること | 記録する情報 |
|---|---|
| どの構造化ログ契約に従うか | 契約バージョン |
| どの記録か | 構造化ログ1件を識別するID |
| いつ記録されたか | 記録時刻 |
| どこで生成されたか | 生成したコンポーネント |
| どの実行に関係するか | 1回のCLI実行との関連、または特定のCLI実行に属さないコンポーネント自身の状態変化 |
| 何の処理で起きたか | ログで追跡する処理種別 |
| 何が起きたか | 通常の出来事、または処理の失敗 |
| 出来事にどのような補足があるか | 各機能で記録を許可した安全な補助情報 |
| 失敗の内容は何か | 失敗時だけ記録する安全なエラー情報 |

## 2. 通常の出来事と失敗

構造化ログ1件が表す出来事は、通常の出来事または処理の失敗のどちらか一方とする。

| 種類 | 記録する内容 | ログレベル | エラー情報 |
|---|---|---|---|
| 通常の出来事 | 何が起きたかを表す通常の出来事名 | `debug` / `info` / `warn`のいずれか | 持たない |
| 処理の失敗 | 処理が失敗したこと | `error` | 安全なエラー情報を必須とする |

通常の出来事と処理の失敗を同時に表す状態は許可しない。処理の失敗には通常の出来事名を付けない。

この区別を採用した設計判断は[ADR-0004](<../../adr/ADR-0004 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する.md>)に記録する。

## 3. 同じCLI実行に属するログを追跡する

1回のCLI実行から生じる構造化ログには、同じ`execution_id`を使用する。処理がコンポーネントの境界をまたいでも、同じCLI実行に属するログは同じ`execution_id`で関連付ける。別のCLI実行には別の`execution_id`を使用する。

コンポーネントの起動・終了など、特定のCLI実行に属さないコンポーネント自身の状態変化には`execution_id`を付けない。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、現在の構造化ログの対象に含めない。

## 4. ログへ記録してよい情報

各機能設計は、その機能の出来事に付随して記録してよい補助情報を定める。失敗時に記録するエラー情報は[エラー設計](../エラー設計.md)の公開境界に従い、機能固有のエラーコードや補助情報は各機能設計で定める。

| 対象 | 記録しない情報 | 記録に使用できる情報の例 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

記録した後に正規表現で伏せ字にする処理だけを、情報保護の手段にはしない。

`debug`を有効にしても記録してよい情報の範囲は増やさない。安全性を確認できない値は記録しない。
