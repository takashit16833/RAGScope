# 構造化ログ設計

> [!abstract] この文書の役割
> RAGScopeの構造化ログについて、プロジェクト全体が従う共通の意味と保証を定義する。
>
> 機能固有のイベント、各コンポーネント内部での実現、v1 JSONへの表現は、それぞれの設計と機械可読な正本で定義する。

## 1. 構造化ログから確認できる情報

ログイベント1件は、RAGScopeで観測した1つの出来事を表す。構造化ログから次の情報を確認できる状態を保証する。

| 確認できること | 記録する情報 |
|---|---|
| どの構造化ログ契約に従うか | 契約バージョン |
| どのログイベントか | ログイベント1件を識別するイベント識別子 |
| いつ、どこで記録されたか | 記録時刻と生成元 |
| どの実行またはサービス状態に関係するか | CLI実行では`execution_id`、サービス自身の状態変化ではサービス状態としての関連 |
| 何の処理で何が起きたか | 処理種別と、通常イベントまたは失敗イベント |
| その出来事に必要な追加情報 | 各機能で記録を許可した安全な補助情報 |
| 失敗した場合に何が起きたか | 公開してよい安全なエラー情報 |

生成元は、RAGScopeアプリケーションまたはAI推論サービスのどちらがログイベントを生成したかを表す。

処理種別は、ログで追跡する処理の種類を表す。通常イベント名は、その処理で観測した通常の出来事を表す。使用する処理種別、通常イベント名、ログを記録する処理上の位置、補助情報は各機能設計で定義する。

実験識別子など、機能固有の追跡情報は、各機能設計で記録する情報と記録位置を定める。

## 2. 通常の出来事と失敗を区別する

ログイベントが表す出来事は、通常イベントまたは失敗イベントのどちらか一方として扱う。

| 種類 | 表す内容 | 常に成立させる条件 |
|---|---|---|
| 通常イベント | 処理の進行、完了、注意など、処理失敗ではない出来事 | 通常イベント名と`debug` / `info` / `warn`のいずれかのログレベルを持ち、エラー情報を持たない |
| 失敗イベント | 処理が失敗したこと | 安全なエラー情報を必須とし、ログレベルは`error`として扱う |

通常イベントと失敗イベントを同時に表す状態は許可しない。失敗イベントに必要なエラー情報がない状態や、通常イベントを`error`レベルとして扱う状態も許可しない。

失敗イベントは通常イベント名を持たない。外部表現で失敗を示すイベント名が必要な場合は、失敗イベントであることから外部表現の変換時に決める。

この区別を採用した理由は[ADR-0004](<../../adr/ADR-0004 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する.md>)に記録する。

## 3. CLI実行とサービス状態へ関連付ける

ログイベントは、1回のCLIコマンドに属する出来事か、特定のCLIコマンドに属さないサービス自身の状態変化のどちらかとして記録する。

| ログイベント | 関連付ける対象 | `execution_id` |
|---|---|---|
| CLI実行に属するイベント | 1回のCLIコマンド | 必須 |
| サービス状態を表すイベント | サービスの起動・終了など、特定のCLIコマンドに属さない状態変化 | 持たない |

`execution_id`は、1回のCLIコマンドの処理を開始するとき、最初のログイベントを記録する前に1回生成する。

同じCLIコマンドに属するすべてのログイベントには同じ`execution_id`を使用し、別のCLIコマンドには別の値を使用する。

生存確認（health）・準備完了確認（readiness）などの稼働確認リクエストは、v1の構造化ログで定義するイベントの対象に含めない。

## 4. ログへ記録してよい情報

各機能設計で、補助情報とエラー情報へ記録してよい内容を定める。ログイベントには、そこで許可した情報だけを含める。

| 対象 | 記録しない情報 | 記録に使用できる情報の例 |
|---|---|---|
| 文書・生成内容 | 文書、文書チャンク、回答の全文 | 安定したID、件数、バイト数 |
| AI入力 | プロンプト全文、Embedding | トークン数、モデルID |
| 認証・接続情報 | 秘密情報、認証情報、DB接続文字列 | 記録しない |
| HTTP | 本文、ヘッダーの全文 | ステータス、許可した要約 |
| 例外 | スタックトレース、元の例外メッセージ | エラー分類、コード、安全なメッセージ |

記録した後に正規表現で伏せ字にする処理だけを、情報保護の手段にはしない。

`debug`を有効にしても記録してよい情報の範囲は増やさない。安全性を確認できない値は記録しない。

エラー情報として公開してよい内容と、元の例外など公開しない情報の境界は[エラー設計](../エラー設計.md)で定義する。

## 5. 設計・実装の分担

| 対象 | 担当する内容 |
|---|---|
| 本設計 | 構造化ログから確認できる情報、通常イベントと失敗イベントの条件、CLI実行・サービス状態との関連付け、記録してよい情報 |
| 各機能設計 | 機能固有の処理種別、通常イベント、記録する処理上の位置、補助情報、通常時のログレベル、機能固有の記録禁止情報 |
| 各コンポーネントの構造化ログ設計・実装 | 共通の意味と保証を、それぞれの内部型、ログ受付、実行時処理、出力境界で実現する |
| [RAGScopeアプリケーション構造化ログ設計](./RAGScopeアプリケーション構造化ログ設計.md) | RAGScopeアプリケーションでのログ受付、Haskell内部型、Runtime、Sink、出力境界 |
| [エラー設計](../エラー設計.md) | 公開してよい共通エラー情報と、機能処理・必須ログ記録の失敗を扱う規則 |
| [構造化ログJSON表現設計](./構造化ログJSON表現設計.md) | 本設計で定義した共通の意味をv1 JSONへ表現する規則 |
| [`log-event.schema.json`](../../../contracts/logging/v1/log-event.schema.json) | v1 JSONの正確な項目、型、必須条件、許可される組み合わせ |
| 各コンポーネントのコード | 正確な内部型、ログ生成処理、外部表現への変換実装、出力処理 |

v1 JSONへの変換は各コンポーネントが実装し、変換結果は共通の[構造化ログJSON表現設計](./構造化ログJSON表現設計.md)と[`log-event.schema.json`](../../../contracts/logging/v1/log-event.schema.json)に従う。
