# RAGScope要求定義

> [!abstract] この文書の役割
> RAGScopeが満たすべき機能、品質、制約、対象範囲、対象外を定義する。  
> システムの目的と価値は[RAGScope概要](./RAGScope概要.md)、ドメイン領域とその責務は[RAGScopeドメインモデル](./design/RAGScopeドメインモデル.md)、正式用語と概念間の基本関係は[RAGScope用語集](./RAGScope用語集.md)、実現方法は[システムアーキテクチャ](./design/システムアーキテクチャ.md)、段階的な実現計画は[ロードマップ](./project-management/ロードマップ.md)を参照する。

## 1. 機能要件

機能要件は、[RAGScopeドメインモデル](./design/RAGScopeドメインモデル.md)で定義する4つのドメイン領域と、それらを横断する利用インターフェースに沿って整理する。

| 分類 | 要求ID | 扱うこと |
|---|---|---|
| 文書 | `REQ-DOC-*` | 文書の取り込み、版・分割・追跡、検索用データ |
| 評価データ | `REQ-DATASET-*` | 評価データセット、評価データ、正解根拠 |
| 検索・回答生成 | `REQ-RET-*`、`REQ-GEN-*` | 検索、回答生成用文書チャンク選択、回答、引用 |
| 実験・評価 | `REQ-EXP-*`、`REQ-EVAL-*`、`REQ-RPT-*` | 実験条件、実行結果、評価、集計、実験レポート |
| 横断的な利用 | `REQ-USE-*` | RAGScope CLIとRAGScope APIからの利用 |

### 1.1 文書

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-DOC-001` | 技術文書を取り込めること。 | 対象形式の文書をそれぞれ登録し、本文が保存されることを確認する。 |
| `REQ-DOC-002` | 文書バージョンを文書チャンクへ分割できること。 | 取り込んだ文書バージョンから複数の文書チャンクが生成されることを確認する。 |
| `REQ-DOC-003` | 各文書チャンクを、対応する文書、文書バージョン、文書内の位置へ追跡できること。 | 文書チャンクから対応する文書バージョンの本文範囲を特定できることを確認する。 |
| `REQ-DOC-004` | 文書、文書集合、分割条件を識別し、異なる版や条件を混同せず管理できること。 | 異なる文書内容または分割条件を混同せず参照できることを確認する。 |
| `REQ-DOC-005` | 文書または分割条件を更新した場合、対応する検索用データを再生成できること。 | 更新前後のデータが識別され、更新後の条件で検索できることを確認する。 |

### 1.2 評価データ

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-DATASET-001` | 質問、参照回答、回答可能性、正解根拠を1件の評価データとして管理できること。 | 保存した評価データの各要素を取得できることを確認する。 |
| `REQ-DATASET-002` | 正解根拠を、正規化後の文書内の範囲として指定できること。 | 指定した根拠範囲と文書の本文が一致することを確認する。 |
| `REQ-DATASET-003` | 根拠文字列から文書内の位置を計算し、位置を手作業で数えずに評価データを作成できること。 | 根拠文字列を指定し、位置が自動計算されることを確認する。 |
| `REQ-DATASET-004` | 複数の評価データを評価データセットとして管理し、評価データを開発用（`dev`）とテスト用（`test`）に分けて扱えること。 | 同じ評価データセットから`dev`または`test`の評価データだけを選択して実験できることを確認する。 |
| `REQ-DATASET-005` | 回答可能（`answerable`）な評価データに、文書内の連続した範囲を正解根拠として設定できること。 | 連続した範囲を正解根拠として持つ評価データを登録・評価できることを確認する。 |

### 1.3 検索・回答生成

#### 1.3.1 検索

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-RET-001` | 比較基準（baseline）となる全文検索を実行できること。 | 質問に対する順位付き検索結果を取得できることを確認する。 |
| `REQ-RET-002` | 文書チャンクと質問の意味的な近さを利用するdense検索を実行できること。 | 質問に対する順位付き検索結果を取得できることを確認する。 |
| `REQ-RET-003` | 全文検索とdense検索の結果を統合するhybrid検索を実行できること。 | 両方式の候補から統合された順位結果を取得できることを確認する。 |
| `REQ-RET-004` | 検索候補を別の基準またはモデルで再評価し、並べ替えられること。 | 並べ替え前後の順位を比較できることを確認する。 |
| `REQ-RET-006` | 検索結果と、回答生成へ実際に渡した回答生成用文書チャンクを区別できること。 | 検索結果と回答生成用文書チャンクの内容・順位・件数を別に確認できることを確認する。 |

#### 1.3.2 回答生成と引用

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-GEN-001` | 検索結果から回答生成用文書チャンクを選び、回答を生成できること。 | 質問、回答生成用文書チャンク、生成された回答を対応付けて確認できることを確認する。 |
| `REQ-GEN-002` | 利用者が管理する環境で動作する学習済みモデルを、主要な回答生成手段として使用できること。 | 外部LLM APIを必須とせず回答生成を実行できることを確認する。 |
| `REQ-GEN-003` | 回答と引用を構造化して取得できること。 | 回答と引用を機械的に区別して取得できることを確認する。 |
| `REQ-GEN-004` | 引用先が存在しない引用を検出できること。 | 存在しない参照先を含む引用を評価で識別できることを確認する。 |
| `REQ-GEN-005` | 文書から回答できない質問に対して、回答を拒否する動作を扱えること。 | 回答不能（`no-answer`）の評価データで回答または拒否結果を確認する。 |
| `REQ-GEN-006` | 回答生成で得た引用と、評価データが保持する正解根拠を区別して管理できること。 | 任意の評価データについて、生成結果の引用と正解根拠を別に取得できることを確認する。 |

### 1.4 実験・評価

#### 1.4.1 実験

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-EXP-001` | 文書分割、検索、`reranking`、回答生成、評価の条件を実験条件として保存できること。 | 実験結果から使用した各条件を特定できることを確認する。 |
| `REQ-EXP-002` | 条件の異なる実験を識別し、同じ評価データに対する結果を比較できること。 | 2つ以上の実験を指定し、同じ評価データに対応する評価データごとの実行結果を比較できることを確認する。 |
| `REQ-EXP-003` | 各評価データについて、各検索段階の結果、回答生成用文書チャンク、回答生成用プロンプト、回答、引用、処理時間、状態、エラーを評価データごとの実行結果として追跡でき、評価処理で得た指標や判定を評価データごとの評価結果として追跡できること。 | 任意の評価データに対応する評価データごとの実行結果と評価データごとの評価結果から各情報を取得できることを確認する。 |
| `REQ-EXP-004` | 実験結果として、評価データごとの実行結果、評価データごとの評価結果、実験全体の集計結果を保存できること。 | 1つの実験について、3種類の結果をそれぞれ取得できることを確認する。 |
| `REQ-EXP-005` | 保存済みの評価データごとの実行結果を使って、検索または回答生成を再実行せずに再評価し、評価データごとの評価結果と実験全体の集計結果を再計算できること。 | 評価処理の変更後に、保存済みの評価データごとの実行結果から評価データごとの評価結果と実験全体の集計結果を再計算できることを確認する。 |
| `REQ-EXP-006` | 実験の開始、終了、成功、失敗と、失敗した場合のエラーを記録できること。 | 正常終了と異常終了した実験について、状態、開始、終了、エラーを確認する。 |

#### 1.4.2 評価

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-EVAL-001` | 回答可能（`answerable`）な評価データについて、検索結果を`Hit@k`、`MRR`、`EvidenceCoverage@k`、`EvidenceDensity@k`で評価できること。 | 既知の検索結果に対する各指標を計算し、期待値と一致することを確認する。 |
| `REQ-EVAL-002` | 必要に応じて`Recall@k`と`Precision@k`を補助指標として計算できること。 | 同一の関連チャンク定義に対して各指標を計算できることを確認する。 |
| `REQ-EVAL-003` | 検索結果と、回答生成用文書チャンクを別に評価できること。 | 同じ評価データに対して両者のCoverageとDensityを別に取得できることを確認する。 |
| `REQ-EVAL-004` | `reranking`前後の検索品質と追加処理時間を比較できること。 | 同じ候補集合に対する前後の指標と処理時間を確認する。 |
| `REQ-EVAL-005` | 回答の根拠忠実性（`faithfulness`）、正確性、関連性、引用の正確性を評価できること。 | 各評価データについて、回答と引用の評価指標・判定を評価データごとの評価結果として取得できることを確認する。 |
| `REQ-EVAL-006` | 回答可能（`answerable`）／回答不能（`no-answer`）という回答可能性の判定結果を、正解率、適合率（`precision`）、再現率（`recall`）、F1、誤回答率、誤拒否率で確認できること。 | 回答可能と回答不能の評価データを含む評価データセットで各値を集計する。 |
| `REQ-EVAL-007` | 検索、`reranking`、回答生成などについて、処理時間、成功率、タイムアウト率、実行資源を実験間で比較できること。 | 条件の異なる実験について、各値を同じ基準で比較できることを確認する。 |
| `REQ-EVAL-008` | 回答内の引用が正しいかだけでなく、根拠を必要とする主張に必要な引用が付いているかを評価できること。 | 必要な引用を欠く回答を評価し、引用完全性の不足を識別できることを確認する。 |

#### 1.4.3 実験レポート

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-RPT-001` | 実験結果をMarkdown / CSV形式の実験レポートとして出力できること。 | 同じ実験結果から両形式の実験レポートを生成する。 |
| `REQ-RPT-002` | 実験レポートから実験条件、実験全体の集計結果、評価データごとの実行結果、評価データごとの評価結果、失敗例を確認できること。 | 生成された実験レポートに必要な情報が含まれることを確認する。 |
| `REQ-RPT-003` | 条件の異なる実験結果を比較した実験レポートを生成できること。 | 2つ以上の実験を指定して比較結果を含む実験レポートを出力する。 |

### 1.5 横断的な利用

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-USE-001` | 主要な処理をRAGScope CLIから実行できること。 | 文書登録、検索、実験、比較、実験レポート生成の主要操作をRAGScope CLIから実行する。 |
| `REQ-USE-002` | 主要な処理をRAGScope APIとして提供できること。 | RAGScope APIから主要処理を呼び出せることを確認する。 |

## 2. 非機能要件

### 2.1 追跡可能性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-TRACE-001` | 回答から、回答生成用文書チャンク、検索結果、文書バージョン、実験条件へ遡れること。 | 任意の回答から各情報を参照できることを確認する。 |
| `REQ-NF-TRACE-002` | 文書チャンクと正解根拠を、同じ文書バージョンと位置情報で比較できること。 | 文書更新前後を混同せず重なりを計算できることを確認する。 |

### 2.2 再現性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-REP-001` | 使用したコード、文書集合、評価データセット、実験条件、モデル、実行環境を記録できること。 | 実験結果から各情報を取得できることを確認する。 |
| `REQ-NF-REP-002` | 再現性は、出力文章の完全一致ではなく、同じ条件と手順で比較可能な実験を再実行できることとして扱う。 | 記録した条件を用いて再実行し、比較対象として扱える結果が得られることを確認する。 |
| `REQ-NF-REP-003` | 第三者がREADMEに従ってローカル環境を構築し、サンプルデータの取り込みから実験レポート生成まで実行できること。 | 新しい環境で公開手順を実行し、一連の処理が完了することを確認する。 |

### 2.3 信頼性と保守性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-REL-001` | 主要な正常系と異常系をテストで確認できること。 | 自動テストを実行し、主要経路と代表的な失敗を確認する。 |
| `REQ-NF-REL-002` | 外部プロセス、モデル処理、データベース処理の失敗を、処理状態とエラーとして記録できること。 | 意図的に失敗を発生させ、状態と原因を確認する。 |
| `REQ-NF-REL-003` | タイムアウトと、同じ処理を繰り返しても安全な場合の再試行を扱えること。 | タイムアウトと一時的失敗を発生させ、規定した挙動を確認する。 |
| `REQ-NF-REL-004` | 実験で変更する設定をコードへ埋め込まず、実験条件として管理できること。 | 実験条件の変更をコード変更なしで反映できることを確認する。 |
| `REQ-NF-REL-005` | 処理の進行、失敗、実験を識別できるログを出力できること。 | 1回の実験に関係するログを識別して確認する。 |

### 2.4 性能の観測

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-PERF-001` | 検索、`reranking`、回答生成などの処理時間を段階別に計測できること。 | 実験結果から段階ごとの処理時間を取得する。 |
| `REQ-NF-PERF-002` | 回答生成では、最初のトークンが得られるまでの時間、生成トークン数、生成時間を計測できること。 | 評価データごとの実行結果から各値を取得する。 |
| `REQ-NF-PERF-003` | 実行環境のCPU / GPU、メモリ、デバイス、データ型（`dtype`）など、性能比較に必要な条件を記録できること。 | 実験結果から実行環境を確認する。 |

具体的な性能目標値は、対象文書集合とモデルを決定し、実測可能になった段階で定める。

### 2.5 AWSへの配置

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-DEPLOY-001` | RAGScopeをAWSへ配置し、サンプルデータの取り込みから代表的な実験と実験レポート生成までを実行できること。 | AWS上へ構築した環境で代表的な一連の処理を実行し、結果を取得できることを確認する。 |
| `REQ-NF-DEPLOY-002` | AWS環境を再現可能な手順とInfrastructure as Codeで構築・削除できること。 | 新しいAWS環境へ同じ定義を適用して構築し、検証後に対象資源を削除できることを確認する。 |

## 3. 制約

### 3.1 技術・実行方針

- モデルの事前学習や基盤モデルの研究は行わず、既存の学習済みモデルを使用する。
- RAGScopeの中核機能はローカル環境で実行可能な構成を維持する。
- 外部のLLM APIは主要な実行手段とせず、必要になった場合に比較対象として追加する。

### 3.2 初期データ

| 項目 | 制約 |
|---|---|
| 文書形式 | Markdown / TXT |
| 言語 | 最初は英語。日本語は第2の文書集合 |
| 規模 | 数十〜数百文書 |
| 分野 | ライセンスが明確な1つの技術分野 |
| 正解根拠 | v0.1では回答可能（`answerable`）な評価データ1件につき1つの連続範囲 |

## 4. 対象外

初期版からv1.0までは、次を対象外とする。

- PDF、OCR、画像
- 複雑なレイアウト解析
- 大量データ
- 複数箇所の根拠を統合する評価（multi-hop評価）
- マルチテナント
- 本格的なWeb UI
- 認証
- ストリーミング
- エージェント
- Kubernetes
- 複数ノードの分散推論
- 高可用構成
- vLLM
