## 判断案

|論点|推奨する判断|
|---|---|
|1. JSON Schemaの配置|`contracts/logging/v1/log-event.schema.json`|
|2. fixtureの配置|`contracts/logging/v1/fixtures/valid/`と`invalid/`|
|3. Schemaの版|Draft 2020-12を使用|
|4. ログのスコープ|`scope: execution`と`scope: service`の2種類|
|5. ID|`event_id`と`execution_id`はUUIDv4|
|6. 時刻|RFC 3339のUTC、ミリ秒3桁、末尾`Z`|
|7. logger障害|JSON変換失敗と出力先への書き込み失敗を区別|
|8. 命名|コンポーネント名・イベント名・エラーコードの規則を統一|

JSON Schemaは、現在の公式仕様である[Draft 2020-12](https://json-schema.org/specification)を採用します。Haskell専用、Python専用の場所ではなく、両者が参照する`contracts/`配下に置く案です。

### 実行ログとサービスログ

ログ自身に次の区別を持たせます。

- `execution`
    - CLIコマンドなど、開始と終了がある処理
    - `execution_id`必須
- `service`
    - AIサービスの起動・停止など
    - `execution_id`なし

ヘルスチェックやHTTPアクセスログは、この共通ログ契約にはまだ含めません。API設計が確定してから扱います。

### IDと時刻

- `event_id`
    - ログ1件ごとに異なるUUIDv4
- `execution_id`
    - CLIコマンドの開始から終了まで共通のUUIDv4
- `timestamp`
    - 例：`2026-07-27T10:15:30.123Z`
- `duration_ms`
    - 処理時間が必要なイベントだけに付与

UUIDは現行標準の[RFC 9562](https://www.rfc-editor.org/info/rfc9562/)、時刻形式は[RFC 3339](https://www.rfc-editor.org/info/rfc3339/)に合わせます。UUIDv7の時系列性は現時点では不要なので、単純なUUIDv4を推奨します。

### logger自身が失敗した場合

以下の扱いを推奨します。

- JSONへの変換に失敗した場合：`encode_failed`
- stderrなどへの書き込みに失敗した場合：`sink_failed`
- loggerからloggerを呼び出さない
- 本来の処理も失敗している場合、本来のエラーを優先する
- 本来の処理が成功しても必須ログを出せなかった場合、最終的には内部エラーとして失敗させる
- 同じstderrへプレーンテキストでフォールバックしない

プレーンテキストを混ぜるとJSON Linesとして読み取れなくなるため、フォールバック出力は採用しません。

### 命名規則

`component`は、処理対象ではなく「ログを出したコンポーネント」を表します。

- `ragscope_app`
- `ai_service`

イベント名は次の形式にします。

```
<component>.<operation>.<phase>
```

例：

```
ragscope_app.document_read.started
ragscope_app.document_read.failed
ai_service.embedding_generate.succeeded
```

`phase`は原則として次の3つです。

```
started
succeeded
failed
```

エラーコードは次の形式を基本とします。

```
<domain>.<reason>
```

例：

```
input.file_not_found
config.invalid_value
ai_service.unavailable
internal.log_sink_failed
```
