# RAGScopeロードマップ

> [!abstract] この文書の役割
> RAGScopeがどのようなリリース可能なバージョンを経て発展するかを示す。  
> 要求の正本は[RAGScope要求定義](../docs/RAGScope要求定義.md)、現在のシステム構成は[システムアーキテクチャ](../docs/design/システムアーキテクチャ.md)を参照する。

## 1. 進め方

- 各Milestoneは、単独で実行または検証でき、Git tagを付けられる状態とする。
- Epic・Ticketへの具体化は[RAGScopeプロジェクト管理規約](../RAGScopeプロジェクト管理規約.md)に従う。
- 各Milestoneの成功条件を満たすまで、後続機能を現在の作業へ混ぜない。
- AWSへの配置はRAG本体と分離し、小さな検証として実施する。
- 将来構成は、先行する実装や実験の結果を確認してから決定する。

## 2. バージョン計画

### [v0.0 — 最小のdense検索を実行できる](./milestones/v0.0/v0.0.md)

少量の固定Markdown文書を固定ルールで文書チャンクへ分割し、AI推論サービスで各文書チャンクのEmbeddingを生成して保存する。RAGScope CLIから質問を入力し、exact vector searchによって上位の文書チャンクを表示できる状態にする。あわせて、共通エラー契約と構造化ログSchemaを定義し、契約を利用する各コンポーネントの最小基盤を整える。retry / timeoutは共通原則を定めたうえで、RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求するoperationから必要な範囲で段階的に導入する。

### v0.1 — 検索実験を保存・評価・比較できる

評価問題、文書の正規化と位置情報、文書・データ・設定のバージョン管理、質問ごとの検索結果保存を追加する。dense検索と全文検索のbaselineを同じ評価データで比較し、検索指標とMarkdown / CSVレポートによって差を説明できる状態にする。

### v0.1.5 — AWSへの小規模な配置を検証できる

RAG本体とは独立したデプロイスパイクとして、Embedding処理を含む小さな構成をAWSへ作成・接続・削除する。CloudFormation、EC2、RDS、S3、IAM、Session Manager、Secrets Manager、CloudWatchを利用し、通信経路、権限、料金、成果物の退避、削除後の残存物を説明できる状態にする。v0.0で整備した構造化ログをCloudWatchへ収集し、同じ実行に関係するイベントを検索できることも確認する。

### v0.2 — self-hosted modelで回答と引用を生成できる

検索した文書をcontextとして、自分の環境で動かすモデルから回答を生成する。生成条件、prompt、context、回答、構造化引用を保存し、文書から回答できない質問への拒否も扱える状態にする。

### v0.3 — hybrid検索とrerankingを比較できる

全文検索とdense検索を統合するhybrid検索と、Cross Encoderによるrerankingを追加する。適用前後の検索精度、取得内容、追加処理時間を同じ評価データで比較できる状態にする。

### v0.4 — 回答・引用・回答可能性を評価できる

reference answerを利用して、回答のfaithfulness、正確性、関連性、引用の正確性を評価する。answerable / no-answerの判定も含め、検索精度だけでなく最終回答の品質を比較できる状態にする。

### v0.5 — 実験基盤としての信頼性と観測性を備える

v0.0で導入した共通エラー・構造化ログとoperation単位のretry / timeoutを実験基盤向けに拡張し、Embedding cache、tracing、batch、非同期job、性能集計、障害時の挙動を整備する。正常時の精度だけでなく、処理時間、成功率、失敗原因と処理間の関係を追跡できる状態にする。

### v1.0 — 第三者が再現できるローカル公開版を完成させる

README、構成図、API仕様、必要なADR、sample data、比較レポート、再現手順、制約、既知の問題、モデルとデータセットのライセンス、CIを整備する。第三者がローカル環境を構築し、sample dataの取り込みから実験レポートの生成まで実行できる状態にする。

### v1.1 — AWS上の次の構成を判断する

v0.1.5のデプロイスパイクとv1.0の完成結果を確認し、EC2上のcontainer、ECR、ECS / Fargateへ進むかを判断する。AWS構成を追加しても、高可用性や大規模運用を実現したとは主張しない。
