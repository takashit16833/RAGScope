# RS-0002 固定ルールでMarkdown文書をチャンク化する

## 目的

v0.0でMarkdown文書をEmbedding生成とdense検索へ渡すためには、RS-0001で読み込んだ文書本文を、検索対象として扱える複数のチャンクへ分割する必要がある。

このTicketでは、RS-0011で作成した文書処理設計に従い、Markdown本文を1,000 Unicodeコードポイントごとに、overlapなしで先頭から順番に分割する。生成した各チャンクには元文書を識別する情報と文書内での順序を持たせ、後続のEmbedding生成処理から利用できる値として取得する。

## 前提

- [RS-0011 固定Markdown文書の取り込みとチャンク化を設計する](<./RS-0011 固定Markdown文書の取り込みとチャンク化を設計する.md>)が完了している
- [RS-0001 固定Markdownファイルを読み込む](<./RS-0001 固定Markdownファイルを読み込む.md>)が完了し、Markdown本文を`Text`として取得できる

## 完了条件

- [ ] Markdown本文を、先頭から1,000 Unicodeコードポイントごとに分割できる
- [ ] チャンク間にoverlapがなく、最後のチャンクだけが1,000 Unicodeコードポイント未満になり得る
- [ ] 空でない本文から、1件以上のチャンクを生成できる
- [ ] 各チャンクが、元文書を識別する情報、0始まりの連続した`chunkIndex`、本文を持つ
- [ ] すべてのチャンク本文を`chunkIndex`順に連結すると、入力されたMarkdown本文と完全に一致する
- [ ] Markdown記法、空行、改行を削除・置換せず、入力本文の内容を保持できる
- [ ] 生成したチャンク列を、表示処理の内部だけに閉じず、呼び出し元へ返して後続のEmbedding生成処理から利用できる
- [ ] 1,000 Unicodeコードポイント以下の本文、1,000を超える本文、ちょうど境界値となる本文、空の本文について、自動テストで挙動を確認できる
- [ ] 実装で具体化または変更されたチャンクの構造、固定ルール、不変条件、空本文の扱いが`design/文書処理設計.md`へ反映されている
- [ ] 実装と文書処理設計に解消していない差異がない
- [ ] プロジェクトで定めたテストコマンドを実行し、追加したテストを含めて成功する

## 対象外

- Markdown見出し、段落、文、単語などの意味的な境界を考慮した分割
- チャンク間のoverlap
- Tokenizerを使用したトークン数ベースの分割
- チャンクサイズやoverlap値をCLI、設定ファイル、データベースから変更する機能
- 複数のチャンク条件の比較
- 改行コードやUnicodeの正規化
- 元文書内の厳密な`start_offset`・`end_offset`の保存
- 文書、チャンク条件、チャンク集合のversion管理
- FrontmatterやMarkdown構造の解析
- Embedding生成
- PostgreSQLへの保存
- 検索処理

## 実装メモ

- チャンクサイズは、v0.0では`1,000` Unicodeコードポイントに固定する。
- Haskellの`Text`を使用し、UTF-8のバイト数ではなくUnicodeコードポイント数として分割する。
- チャンク化処理は副作用を持たない純粋関数として実装し、入力本文からチャンク列を返す。
- 元文書を識別する値、`chunkIndex`、本文を保持する。正確な型名やフィールド名はコードを正本とする。
- 空の本文は有効な検索対象とせず、文書処理設計で定めた結果を返す。
- 分割前の本文に対して、正規化、Markdown記法の除去、前後空白の削除を行わない。
- 文字の欠落、重複、並び替えがないことを、チャンク本文の再連結によって確認する。
- 1,000 Unicodeコードポイントという値はv0.0の固定条件であり、検索品質が最適であることを主張しない。複数条件の比較と設定管理はv0.1で扱う。
- 初期設計を変更する必要が生じた場合は、理由と後続Epicへの影響を確認してから`文書処理設計.md`を更新する。
