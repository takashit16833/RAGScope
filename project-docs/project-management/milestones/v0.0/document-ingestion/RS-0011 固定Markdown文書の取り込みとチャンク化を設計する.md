# RS-0011 固定Markdown文書の取り込みとチャンク化を設計する

## 目的

v0.0の最初のEpicでは、固定Markdown文書の読み込みとチャンク化を複数の実装Ticketに分けて進める。実装ごとに責務やデータの扱いを個別判断すると、文書読み込みから後続のEmbedding生成までの境界や不変条件が曖昧になる。

このTicketでは、RS-0001とRS-0002へ着手する前に、既存の`docs/design/文書処理設計.md`を保持し、共通エラー・ログ契約、文書処理固有の対応、自動retryを行わない理由を反映して、固定Markdown文書の取り込みからチャンク生成までの現在設計として完成させる。

既存の初期設計に記載されている責務、処理フロー、固定チャンクルール、不変条件を再利用し、共通基盤との境界と残る判断を補完する。後続Ticketが迷わず実装へ着手できる見通しと判断基準を整える一方、正確なHaskellの型名、関数名、module構成など、コードを正本とする詳細までは固定しない。

本Ticketは、[共通エラーと構造化ログによる実行追跡Epic](<../error-logging/v0.0 共通エラーと構造化ログによる実行追跡.md>)が完了した後、その契約と[ADR-0002 — 共通実行基盤の契約とコンポーネント実装を分離する](<../../../../docs/adr/ADR-0002 共通実行基盤の契約とコンポーネント実装を分離する.md>)の共通原則を文書処理へ適用して完了する。retry / timeoutのoperation固有設計やexecutorは本Ticketの前提とせず、文書読み込みでは自動retryを行わないことと理由だけを`文書処理設計.md`へ記載する。

## 完了条件

- [ ] 既存の`docs/design/文書処理設計.md`が同じファイルとして保持され、`note_type: design`の現在設計へ更新されている
- [ ] 固定Markdown文書の読み込み、チャンク化、後続のEmbedding生成への受け渡しについて、RAGScopeアプリケーションが担当する責務と対象外が記載されている
- [ ] 固定パスのUTF-8 Markdownファイル1件を読み込み、本文を`Text`として扱う処理フローが記載されている
- [ ] 読み込んだ本文に対して、正規化、Markdown記法の除去、Frontmatterや見出しの解析を行わない方針が記載されている
- [ ] 実行時の入力パスはv0.0の固定値とし、読み込み処理自体はテスト可能な境界として分離する方針が記載されている
- [ ] Markdown本文を1,000 Unicodeコードポイントごとに、overlapなしで先頭から分割する固定ルールが記載されている
- [ ] 各チャンクが、元文書を識別する情報、0始まりの`chunkIndex`、本文を概念上保持することが記載されている
- [ ] チャンク本文を`chunkIndex`順に連結すると入力本文と完全に一致する不変条件が記載されている
- [ ] 空本文の扱い、存在しないファイルの読み込み失敗、後続処理へ渡してはならない状態が記載されている
- [ ] v0.0では導入しない正規化、offset管理、文書version、可変チャンク条件などの境界が明記されている
- [ ] コード、型、テストを正本とする詳細と、設計書へ記載する責務・契約・不変条件が区別されている
- [ ] 関連する要求定義とシステムアーキテクチャに矛盾しないことを確認できる
- [ ] 所属Epicの`関連文書`から`文書処理設計.md`を参照できる状態になっている
- [ ] 文書読み込み、本文検証、チャンク化で発生する失敗が、共通エラー契約へ対応付けられている
- [ ] 文書処理で出力する開始、完了、失敗のログが、共通ログ契約へ対応付けて記載されている
- [ ] 文書読み込みとチャンク化では自動retryを行わないことと、その理由が記載されている
- [ ] 共通エラー・ログ設計の作成後、`文書処理設計.md`と本Ticketから相対リンクで参照できる

## 対象外

- Markdownファイルを読み込むHaskellコードの実装
- Markdown本文をチャンク化するHaskellコードの実装
- 正確な型名、関数名、module名、使用libraryの決定
- テスト用Markdownファイルの作成
- Embedding生成API、PostgreSQL schema、dense検索の設計
- 複数のチャンク条件を比較するExperiment
- v0.1以降の正規化、offset、version管理の詳細設計
- 共通エラー・構造化ログ基盤そのものの設計と実装
- 外部operation固有のretry / timeout機能設計とexecutor実装

## 実装メモ

- `文書処理設計.md`には、基本設計と詳細設計を別文書へ分けず、責務と全体フローから固定ルール、不変条件、エラー・境界条件までを同じ文書へ記載する。
- 1,000 Unicodeコードポイントという値はv0.0の固定条件として扱い、検索品質が最適であるとは主張しない。
- 元文書を識別する情報は、v0.0の固定文書を後続処理で区別できる最小限の概念として設計する。永続的な文書ID体系やversion管理は導入しない。
- 実装で初期設計を変更する必要が生じた場合は、該当する実装Ticketで理由と影響を確認し、同じ設計書へ現在設計を反映する。
- 共通エラーと構造化ログによる実行追跡Epicが完了するまでは、本Ticketを完了扱いにしない。完了後は共通定義を複製せず、文書処理固有の対応と、自動retryを行わない判断だけを`文書処理設計.md`へ反映する。
