# RS-0011 固定Markdown文書の取り込みとチャンク化を設計する

## 目的

v0.0の最初のEpicでは、固定Markdown文書の読み込みとチャンク化を複数の実装Ticketに分けて進める。実装ごとに責務やデータの扱いを個別判断すると、文書読み込みから後続のEmbedding生成までの境界や不変条件が曖昧になる。

このTicketでは、RS-0001とRS-0002へ着手する前に、既存の[文書処理設計](../../../../design/features/文書処理設計.md)を現在設計として完成させる。文書処理固有の失敗、自動再試行を行わない理由、およびObservability共通設計を文書処理へ適用するときに必要な機能固有の判断を反映する。

既存の初期設計に記載されている責務、処理フロー、固定チャンクルール、不変条件を再利用し、後続Ticketが迷わず実装へ着手できる見通しと判断基準を整える。一方、正確なHaskellの型名、関数名、モジュール構成など、コードを正本とする詳細までは固定しない。

Observabilityについては[Observability設計](../../../../design/observability/README.md)の共通規則を前提とし、文書処理で独自SpanまたはEventRecordが必要か、必要な場合にどの処理・出来事を表すかだけを機能固有の判断として具体化する。開始・成功・失敗という理由だけで共通イベントを自動定義しない。

## 完了条件

### 責務と処理フロー

- [ ] `design/features/文書処理設計.md`が`note_type: design`の現在設計として保持されている
- [ ] 固定Markdown文書の読み込み、チャンク化、後続のEmbedding生成への受け渡しについて、RAGScopeアプリケーションが担当する責務と対象外が記載されている
- [ ] 固定パスのUTF-8 Markdownファイル1件を読み込み、本文を`Text`として扱う処理フローが記載されている
- [ ] 読み込んだ本文に対して、正規化、Markdown記法の除去、Frontmatterや見出しの解析を行わない方針が記載されている
- [ ] 実行時の入力パスはv0.0の固定値とし、読み込み処理自体はテスト可能な境界として分離する方針が記載されている

### チャンク規則と不変条件

- [ ] Markdown本文を1,000 Unicodeコードポイントごとに、重なり（overlap）なしで先頭から分割する固定ルールが記載されている
- [ ] 各文書チャンクが、元文書を識別する情報、0始まりの`chunkIndex`、本文を概念上保持することが記載されている
- [ ] 文書チャンクの本文を`chunkIndex`順に連結すると入力本文と完全に一致する不変条件が記載されている
- [ ] 空本文の扱い、存在しないファイルの読み込み失敗、後続処理へ渡してはならない状態が記載されている
- [ ] v0.0では導入しない正規化、元文書内の厳密な位置管理、文書のバージョン管理、可変チャンク条件などの境界が明記されている

### 失敗・Observability・再試行

- [ ] 文書読み込み、本文検証、チャンク化で発生する失敗を、文書処理固有の具体的なerror typeとして区別する境界が記載されている
- [ ] 文書読み込みとチャンク化について、時間を持つ処理をSpan、処理を説明する値をattributes、名前付きの時点イベントが本当に必要な場合だけEventRecordとする[Observability設計](../../../../design/observability/README.md)の判断基準を適用している
- [ ] typed failureの発生だけ、または処理の開始・成功・失敗だけを理由にEventRecordを自動定義していない
- [ ] 文書読み込みとチャンク化では自動再試行を行わないことと、その理由が記載されている

### 正本と整合

- [ ] コード、型、テストを正本とする詳細と、設計書へ記載する責務・契約・不変条件が区別されている
- [ ] 関連する要求定義、システムアーキテクチャ、Observability設計に矛盾しないことを確認できる
- [ ] 所属Epicの`関連文書`から`文書処理設計.md`を参照できる状態になっている

## 対象外

- Markdownファイルを読み込むHaskellコードの実装
- Markdown本文をチャンク化するHaskellコードの実装
- 正確な型名、関数名、モジュール名、使用ライブラリの決定
- テスト用Markdownファイルの作成
- Embedding生成API、PostgreSQLスキーマ、dense検索の設計
- 複数のチャンク条件を比較するExperiment
- v0.1以降の正規化、元文書内の位置、バージョン管理の詳細設計
- OpenTelemetry基盤そのものの設計と実装
- 外部処理固有の再試行・タイムアウトの機能設計と実行機構の実装

## 実装メモ

- `文書処理設計.md`は、現時点では責務・読者・利用目的が一続きであるため同じ文書で扱う。独立した詳細設計の責務が生じた場合は、文書管理規約に従って分離を判断する。
- 1,000 Unicodeコードポイントという値はv0.0の固定条件として扱い、検索品質が最適であるとは主張しない。
- 元文書を識別する情報は、v0.0の固定文書を後続処理で区別できる最小限の概念として設計する。永続的な文書ID体系やバージョン管理は導入しない。
- 実装で初期設計を変更する必要が生じた場合は、該当する実装Ticketで理由と後続Ticketへの影響を確認してから`design/features/文書処理設計.md`を更新する。
