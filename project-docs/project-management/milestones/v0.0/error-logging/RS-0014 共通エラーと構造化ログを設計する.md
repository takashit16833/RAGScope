# RS-0014 共通エラーと構造化ログを設計する

## 目的

v0.0では、文書読み込み、AI推論サービスとの通信、PostgreSQL処理など、異なる種類の処理と失敗を扱う。各実装Ticketが独自のエラー型、エラーコード、ログ項目、相関情報を決めると、処理全体を追跡できず、後から共通化する際に広範囲な修正が必要になる。

このTicketでは、後続の共通基盤実装と機能実装に先立ち、現在Haskell中心で記載されている`design/エラー・ログ設計.md`を、複数のコンポーネントが利用できる技術非依存の契約へ改訂する。構造化ログのserialized shapeをJSON Schemaとして定義し、各実装で共有する代表的なfixtureを作成する。v0.0のローカル実行で必要な最小範囲を定義し、将来のHTTP、AWS収集、tracingへ拡張できる境界を保ちつつ、現時点で使用しない詳細は固定しない。

## 実装メモ

- 設計書には、実装だけでは分かりにくい責務、契約、不変条件、処理フロー、変更時の注意を記載する。
- 正確な型定義やJSON encoderのコードをMarkdownへ複製しない。
- v0.0ではCLI commandとservice lifecycleを具体的なContextとして扱い、HTTPやbatchの完全なschemaを先回りして作らない。
- 将来のtracingへ拡張できる意図は残すが、現時点で`trace_id`やSpan構造を採用済みとして記載しない。

## 結果

### 設計と契約

- `エラー・ログ設計.md`を、複数コンポーネントが利用する技術非依存の共通契約へ改訂した。
- 共通エラー、LogEvent、event builder、logger、filter、encoder、sink、decoderの責務と変換境界を定義した。
- operationとphaseからevent名を生成し、operationとerror codeを機能ごとの閉じた型として扱う方針を定めた。
- ローカル実行では正常なCLI結果をstdout、構造化ログをstderrへ分け、1 eventを1行のJSONとして出力する方針を定めた。
- logger自身のencode・sink失敗、fallbackを採用しない方針、元のoperation失敗を上書きしない扱いを定めた。

### JSON Schemaとfixture

- serialized shapeの正本として`contracts/logging/v1/log-event.schema.json`を作成した。
- 共通field、category、level、component、execution・service context、Error、UUIDv4、UTC timestamp、識別子形式をDraft 2020-12で定義した。
- `contracts/logging/v1/fixtures/`へSchema適合例3件と不適合例10件を作成した。
- Draft 2020-12 validatorでSchema自体を検査し、適合例3件の受理と不適合例10件の拒否を確認した。

### 後続Ticketへ渡す判断

- RS-0015とRS-0018は同じSchemaとfixtureを使用し、型、例外変換、event builder、logger、encoder、sinkを各コンポーネントで実装する。
- 1回のCLI commandでは、コンポーネント境界を越えて同じ`execution_id`を引き継ぐ。
- 各実装は、Schema適合だけでなく、eventとoperationの対応、識別子の閉じた型、stdoutとstderrの分離、test sink、failing sinkをテストする。

### 後続機能で具体化する事項

- 機能固有のoperation、event、error code、許可するPayload・error contextは、各機能の設計とコードで定義する。
- HTTP error responseと`execution_id`の伝播方法は、API設計とOpenAPIで定義する。
- retry回数、timeout値、再試行安全性はoperationごとに判断する。
- CloudWatchの具体設定はv0.1.5、tracingとbatch・非同期jobの相関情報はv0.5以降で決定する。
