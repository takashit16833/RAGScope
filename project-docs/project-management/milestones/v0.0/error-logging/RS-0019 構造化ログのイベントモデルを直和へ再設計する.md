# RS-0019 構造化ログのイベントモデルを直和へ再設計する

## 目的

RS-0018でAI推論サービス側の構造化ログモデルを実装する過程で、現在の`EventSpec`が`event`、`level`、`error`を独立した値として保持するため、失敗イベントの意味を複数の項目で重複して表し、不正な組み合わせを生成後の検証や限定された生成関数で防ぐ必要があることが明確になった。

RAGScopeアプリケーションのHaskell実装でも、`EventSpec`は`event`、`level`、`Maybe LogError`を独立したフィールドとして持つ。現在のJSON Schemaも`event = failed`の場合に`level = error`と`error`必須を要求する一方、`event != failed`かつ`level = error`の組み合わせを禁止しておらず、内部モデルと外部契約の双方で本来不要な状態を表現できる。

このTicketでは、通常イベントと失敗イベントを直和として表現し、固定的に導出できる失敗イベント名やログレベルを内部モデルの独立入力として重複保持しない方針へ、共通ログイベントモデルを再設計する。設計判断を新しいADRへ記録し、現在設計、JSON Schemaとfixture、RAGScopeアプリケーションのHaskell実装を新しいモデルへ整合させる。

外部JSONの`LogEvent` / `spec`構造は維持し、JSON変換境界で通常イベントと失敗イベントから契約上必要な`event`、`level`、`error`を表現する。RS-0018のPython実装は、本Ticketで共通モデルを確定した後に新しい設計へ追随する。

## 実装メモ

現在の意味モデルは概念的に次の直積として扱われている。

```text
EventSpec
  ≈ Operation
  × Event
  × LogLevel
  × Payload
  × Maybe LogError
```

再設計では、共通部分と通常・失敗の選択を分ける次の形を出発点とする。

```text
EventSpec
  ≈ (Operation × Payload)
  × (NormalEvent + FailedEvent)
```

`NormalEvent`は通常イベント名と通常レベルを持ち、`FailedEvent`は安全な`LogError`を持つ。`failed`というイベント名と`error` levelは失敗variantから導出する。正確なHaskellの型名、constructor、モジュール配置は実装と設計更新の中で決定し、Ticket本文を型定義の正本にはしない。

RS-0018のPython実装は、本Ticketがデフォルトブランチへ反映されるまで共通イベントモデル部分の作業を停止し、その後に確定した共通設計とSchemaへ追随する。
