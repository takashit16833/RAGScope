# RS-0019 構造化ログのイベントモデルを直和へ再設計する

> [!note] 現在仕様について
> このTicket本文と結果はRS-0019実施時点の判断履歴であり、通常イベントと失敗イベントの直和や固定`failed`イベントは後続のADR-0005で置き換えられている。現在の実行追跡・構造化ログ契約は[実行追跡・構造化ログ契約設計](../../../../design/実行追跡・構造化ログ契約設計.md)を正本とする。RS-0018も現在契約へ追随して[AI推論サービスの実行追跡・構造化ログ基盤を実装する](<./RS-0018 AI推論サービスの実行追跡・構造化ログ基盤を実装する.md>)へ更新されている。

## 目的

RS-0018でAI推論サービス側の構造化ログモデルを実装する過程で、現在の`EventSpec`が`event`、`level`、`error`を独立した値として保持するため、失敗イベントの意味を複数の項目で重複して表し、不正な組み合わせを生成後の検証や限定された生成関数で防ぐ必要があることが明確になった。

RAGScopeアプリケーションのHaskell実装でも、`EventSpec`は`event`、`level`、`Maybe LogError`を独立したフィールドとして持つ。現在のJSON Schemaも`event = failed`の場合に`level = error`と`error`必須を要求する一方、`event != failed`かつ`level = error`の組み合わせを禁止しておらず、内部モデルと外部契約の双方で本来不要な状態を表現できる。

このTicketでは、通常イベントと失敗イベントを直和として表現し、固定的に導出できる失敗イベント名やログレベルを内部モデルの独立入力として重複保持しない方針へ、共通ログイベントモデルを再設計する。あわせて、構造化ログの意味モデル、RAGScopeアプリケーションでの実現、JSONによる外部表現を別の設計責務として分離し、外部表現の都合が共通の意味やコンポーネント内部の型へ逆流しない境界を確定する。

設計判断をADR-0004へ記録し、現在設計、JSON Schemaとfixture、RAGScopeアプリケーションのHaskell実装を新しいモデルへ整合させる。外部JSONの`LogEvent` / `spec`構造は維持し、serialization境界で通常イベントと失敗イベントから契約上必要な`event`、`level`、`error`を表現する。RS-0018のPython実装は、本Ticketで共通モデルを確定した後に新しい設計へ追随する。

## 実装メモ

現在の意味モデルは概念的に次の直積として扱われている。

```text
EventSpec
  ≈ Operation
  × Event
  × LogLevel
  × Payload
  × Maybe LogError
```

再設計では、共通部分と通常・失敗の選択を分ける次の形を出発点とする。

```text
EventSpec
  ≈ (Operation × Payload)
  × (NormalEvent + FailedEvent)
```

`NormalEvent`は通常イベント名と通常レベルを持ち、`FailedEvent`は安全な`LogError`を持つ。失敗を表すイベント名と`error` levelは失敗variantから導出する。正確なHaskellの型名、constructor、モジュール配置は実装と設計更新の中で決定し、Ticket本文を型定義の正本にはしない。

RS-0018のPython実装は、本Ticketがデフォルトブランチへ反映されるまで共通イベントモデル部分の作業を停止し、その後に確定した共通設計とSchemaへ追随する。

## 結果

- ADR-0004で、共通`EventSpec`を通常イベントと失敗イベントの直和として扱い、外部JSONの項目構造へ内部モデルを従属させない方針を採用した。ADR-0003は本判断により`superseded`とした。
- 構造化ログの現在設計を、共通の意味と不変条件、RAGScopeアプリケーションでのHaskell実現、v1 JSONへの投影という3つの責務へ分離した。
- `log-event.schema.json`は外部の`LogEvent` / `spec`構造を維持し、通常イベントを`event != failed`・`level = debug | info | warn`・`error`なし、失敗イベントを`event = failed`・`level = error`・`error`必須として相互排他的に検証する。
- Haskellの`EventSpec`は`NormalEvent`と`FailedEvent`を区別する型表現へ変更した。通常イベントは通常レベルだけを持ち、失敗イベントは`LogError`を必須とする。失敗イベント名と`error` levelは独立入力として保持しない。
- Runtimeは内部イベントから導出した実効ログレベルで出力判定し、JSON変換境界で通常・失敗variantをv1の外部JSONへtotalに投影する。
- `make check-app`を実行し、Fourmoluの整形確認、`cabal build all`、`cabal test all`、`cabal haddock all`が成功した。テスト結果は69 examples、0 failuresだった。
- RS-0018へ、通常イベントと失敗イベントを同じ意味上の不変条件で区別し、失敗時の`event = failed`と`level = error`を内部の独立入力として持たずserialization境界で導出する共通契約を引き渡す。
- AI推論サービス側のPython実装変更は本Ticketの対象外であり、RS-0018で追随する。
- Haddockでは一部の内部表現型と`LoggingFailure`へのリンク先未解決警告が出るが、`cabal haddock all`は成功しており、本Ticketの完了条件を阻害する失敗は確認されなかった。
