# RS-0018 AI推論サービスの共通エラー・構造化ログ基盤を実装する

## 目的

RS-0014で定義した実装技術に依存しない共通エラー契約と構造化ログ契約を、Embedding生成以降のAI推論サービス実装から利用できるPythonの最小基盤として提供する必要がある。

RAGScopeアプリケーションではRS-0015によって同じ共通契約を利用する基盤が実装された。RS-0019では、構造化ログの意味モデル、コンポーネントでの実現、JSONによる外部表現を別の責務として整理し、通常イベントと失敗イベントの不変条件を共通の意味として確定する。

AI推論サービスでもRAGScopeアプリケーションのHaskell固有構造を共有するのではなく、共通の意味と不変条件をPythonの型と生成境界で表現し、外部JSONへの変換は別のserialization境界として実装する。

このTicketでは、Pythonで発生した例外を安全な共通エラーへ変換する境界、`LogEvent`の意味モデル、実行との関連情報、JSON変換、ローカル環境向けの出力処理、テスト用の出力処理、ログ基盤自身の失敗を扱う境界を実装する。

あわせて、これらを正本リポジトリ上で実装・自動テストできる最小限のAI推論サービス用Pythonプロジェクト構成とテスト入口を整える。Webフレームワーク、HTTPアダプター、モデル、Tokenizer、AIライブラリ固有の処理は後続の機能Ticketへ残す。

- `design/structured-logging/構造化ログ設計.md`に、コンポーネントと外部表現から独立したLogEventの意味、不変条件、実行との関連付け、情報保護が記載されている

## 完了条件

### AI推論サービスの最小実装・テスト基盤

- [ ] AI推論サービスのPythonコードと自動テストを正本リポジトリで管理できる最小のプロジェクト構成が作成されている
- [ ] AI推論サービス側の共通エラー・構造化ログ基盤を、モデルやWebフレームワークを必要とせず自動テストできる
- [ ] AI推論サービス側のテストを再現可能に実行するコマンドまたはプロジェクト共通の検査入口が定義されている

### 共通エラーと例外変換

- [ ] 共通エラーの意味をPythonで表現し、正常結果と失敗結果を明示的に区別して扱える境界が実装されている
- [ ] Pythonで発生した例外を、安全な共通エラーへ変換するための機能固有ライブラリへ依存しない境界が実装されている
- [ ] 想定外の例外を、エラー分類`internal`の安全な共通エラーへ変換できる
- [ ] 内部原因を保持する情報と外部へ公開してよい情報を区別し、元の例外メッセージ、スタックトレース、その他の非公開情報を利用者向け情報や構造化ログへ渡さない
- [ ] 共通層が機能固有のエラーコードを任意に決定せず、各機能で定義する閉じたエラー表現または同等の境界から共通エラーへ変換できる

### 構造化ログの内部モデル

- [ ] Envelope、EventContext、EventSpecからなるLogEventの意味をPythonで表現できる
- [ ] EventSpecが通常イベントと失敗イベントを直和または同等の型表現で区別し、通常イベントは通常イベント名と通常レベル、失敗イベントは安全なLogErrorを必須とする
- [ ] 失敗イベントで固定的に決まるイベント名と`error` levelを内部の独立した入力として重複保持しない
- [ ] 1回の実行に属するログイベントとサービスの状態変化に属するログイベントを意味上区別できる
- [ ] 呼び出し元から渡された`execution_id`を、同じCLIコマンドに由来するAI推論サービスのログイベントへ引き継げる
- [ ] AI推論サービス自身の状態変化を表すサービスイベントでは、`execution_id`を持たないContextを扱える
- [ ] ログイベントごとにイベント識別子と記録時刻を付与できる
- [ ] 通常の機能処理から任意の`operation`、イベント名、ログレベル、`payload`を自由に組み立てさせず、各機能の閉じたイベント表現または同等の境界から共通ログ表現へ変換できる
- [ ] Pythonの内部モデルがJSONの項目構造やserialization方式を設計理由として持たない

### JSON変換とSchema適合

- [ ] 完成した意味上有効なLogEventを、serialization境界でv1のJSON表現へ投影できる
- [ ] 失敗variantから`event = failed`、`level = error`、`error`を導出し、通常variantでは`event != failed`、通常level、`error`なしとして表現できる
- [ ] 完成したログイベントを、ログイベント1件につき1行のJSONへ変換できる
- [ ] AI推論サービスが生成するログイベントが共通JSON Schemaへ適合することを自動テストで確認できる
- [ ] 共通の適合fixtureを検証入力として利用し、不適合fixtureがSchemaから拒否されることを確認できる
- [ ] JSONオブジェクトの項目順ではなく、意味とSchema適合性を検査している
- [ ] 通常のログイベント生成経路で契約不適合をserializationまで先送りせず、Python側の型、生成境界、検証、テストによって可能な範囲で防止している
- [ ] JSON変換でなお発生し得る失敗を、機能固有の失敗ではなくログ基盤自身の失敗として扱える

### 出力処理と情報保護

- [ ] ローカル環境向けの出力処理が、構造化ログを標準エラー出力へ1イベント1行で出力できる
- [ ] ログ受付処理が具体的な標準エラー出力へ直接固定されず、出力処理を差し替えられる
- [ ] 自動テストから出力された`LogEvent`を直接検査できる、メモリ保存の出力処理または同等のテスト用出力処理が実装されている
- [ ] 意図的に失敗する出力処理または同等のテスト境界を用いて、ログ基盤自身の失敗を検査できる
- [ ] 文書本文、文書チャンク、プロンプト、Embedding、秘密情報、認証情報、HTTP本文・ヘッダー全文、元の例外メッセージ、スタックトレースなど、構造化ログ設計で記録対象外とした情報を不用意に出力しない

### 機能処理と必須ログ記録の失敗時の意味

- [ ] 機能処理の結果と、その結果を記録する必須ログ処理の結果を独立した事実として扱える境界が実装されている
- [ ] 機能処理が成功し、必須ログ記録も成功した場合は元の成功結果を維持できる
- [ ] 機能処理が成功しても必須ログ記録が失敗した場合は、外側の実行を失敗として扱える
- [ ] 機能処理が失敗して必須ログ記録が成功した場合は、元の共通エラーを保持できる
- [ ] 機能処理と必須ログ記録の両方が失敗した場合は、元の共通エラーをログ基盤の失敗で上書きせず、両方の失敗を区別して保持できる
- [ ] ログ基盤自身の失敗を、失敗した同じログ経路へ再帰的に記録しない
- [ ] 壊れたJSONや通常テキストを、失敗した構造化ログの代替として標準エラー出力へ書き込まない
- [ ] 上記の成功・失敗の組み合わせと、失敗する出力処理を使用した挙動を自動テストで確認できる

### 設計反映と最終検証

- [ ] `design/structured-logging/AI推論サービス構造化ログ設計.md`が、共通の構造化ログ設計をAI推論サービスのPython実装で成立させる設計として作成され、RAGScopeアプリケーション固有の具体とJSON表現固有の具体を持たない
- [ ] 共通エラー、構造化ログ、JSON変換、実行との関連情報、任意項目、ログ基盤失敗の主要な正常系・異常系を自動テストで確認できる
- [ ] 実装によって共通の意味または外部JSON表現を変更する必要が生じた場合は、`design/エラー設計.md`、`design/structured-logging/構造化ログ設計.md`、`design/structured-logging/構造化ログJSON表現設計.md`、JSON Schemaのうち責務を持つ正本へ反映されている
- [ ] AI推論サービス固有の正確な型、関数、モジュール、設定、依存関係、具体的なテストケースをMarkdownへ重複して正本化していない
- [ ] Python実装、AI推論サービス構造化ログ設計、JSON Schema、検証用データ、共通設計に解消していない差異がない
- [ ] プロジェクトで定めたAI推論サービス側のテストまたは品質検査コマンドを実行し、追加したテストを含めて成功する

## 実装メモ

- AI推論サービスでは、共通エラーと構造化ログの実装を責務の明確な共通モジュールとして内部に置く。利用実態が生じる前に独立した共通パッケージへ分離しない。
- RAGScopeアプリケーションのHaskell型、private sublibrary、Facade構成をPythonへ移植すること自体を目的にしない。共有するのは`構造化ログ設計.md`が定める意味と不変条件、および`構造化ログJSON表現設計.md`とJSON Schemaが定める外部表現である。
- Python内部の型は前者を自然に表現するために設計し、後者の項目構造へ合わせることを優先しない。
- 具体的なWebフレームワークやAIライブラリの例外は、RS-0003やRS-0007などで機能固有のエラーコードとともに共通エラーへ変換する。
- 共通ログ基盤は`operation`と通常・失敗イベントの意味を提供するが、具体的な組、観測点、イベント固有情報は各機能設計と機能側の閉じた型または同等の境界を正本とする。
- PythonでJSON変換失敗の経路が残る場合も、機能処理の失敗とは分離したログ基盤自身の失敗として扱い、元の機能エラーを上書きしない。
- 正確なPythonの型、関数、モジュール、プロジェクト設定、依存パッケージ、テストコマンドはコードと設定を正本とする。
- JSONオブジェクトの項目順に依存せず、Schema適合性と意味を検査する。
