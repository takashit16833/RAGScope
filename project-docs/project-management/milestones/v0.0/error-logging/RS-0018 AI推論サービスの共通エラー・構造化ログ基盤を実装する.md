# RS-0018 AI推論サービスの共通エラー・構造化ログ基盤を実装する

## 目的

RS-0014で定義した共通エラー契約と構造化ログを、Embedding生成以降のAI推論サービス実装から利用できる最小基盤として提供する必要がある。

このTicketでは、Pythonで発生した例外を安全な共通エラーへ変換する境界、構造化ログイベント、実行との関連情報、JSON出力、ローカル環境向けの出力処理、テスト用の出力処理を実装する。共通のJSON Schemaと検証用データ（fixture）へ適合させる一方、Webフレームワーク、モデル、Tokenizer、AIライブラリ固有の例外変換は後続の機能Ticketに残す。

## 前提

- [RS-0014 共通エラーと構造化ログを設計する](<./RS-0014 共通エラーと構造化ログを設計する.md>)が完了している
- `design/エラー設計.md`に、v0.0で実装する共通エラーの意味と公開境界が記載されている
- `design/構造化ログ設計.md`に、v0.0で実装するログ契約、AI推論サービスの責務境界、ローカル出力方針が記載されている
- 共通ログイベントのJSON Schemaと、Schemaへ適合する例・適合しない例を表す代表的な検証用データが作成されている

## 完了条件

### 例外を共通エラーへ変換する境界

- [ ] Pythonで発生した例外を共通エラーへ変換するための、機能固有のライブラリへ依存しない共通境界が実装されている
- [ ] 想定外の例外を、エラー分類`internal`の安全な共通エラーへ変換する処理が実装されている
- [ ] 利用者またはHTTP境界へ元の例外とスタックトレースを公開せず、内部原因と公開情報を区別できる

### 構造化ログと共通契約への適合

- [ ] 共通項目（Envelope）、実行との関連情報（Context）、イベント固有情報（Payload）、エラー情報（Error）を表現できるPythonの型または同等の境界が実装されている
- [ ] 1回の実行に属するログイベントとサービスの状態変化に属するログイベントを、`context.scope`と対応する構造によって区別できる
- [ ] ログイベント（`event`）、ログレベル（`level`）、コンポーネント（`component`）、処理種別（`operation`）、エラーコード、エラーの補助情報を設計に従って表現できる
- [ ] 各機能が定義した`operation`と`event`を閉じた型または同等の境界で表現し、任意の識別子を呼び出し側から渡せない
- [ ] 呼び出し元から渡された`execution_id`を、同じCLIコマンドに由来するAI推論サービスのログイベントへ引き継げる
- [ ] AI推論サービス自身が生成するサービスの状態変化を表すログイベントでは、設計に従って`execution_id`を持たない構造を扱える
- [ ] 構造化ログを、ログイベント1件につき1行のJSONへ変換できる
- [ ] AI推論サービスが出力するログイベントがJSON Schemaへ適合することを自動テストで確認できる
- [ ] 共通の適合例をJSON変換またはSchema適合テストの入力として利用し、不適合例が拒否されることを確認できる
- [ ] 該当しない任意項目が設計に従って省略され、異なるログイベントの項目を1つの大きなnullable構造へ集約していない

### 機能処理と出力処理の分離

- [ ] ローカル環境向けの出力処理が構造化ログを標準エラー出力へ出力し、正常なHTTPレスポンスの生成から分離されている
- [ ] 機能処理が具体的な標準エラー出力の処理へ直接依存せず、出力処理を差し替えられる
- [ ] 自動テストから出力したログイベントを検査できる、メモリへ保存する出力処理または同等のテスト用出力処理が実装されている
- [ ] 文書本文、プロンプト、秘密情報、認証情報など、設計で記録対象外とした情報を不用意に出力しない

### ログ出力が失敗した場合の挙動

- [ ] JSON変換の失敗と出力処理の失敗を設計どおりに扱い、元の処理種別の失敗をログ受付処理の失敗で上書きせず、失敗した出力処理へ再帰的にログイベントを書き込まない
- [ ] 失敗する出力処理を使用し、ログ受付処理が失敗した場合の挙動を自動テストで確認できる

### 設計反映と検証

- [ ] 共通エラーと代表的な構造化ログイベントについて、JSON出力、実行との関連情報、ログレベル、エラー情報、任意項目の扱いを自動テストで確認できる
- [ ] 実装で具体化または変更された現在設計が`design/エラー設計.md`と`design/構造化ログ設計.md`へ反映されている
- [ ] 実装、JSON Schema、検証用データ、両設計書に解消していない差異がない
- [ ] プロジェクトで定めたAI推論サービス側のテストコマンドを実行し、追加したテストを含めて成功する

## 対象外

- AI推論サービスのWebフレームワークとHTTPアダプターの実装
- リクエスト検証、HTTPステータス、エラーレスポンスの具体的な変換規則
- モデル、Tokenizer、AIライブラリ固有の例外変換
- Embedding、`reranking`、回答生成など、各機能固有のエラー分類、処理種別、ログ観測点、イベント固有情報の実装
- RAGScopeアプリケーション側の共通エラー型とログ受付処理の実装
- 再試行・タイムアウトの方針と実行機構
- CloudWatchへの送信、AWS SDKへの依存、ロググループや保持期間の設定
- 生存確認・準備完了確認エンドポイントのアクセスログ共通化
- 本格的な分散追跡（tracing）、性能集計、バッチ処理、非同期ジョブ固有の関連付け情報
- 独立した共通パッケージへの分離

## 実装メモ

- 最初はAI推論サービス内部に、責務の明確な共通モジュールとして実装する。利用実態が生じる前に独立したパッケージへ分離しない。
- 具体的なWebフレームワークやAIライブラリの例外は、RS-0003やRS-0007で機能固有のエラーコードと一緒に共通境界へ変換する。
- 元の例外とスタックトレースは公開レスポンスへ含めず、内部で記録する場合もエラー設計と構造化ログ設計の情報保護方針に従う。
- 共通ログ基盤は`operation`と`event`を含む共通構造を提供するが、具体的な組、観測点、イベント固有情報は各機能設計と機能側の閉じた型または同等の境界を正本とする。
- JSONオブジェクトの項目順に依存せず、Schema適合性と意味を検査する。
