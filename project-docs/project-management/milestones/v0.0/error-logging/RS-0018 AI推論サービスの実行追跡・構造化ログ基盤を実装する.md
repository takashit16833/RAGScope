# RS-0018 AI推論サービスの実行追跡・構造化ログ基盤を実装する

## 目的

AI推論サービスで、現在の[実行追跡・構造化ログ契約設計](../../../../design/実行追跡・構造化ログ契約設計.md)を成立させる最小の実行追跡・構造化ログ基盤を実装する。

RAGScopeの実行追跡はRAGScopeアプリケーションだけで完結しない。RAGScopeアプリケーションがAI推論サービスへ処理を依頼するときはTrace Contextを通信で引き継ぎ、AI推論サービス側でも同じ`TraceId`を使って呼び出し元`span`を親とする新しい`span`を開始し、同じ`trace`を継続する。AI推論サービス内部で、開始・終了、所要時間、エラーを独立して確認する必要がある処理は、各機能設計が定める範囲でさらに子`span`として追跡できるようにする。

構造化ログは実行追跡より広い。AI推論サービスの処理中に特定の`span`へ属するイベントは`TraceId`・`SpanId`を組で持つ構造化ログとして記録し、サービスの起動・終了など特定の利用者操作へ属さないイベントはTrace Contextを持たない構造化ログとして同じ基盤へ渡せるようにする。

このTicketでは、現在のAI推論サービス実装言語であるPythonに、共通契約を自然に表現する内部境界、OpenTelemetryによる実行追跡、構造化ログ生成、共有JSON Contractへの投影、差し替え可能な出力処理、自動テストの最小基盤を実装する。RAGScopeアプリケーションのHaskell型やmodule構成をPythonへ移植することは目的にしない。

正確なPythonの型、関数、module、依存package、設定、OpenTelemetry SDKの具体的な利用方法、テストケースは、実装時のコード・設定・テストを機械可読な正本とする。Markdownで長期的に管理すべきAI推論サービス固有の実行追跡責務や依存境界が実装時に生じた場合は、文書管理規約に従ってコンポーネント別の詳細設計が必要かをその時点で判断する。

## 前提

- [実行追跡・構造化ログ契約設計](../../../../design/実行追跡・構造化ログ契約設計.md)に、`trace`・`span`、Span Status、構造化ログ、`error_type`、コンポーネント間のTrace Context引き継ぎの共通契約が定義されている
- [構造化ログ外部表現共通設計](../../../../design/logging/構造化ログ外部表現共通設計.md)と[構造化ログJSON表現設計](../../../../design/logging/構造化ログJSON表現設計.md)に、RAGScopeが定める構造化ログ外部表現が定義されている
- `contracts/logging/v1/log-event.schema.json`と共有fixtureに、現在のJSON Contractが定義されている
- [ADR-0005 — 実行追跡をOpenTelemetryのtrace・spanで表現し、イベントを構造化ログとして記録する](<../../../../adr/ADR-0005 実行追跡をOpenTelemetryのtrace・spanで表現し、イベントを構造化ログとして記録する.md>)がacceptedである
- AI推論サービスのproduction Python実装はまだ存在しないため、旧Python実装の移行ではなく現在契約から最小基盤を実装する

## 完了条件

### AI推論サービスの最小実装・テスト基盤

- [ ] AI推論サービスのPythonコードと自動テストを正本リポジトリで管理できる最小のプロジェクト構成が作成されている
- [ ] モデル、Tokenizer、Webフレームワークを必要とせず、実行追跡と構造化ログの共通基盤を自動テストできる
- [ ] AI推論サービス側のテストまたは品質検査を再現可能に実行する入口が定義されている

### 実行追跡

- [ ] 呼び出し元から受け取ったTrace Contextを使って同じ`TraceId`の`trace`を継続し、呼び出し元`SpanId`で識別される`span`を親とするAI推論サービス側の新しい`span`を開始できる
- [ ] AI推論サービスが受け取った1回の処理依頼について開始した`span`を、処理結果が確定した境界で終了できる
- [ ] AI推論サービス内部で開始する子`span`が、現在の`span`を親として同じ`trace`に属する構造を実装できる
- [ ] 同じサービスプロセスで複数処理を並行実行してもcurrent Trace Contextを混在させない
- [ ] `span`が表す処理自身の最終結果に従ってSpan Statusを`Error`または`Unset`として扱い、`Error`の場合はその失敗理由の`error_type`を関連付けられる
- [ ] ログの重要度からSpan Statusを導出せず、Span Statusと構造化ログの重要度を独立して扱う
- [ ] Trace Contextの正確な通信項目・header・serialization方式をこのTicketだけで先行決定せず、通信方式を定義する設計または機械可読な契約を正本として利用する

### 構造化ログ

- [ ] AI推論サービスの構造化ログ1件を、発生時刻、発生元、イベント名、重要度、任意の`message`、任意の`attributes`、条件付きの`TraceId`・`SpanId`として扱える
- [ ] 特定の`span`中で記録するログはcurrent Trace Contextの`TraceId`・`SpanId`を組で持ち、片方だけを持つ内部状態を通常の生成経路で作らない
- [ ] AI推論サービスの起動・終了など、特定の利用者操作や`span`へ属さないイベントをTrace Contextなしで同じ構造化ログ基盤へ渡せる
- [ ] 失敗をログで報告する場合は`error_type`を通常の属性として記録でき、同じ失敗を`span`とログの両方へ記録する場合は同じ`error_type`を使用できる
- [ ] 子`span`の失敗が親へ伝播したことだけを理由に、同じ失敗ログを各階層へ重複して記録しない
- [ ] `execution_id`、`EventId`、`EventContext`、`OperationName`、通常イベントと失敗イベントの直和、固定`failed`イベント、重要度と失敗の結合など、現在契約が採用しない旧論理モデルをAI推論サービス基盤の前提にしない

### JSON変換と出力境界

- [ ] AI推論サービスが生成する構造化ログを現在の共有JSON Contractへ投影できる
- [ ] JSON出力が`contracts/logging/v1/log-event.schema.json`へ適合することを自動テストで確認できる
- [ ] trace内ログ、trace外ログ、`trace_id`・`span_id`片方だけの不正表現を含む共有fixtureをAI推論サービス側の検証入力として利用できる
- [ ] ローカル環境向け出力では1ログ1JSON objectを1物理行のUTF-8として標準エラー出力へ出力し、利用者へ返す正常な出力と混在させない
- [ ] 構造化ログの受付境界を標準エラー出力へ直接固定せず、テストから出力先を差し替えて完成したログを検査できる
- [ ] ログ基盤自身の失敗を、失敗した同じログ経路へ再帰的に記録しない

### 情報保護

- [ ] 文書本文、文書チャンク本文、回答生成用プロンプト、Embedding、秘密情報、認証情報、通信本文・header全文、元の例外メッセージ、スタックトレースなど、記録を明示的に許可していない情報を構造化ログへ不用意に出力しない
- [ ] 機能固有の安全な属性、イベント、`error_type`は、その機能を所有する設計・実装が定め、共通基盤が任意に決定しない

### 正本と検証

- [ ] AI推論サービス固有の正確な型、関数、module、設定、依存関係、OpenTelemetry SDK利用方法、具体的なテストケースをコード・設定・テストの正本で確認できる
- [ ] 実装によって共通の実行追跡・構造化ログ契約や共有JSON Contractを変更する必要が生じた場合は、責務を持つ正本へ同じ作業で反映されている
- [ ] AI推論サービス実装、共有JSON Contract、共通設計の間に未解消な差異がない
- [ ] プロジェクトで定めたAI推論サービス側のテストまたは品質検査を実行し、追加したテストを含めて成功する

- RAGScopeアプリケーションとAI推論サービスの具体的な通信プロトコル、endpoint、Trace Context伝播形式を、このTicket単独で決定すること

## 実装メモ

- AI推論サービスでは、RAGScopeアプリケーションの`Tracing m`、Cabal package構成、Haskell固有の型クラスをそのまま再現しない。共有するのはシステム全体の実行追跡・構造化ログ契約と外部Contractである。
- Python側のcurrent Trace Context管理は、並行処理で別の依頼のContextを混在させないことを満たす実装を選ぶ。正確な機構はコードと依存packageを確認して実装時に確定する。
- AI推論サービスで受け取った処理依頼を表す`span`と、その内部処理の子`span`の具体的な名称・粒度は、対象機能が実際に利用するときに機能設計と実装で決める。
- 構造化ログのJSON項目構造をPython内部型の設計理由にせず、内部表現からserialization境界で共有JSON Contractへ投影する。
