# v0.0 共通エラーと構造化ログによる実行追跡

## 能力

v0.0の各処理が、失敗を正常結果と区別できる共通エラー契約を利用し、処理の進行と失敗を共通形式の構造化ログとして出力できる。

ローカル実行では、利用者へ返す正常出力とログを分離し、同じ実行に関係するログイベントと失敗原因を識別して確認できる。

## Milestoneでの役割

### 機能実装より先に共通化する理由

v0.0では、文書読み込み、AI推論サービスとの通信、PostgreSQL処理などを順次実装する。各機能が独自のエラー表現やログ形式を作ると、後続機能での追跡と保守が難しくなり、共通化時に広範囲な修正が必要になる。

### このEpicで整えるもの

このEpicでは、文書処理の実装へ着手する前に、共通エラーと構造化ログの現在設計を定める。構造化ログをJSONへ変換したときの項目構成をJSON Schemaとして定義し、代表的な検証用データ（fixture）を作成する。あわせて、契約を利用する各コンポーネントから利用できる最小基盤を実装する。

### 後続機能へ委ねるもの

各機能で発生する具体的なエラー、出力するログイベント、HTTPやPostgreSQLとの境界への適用は、関係する機能設計と実装Ticketで具体化する。

再試行・タイムアウトはログとは別の実行制御として扱い、このEpicでは処理種別（`operation`）ごとの方針や実行機構を実装しない。

## 完了条件

### 共通契約と設計

- [ ] 共通エラー契約と構造化ログの現在設計が、それぞれの機能別設計書として定義されている
- [ ] 共通契約として共有する意味と、コンポーネントごとに実装する責務が区別されている
- [ ] 内部エラー、利用者向けのエラー表示、HTTPなどの境界で受け渡す失敗、構造化ログイベントの責務が区別されている
- [ ] 構造化ログをJSONへ変換したときの項目構成がJSON Schemaとして定義され、共通項目、エラー分類（`category`）、`context.scope`の構造、エラーコードの形式を機械的に検証できる
- [ ] Schemaへ適合する例・適合しない例を表す代表的な検証用データを、契約を利用する各実装から共通入力として利用できる

### コンポーネントごとの最小基盤

- [ ] 契約を利用する各コンポーネントから、共通エラーと構造化ログを利用できる最小基盤が実装されている

### ローカル出力と実行追跡

- [ ] ローカル実行で、正常なCLI出力・HTTP応答とログを分離できる
- [ ] 1回のコマンド実行内でコンポーネント境界を越えて同じ`execution_id`を引き継ぎ、処理の開始・成功・失敗を確認できる
- [ ] 1回の実行に属するログイベントと、サービスの状態変化に属するログイベントを、共通契約に従って区別できる
- [ ] ログ受付処理自身が失敗した場合も、元の処理結果と失敗原因を共通設計に従って扱える

### 検証と後続機能への引き渡し

- [ ] 契約を利用する各実装で、JSON Schema、検証用データ、主要な異常系を自動テストまたは実行によって確認できる
- [ ] 後続の機能設計が、共通契約を参照して機能固有のエラーとログを定義できる境界が提供されている
