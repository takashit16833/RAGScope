# v0.0 共通エラーと構造化ログによる実行追跡

## 能力

v0.0の各処理について、処理が成立しなかった理由を`error_type`で識別し、**利用インターフェースが受け付けた1回のトップレベルな操作を1つの`trace`として追跡し、その中でユースケース実行と必要な内部処理を`span`として追跡できる**。RAGScopeで起きた意味のある出来事は共通契約に従う構造化ログとして記録し、特定の`span`中で起きたログは`TraceId`・`SpanId`でその`span`へ関連付け、コンポーネントの起動・終了など特定の`span`へ属さないログはTrace Contextなしで記録できる。

ローカル実行では、利用者へ返す正常なCLI出力・HTTP応答とログを分離する。1回の利用者操作に属する処理と出来事は同じ`trace`として関連付けて確認でき、trace外の構造化ログは特定の利用者操作へ誤って関連付けない。

## Milestoneでの役割

### 機能実装より先に共通化する理由

v0.0では、文書読み込み、AI推論サービスとの通信、PostgreSQL処理などを順次実装する。各機能が独自の失敗理由の識別方法、実行追跡方法、ログ形式を作ると、後続機能での追跡と保守が難しくなり、共通化時に広範囲な修正が必要になる。

### このEpicで整えるもの

このEpicでは、`error_type`、`trace`・`span`、構造化ログの共通論理契約と、RAGScopeが定める外部表現の共通規則・JSON表現を定める。実行追跡では、1回のトップレベルな利用者操作を1つの`trace`とし、そのroot `span`の配下でユースケース実行と必要な内部処理を子`span`として扱う。構造化ログは`trace`より広い概念とし、Trace Contextの存在・不存在を含めて共通契約で扱う。

構造化ログをJSONへ変換したときの正確な項目、型、必須条件、文字列形式はJSON Schemaとして定義し、代表的な検証用データ（fixture）を作成する。あわせて、この契約を利用する各コンポーネントの最小基盤を実装する。

共通の意味と外部表現を、各コンポーネント固有の内部型、発生元の値、OpenTelemetry利用方法、ログ受付・出力境界、設定、ログ基盤自身の失敗処理から分離し、後者はコード・設定・Schema・テストなどの正本で具体化する。

### 後続機能へ委ねるもの

各機能で使用する具体的な子`span`、ログイベント、属性、`error_type`、それらの記録条件は、関係する機能設計と実装Ticketで具体化する。RAGScope API・RAGScope CLI固有の具体的なrouting・command判定・入力検証・結果処理イベントや利用者へ返す具体的な失敗表現、コンポーネント固有の具体的なライフサイクルイベント、コンポーネント間でTrace Contextを受け渡す具体的な通信形式も、それぞれの責務を持つ設計・契約・実装へ委ねる。

再試行・タイムアウトはログとは別の実行制御として扱う。具体的な対象、条件、試行回数、待機方法、タイムアウト範囲は関係する機能設計と実装Ticketで定め、このEpicでは利用箇所のない汎用的な実行機構を先行実装しない。

## 完了条件

### 共通契約と外部表現

- [ ] `error_type`、`trace`・`span`、Span Status、構造化ログ、イベント、重要度、属性、`TraceId`・`SpanId`の意味と関係が、実装技術に依存しない共通契約として定義されている
- [ ] 1回のトップレベルな利用者操作を1つの`trace`として扱い、root `span`が利用インターフェース固有処理からユースケース前後までの操作全体を追跡し、ユースケース実行を必要に応じて子`span`として追跡する契約が定義されている
- [ ] 構造化ログはtrace内外のイベントを扱え、特定の`span`へ属するログだけが`TraceId`・`SpanId`を組で持ち、特定の`span`へ属さないログは両方を持たない契約が定義されている
- [ ] 機能固有の子`span`、イベント、属性、`error_type`、利用インターフェース固有イベント、コンポーネント固有ライフサイクルイベントと、コンポーネント固有の実装情報について、共通契約との責務分担が明確になっている
- [ ] RAGScopeが定めるnon-OTLP外部表現で共通する項目名と値表現、およびJSON固有の階層・値型・省略規則・出力単位が定義されている
- [ ] 構造化ログの現在のJSON表現がJSON Schemaとして定義され、正確な項目、型、必須条件、文字列形式を機械的に検証できる
- [ ] Schemaへ適合する例・適合しない例を表す代表的な検証用データを、契約を利用する各実装から共通入力として利用できる

### コンポーネントごとの最小基盤

- [ ] 契約を利用する各コンポーネントで、`trace`・`span`による実行追跡と、trace内外の構造化ログを扱える最小基盤が実装されている
- [ ] 特定の`span`へ属する構造化ログは`TraceId`・`SpanId`で対応する`span`へ関連付けられ、trace外ログへ不要なTrace Contextを要求しない
- [ ] 各コンポーネント固有の正確な内部型、発生元の値、ログ受付・出力境界、設定、ログ基盤自身の失敗処理が、共通設計へ重複せずコード・設定・Schema・テストなどの正本で管理されている

### ローカル出力と実行追跡

- [ ] ローカル実行で、正常なCLI出力・HTTP応答と構造化ログを分離できる
- [ ] 利用インターフェースが受け付けた1回のトップレベルな操作について、RAGScopeアプリケーションとAI推論サービスのコンポーネント境界を越えて同じ`trace`を継続できる
- [ ] RAGScope Applicationがユースケースを呼び出した場合、その実行を利用者操作のroot `span`配下の子`span`として追跡でき、ユースケースを呼び出さず操作が終了する場合にもroot `span`だけで操作全体を追跡できる
- [ ] Trace Contextを持つ構造化ログの`TraceId`・`SpanId`から、そのイベントが起きた`span`を関連付けて確認できる
- [ ] 処理が成立しなかった理由を`error_type`で識別でき、同じ失敗を`span`と構造化ログの両方へ記録する場合に同じ`error_type`を使用できる

### 検証と後続機能への引き渡し

- [ ] 契約を利用する各実装で、JSON Schema、検証用データ、主要な正常系・異常系を自動テストまたは実行によって確認できる
- [ ] 後続の機能設計、利用インターフェース設計、コンポーネント実装が、共通契約を参照してそれぞれが所有する子`span`、イベント、属性、`error_type`を定義できる境界が提供されている
