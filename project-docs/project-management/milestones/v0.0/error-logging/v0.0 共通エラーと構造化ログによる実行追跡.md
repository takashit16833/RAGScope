# v0.0 共通エラーと構造化ログによる実行追跡

## 能力

v0.0の各処理について、処理の進行と失敗を後から確認でき、RAGScopeアプリケーションとAI推論サービスのコンポーネント境界を越えた一連の処理を追跡できる。

ローカル実行では、利用者へ返す正常なCLI出力・HTTP応答とTelemetryを分離し、処理の流れと、その途中で記録した出来事を関連付けて確認できる。

## Milestoneでの役割

### 機能実装より先に共通化する理由

v0.0では、文書読み込み、AI推論サービスとの通信、PostgreSQL処理などを順次実装する。各機能が独自の実行追跡方法やログ記録方法を作ると、後続機能での追跡と保守が難しくなり、共通化時に広範囲な修正が必要になる。

### このEpicで整えるもの

このEpicでは、OpenTelemetry Trace / Logsを前提に、RAGScopeで必要な実行追跡と構造化ログの全体アーキテクチャを定め、契約を利用する各コンポーネントの最小基盤を実装する。

OpenTelemetryへ委ねる責務とRAGScopeが所有する意味・型・契約の境界、`trace`・`span`とログの役割分担、失敗の扱い、Telemetry基盤自身の失敗、ローカルでの確認方法、JSON / SQLiteなど外部表現をRAGScopeがどこまで所有するかは、[RS-0023](<./RS-0023 OpenTelemetry Logsを前提に実行追跡・構造化ログアーキテクチャを再設計する.md>)で現在設計を前提にせず再設計する。

### 後続機能へ委ねるもの

各機能で使用する具体的な子`span`、ログイベント、属性、失敗理由の表現、それらの記録条件は、関係する機能設計と実装Ticketで具体化する。RAGScope API・RAGScope CLIで利用者へ返す具体的な失敗表現や、コンポーネント間で実行追跡に必要な情報を受け渡す具体的な通信形式も、それぞれのインターフェースまたは通信方式を定義する設計・契約へ委ねる。

再試行・タイムアウトはTelemetryとは別の実行制御として扱う。具体的な対象、条件、試行回数、待機方法、タイムアウト範囲は関係する機能設計と実装Ticketで定め、このEpicでは利用箇所のない汎用的な実行機構を先行実装しない。

## 完了条件

### 実行追跡・構造化ログアーキテクチャ

- [ ] RAGScope要求定義と現在のシステム構造から、後から識別・確認する必要がある処理、出来事、失敗、コンポーネント間の関係が特定されている
- [ ] OpenTelemetry Trace / Logsへ委ねる責務と、RAGScopeが所有する意味・型・契約の境界が決定されている
- [ ] `trace`・`span`と構造化ログの役割分担、失敗のTelemetryへの反映、Telemetry基盤自身の失敗時の扱いが決定されている
- [ ] ローカルでTelemetryを確認する方法と、Exporter / Collector / backend、JSON / SQLiteなど保存・外部表現をRAGScopeがどこまで所有するかが決定されている
- [ ] 関係するADR・設計書・Contract・プロジェクト管理文書が、採用したアーキテクチャと整合している

### コンポーネントごとの最小基盤

- [ ] 契約を利用する各コンポーネントで、採用したアーキテクチャに従う実行追跡と構造化ログを扱える最小基盤が実装されている
- [ ] 各コンポーネント固有の正確な内部型、発生元の値、Telemetry受付・出力境界、設定、基盤自身の失敗処理が、共通設計へ重複せずコード・設定・Schema・テストなどの正本で管理されている

### ローカル出力と実行追跡

- [ ] ローカル実行で、正常なCLI出力・HTTP応答とTelemetryを分離できる
- [ ] 1回のユースケース実行について、RAGScopeアプリケーションとAI推論サービスのコンポーネント境界を越えて一連の処理を追跡できる
- [ ] 記録した構造化ログを、対応する実行追跡情報と関連付けて確認できる

### 検証と後続機能への引き渡し

- [ ] 契約を利用する各実装で、主要な正常系・異常系を自動テストまたは実行によって確認できる
- [ ] 後続の機能設計が、共通アーキテクチャを参照して機能固有の子`span`、ログイベント、属性、失敗理由の表現を定義できる境界が提供されている
