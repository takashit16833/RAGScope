# RS-0020 共通エラー・構造化ログの論理契約を再設計する

## 目的

現在の共通エラー・構造化ログ設計は、Haskell実装、JSON外部表現、CLI実行を具体化する過程で段階的に形成されている。設計文書を整理する中で、`execution_id`をCLIコマンド単位とすること、`execution`と`service`でログの文脈を分類すること、通常イベントと失敗イベントの関係、共通エラーの構造などが、RAGScopeが必要とする意味そのものではなく、既存の実装や外部表現から決まっている可能性が明確になった。

RAGScopeの要求にはCLIとAPIの両方から主要処理を実行すること、および処理の進行・失敗・関連する実行を追跡できることが含まれる。本Ticketでは、既存のHaskell型、Python型、JSON Schema、現在のログ・エラー設計を新しい論理モデルの前提とせず、要求、システム境界、外部標準を入力として、共通エラー、構造化ログ、処理の関連付けに必要な論理契約を再設計する。

論理契約を確定した後に初めて既存設計、ADR、Contract、実装と比較し、維持する判断と置き換える判断を確定する。JSONと性質の異なるTSVへの投影も試作し、特定の外部表現の都合が論理契約へ入り込んでいないことを検証する。

## 完了条件

- [ ] RAGScopeが共通エラー、構造化ログ、処理の関連付けから確認する必要がある事実が、既存の型・Schema・外部表現に依存せず整理されている
- [ ] ログ1件が表す事実、生成元、重要度、出来事、エラー情報、処理間の関連付けについて、外部表現に依存しない論理契約が定義されている
- [ ] CLI・APIなどの入口、RAGScope上の一連の処理、個々のHTTP request、コンポーネントのライフサイクルを同一概念として扱うか分離するかが、それぞれの追跡目的に基づいて決定されている
- [ ] ログの重要度、出来事、処理の失敗、エラー情報の関係が、現在の通常イベント・失敗イベントの直和を前提とせず再評価されている
- [ ] 共通エラーの論理契約と、CLI表示・HTTPエラー表現など利用境界ごとの表現の責務が分離されている
- [ ] 論理契約をJSONとTSVへ投影する試作を行い、投影結果と形式固有の制約をExperimentとして記録している
- [ ] TSVは本番利用する外部形式として要求せず、JSON固有の構造が論理契約へ入り込んでいないことを検証するために使用している
- [ ] 新しい論理契約と、既存の共通エラー設計、構造化ログ設計、JSON表現設計、関連ADR、JSON Schema、Haskell・Python実装との差分が整理されている
- [ ] 維持する設計判断と置き換える設計判断が確定し、必要な設計書とADRが現在設計へ更新されている
- [ ] ContractやHaskell・Python実装の変更が本Ticketへ自然に収まらない場合は、必要な後続Ticketが正本として作成され、設計変更だけを未追跡の実装課題として残していない
- [ ] 要求、現在設計、ADR、機械可読な契約の間に、本Ticketで扱う範囲の未解消な矛盾がない

## 対象外

- RAGScope CLIまたはRAGScope APIの機能そのものを完成させること
- OpenTelemetry Collector、CloudWatch、分散トレーシング基盤などの運用基盤を導入すること
- TSVを本番の構造化ログ出力形式としてサポートすること
- 共通エラー、構造化ログ、処理の関連付けと無関係な設計書・実装を一括して書き直すこと
- 再設計の結果として必要になる大規模なHaskell・Python実装変更を、作業単位を分けず本Ticketへ含めること

## 実装メモ

### 手順1〜3の参照範囲

本Ticketの手順1〜3では、既存モデルへ新しい意味を後付けしないため、論理契約の設計と投影検証の入力を、RAGScope要求定義、システムアーキテクチャ、`project-docs/`の管理規約・作業ルール、本Ticket、外部標準に限定する。

手順4で既存設計との比較を開始するまでは、隔離した既存のエラー・構造化ログ設計本文、関連ADRの具体的な設計判断、ContractおよびJSON Schemaの具体的な構造、Haskell・Pythonのログ・エラー実装を、新しい論理契約の設計材料として確認しない。

隔離対象の決定、存在・配置・参照関係の確認に必要な場合は、ファイル名、配置、リンク関係など、設計内容そのものを取り込まない範囲だけ確認してよい。

この参照制限はRS-0020の手順1〜3だけに適用し、通常のRAGScope文書作業ルールを変更しない。

### 隔離中のリンク

手順1で隔離対象を作業branchから一時的に取り除いた結果、その文書を参照していたリンクは、手順5で新しい現在設計を反映するまで一時的な不整合として扱う。リンクを成立させる目的だけで旧設計を復元したり、ADRや仮文書へ参照先を付け替えたりしない。手順6の最終整合性確認までに解消する。

### 外部標準と作業順序

外部標準の調査対象には、少なくともOpenTelemetry Log Data Model、W3C Trace Context、RFC 5424、RFC 9457を含める。標準をそのまま採用することを前提とせず、RAGScopeが必要とする意味と責務を区別するための比較対象として使用する。

作業は次の順序を基本とする。

1. 再設計対象の既存エラー・ログ設計を作業branch上から一時的に取り除き、新しい論理モデルの入力にしない状態を作る。ADRは判断履歴として削除しない。
2. 要求と外部標準から、RAGScopeが必要とする共通エラー・構造化ログ・関連付けの論理契約を設計する。
3. 論理契約をJSONとTSVへ独立に投影し、表現固有の構造が論理契約へ入り込んでいないか検証する。
4. 新しい論理契約を既存設計、ADR、Schema、実装と比較し、維持・置換・後続作業を決める。
5. 現在設計とADRを新しい判断へ更新し、必要な後続Ticketを作成する。
6. 正本間の整合性を最終確認し、本Ticketの結果を記録する。

## 結果

完了時に、確定した論理契約、置き換えた設計判断、検証した外部表現、更新した正本、後続Ticket、確認結果を記録する。
