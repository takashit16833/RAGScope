# RS-0020 共通エラー・構造化ログの論理契約を再設計する

## 目的

共通エラーと構造化ログの設計を見直す中で、その部分だけを切り出して再設計すると、RAGScope全体で使っている用語、データのまとまり、識別子、処理の境界、コンポーネントの責務などを、現在の設計のまま前提にしてしまうことが分かった。ある設計の概念を説明するために別の設計へ遡ったとき、同じ言葉が異なる粒度で使われていたり、概念の境界が明確でなかったりすれば、エラーや構造化ログだけを正しく設計してもRAGScope全体として一貫した設計にはならない。

本Ticketでは、エラー・構造化ログだけを隔離して再設計するのではなく、まず`project-docs/design/`にある現在の設計をすべて見直す。RAGScope概要、要求定義、現在の文書・プロジェクト管理規約、関連するADR・Experiment、コード、JSON Schema、OpenAPI、migration、テスト、設定などを、それぞれが正本とする情報に応じて確認し、現在の設計に残っている曖昧な用語、責務の重複、概念のずれ、正本との矛盾を整理する。

既存の設計書や実装を、そのまま正しい前提として採用しない。一方で、既存内容をいったん無視して別のモデルを作ることもしない。現在の正本を横断して、どの情報をどこで定義すべきかを確認し、必要な修正をその情報の正本へ反映する。

`error_type`、構造化ログ、処理追跡の再設計は、この全体レビューの一部として行う。現在の作業branchで作成・更新した契約設計も中間成果として扱い、RAGScope全体の設計を確認した後に改めて妥当性を確認して確定する。

実行追跡の境界を決めるため、構造化ログ・実行追跡に必要な範囲で、利用者がRAGScopeに対して行うトップレベルな操作と、その1回の実行を構成する主要な処理の境界をユースケース設計として整理する。RAGScopeの全ユースケースを網羅すること自体は本Ticketの目的とせず、現在の構造化ログ・実行追跡を成立させるために必要な範囲を扱う。

本Ticketでは最終的に、`error_type`を含む`実行追跡・構造化ログ契約設計`、`構造化ログ外部表現共通設計`、`構造化ログJSON表現設計`、`構造化ログSQLite表現設計`を、それぞれの責務が重複しない現在設計として成立させる。各コンポーネントの正確な内部型、発生元の値、ログ受付・出力の境界、設定、ログ基盤自身の実装固有の失敗処理は、コード、設定、Schema、テストなどを正本とし、内容を重複させる`RAGScopeアプリケーション構造化ログ設計`と`AI推論サービス構造化ログ設計`は作成しない。

## 実装メモ

### 見直しの対象と情報源

`project-docs/design/`の設計書をすべて見直し対象とする。設計書だけを読んで設計書同士を合わせるのではなく、確認する事実に応じて次の正本へ遡る。

| 確認すること | 主な正本 |
|---|---|
| RAGScopeの目的と価値 | RAGScope概要 |
| RAGScopeが満たすこと | RAGScope要求定義 |
| RAGScope固有の用語と概念間の基本関係 | RAGScope用語集 |
| 文書の配置・責務・正本の分担 | `project-docs/rules/`の現行規約 |
| システム全体の構成とコンポーネントの責務 | システムアーキテクチャ |
| 利用者のトップレベルな操作と一連の処理境界 | ユースケース設計 |
| 現在採用している機能設計 | `project-docs/design/`の各設計書 |
| 重要な判断の理由と履歴 | 関連するADR |
| 実際に検証した事実 | 関連するExperiment |
| 正確な型、項目、制約、動作 | コード、JSON Schema、OpenAPI、migration、テスト、設定など |

既存の設計書、ADR、実装、外部表現のいずれか一つへ無条件に合わせない。食い違いを見つけた場合は、その情報をどの正本が持つべきかを先に確認してから修正する。

現行仕様に未採用の将来設計候補は、通常の見直し材料として使用しない。将来Milestoneまたは未採用候補そのものを検討する必要が生じた場合だけ、RAGScopeの作業ルールに従って確認する。

### 作業順序

1. `project-docs/design/`に存在する設計書と設計索引を列挙し、それぞれが答える問いと責務を確認する。
2. RAGScope概要、要求定義、システムアーキテクチャを確認し、システム全体で共有する用語、コンポーネント、データ、処理の境界を整理する。
3. 各機能設計を、関連するADR、Experiment、コード、Schema、OpenAPI、migration、テストなどと照合し、設計上の事実、正確な実装定義、判断履歴を分ける。
4. 設計書をまたいで使う概念と用語を横断確認し、曖昧さ、重複、矛盾がある場合は、正本となる文書または機械可読な定義へ修正を反映する。
5. 構造化ログ・実行追跡に必要な範囲のトップレベルな操作を確認し、ユースケース設計として1回の実行境界と主要な処理フローを定義する。`ユースケース`をRAGScope固有の正式用語として扱う場合は、RAGScope用語集も同じ変更で整合させる。
6. ユースケース設計を踏まえて、`error_type`、構造化ログ、処理追跡の論理契約を再確認する。外部標準は、RAGScopeが採用する仕組みとの対応が必要な箇所だけ確認する。
7. 確定した論理契約と共通外部表現をJSONとSQLiteへそれぞれ投影して検証し、形式固有の都合が論理契約へ入り込んでいないことを確認する。
8. 新しい論理契約を既存設計、ADR、コード、Schemaなどと比較し、維持・置換・削除する内容と、後続Ticketへ分ける実装変更を整理する。
9. `error_type`を含む`実行追跡・構造化ログ契約設計`、`構造化ログ外部表現共通設計`、`構造化ログJSON表現設計`、`構造化ログSQLite表現設計`と、必要なADR・関連設計を現在仕様として成立する状態へ更新する。各コンポーネント固有の正確な内部型、出力境界、設定、ログ基盤自身の失敗処理はコード、設定、Schema、テストなどの正本へ置き、専用のコンポーネント別構造化ログ設計書は作成しない。
10. 更新後の正本を再度横断確認し、設計索引、相対リンク、Frontmatter、ADR、機械可読な定義との未解消な矛盾がないことを確認する。

### 既存設計・ADR・契約との差分整理

この節は現在仕様そのものを定義するものではなく、確定した論理契約を既存の設計判断・機械可読な契約・実装へ反映するための移行判断を記録する。現在仕様は設計書、ADR、Contract、コードなど、それぞれの責務を持つ正本で確定する。

#### 削除前の設計

| 対象 | 判断 | 移行上の扱い |
|---|---|---|
| `project-docs/design/共通エラー契約設計.md` | 削除を維持する | 今回の再設計では、処理が成立しなかった理由を独立した共通エラー値ではなく`error_type`として論理契約に置き、具体的な値を失敗条件を定義する各機能設計が正本とする。設計索引とシステムアーキテクチャもこの責務分担へ更新済みであり、要求上も独立した共通エラー契約を必要とする事実は確認できない。したがって削除前文書は復元・再構成しない。HTTP・CLIなど境界固有のエラー表現は、対応する設計と機械可読な契約で定める。 |
| `project-docs/design/実行追跡・構造化ログ契約設計.md` | 現在の`design/logging/`配下の契約設計で置換する | 1ログ1イベント、重要度と処理成否の分離、`trace`・`span`、ドメイン参照と実行追跡IDの分離などは維持されている。失敗ログに共通エラーの値を抱える構造や、通信媒体におけるTrace Contextの具体を共通ログ契約が所有する構造は現在の責務分担へ置き換える。 |

#### ADR

| ADR | 判断 | 理由 |
|---|---|---|
| ADR-0002 | `accepted`のまま維持する | 実装技術に依存しない共通の意味と、コンポーネント固有実装を分離する判断は現在も有効である。本文に残る`operation`や`execution_id`は採用時点の履歴として扱い、現在仕様は後続ADRと設計書を正本とする。 |
| ADR-0003 | `superseded`のまま維持する | 内部型をJSON構造へ合わせること自体を設計目標にする判断はADR-0004で置き換え済みである。外部表現を内部constructor名から独立させる考えは後続判断へ引き継がれている。 |
| ADR-0004 | `superseded`のまま維持する | `operation`と通常・失敗イベントの直和、失敗variantから固定`failed`イベントと`error` levelを導出する論理モデルはADR-0005で置き換え済みである。内部モデルと外部表現を別責務とする判断だけを維持する。 |
| ADR-0005 | `accepted`のまま維持する | `trace`・`span`による実行追跡、構造化ログをある時点のイベントとして扱うこと、重要度とSpan Statusを分離すること、`error_type`で失敗理由を識別することが現在の論理契約と一致する。 |

現時点の差分を説明するための新しいADRは不要である。ADR-0005が今回の主要な設計変更の理由を既に記録している。今後、現在の論理契約では表せない新しい重要判断が生じた場合だけ、別ADRの必要性を改めて判断する。

#### JSON Schemaとfixture

`contracts/logging/v1/log-event.schema.json`と既存fixtureは、`schema_version`、`event_id`、`context`、`execution_id`、`spec.operation`、固定的な`failed`イベント、失敗時の`error` objectなど、現在の論理契約とJSON表現設計が採用しない構造を契約としている。また、重要度は`debug`、`info`、`warn`、`error`までで、現在の論理契約が持つ`fatal`を表現しない。

一方、属性値で`null`を認めず、string・number・boolean・array・objectを再帰的に扱う部分は現在の属性値契約と共通する。この部分を既存Schemaの階層ごと維持するのではなく、新しいJSON表現の`attributes`へ対応する契約として再利用する。

したがって、既存Schemaとfixtureは現在のJSON表現へ**置換が必要**である。ただしJSON Contractは複数コンポーネントが共有する機械可読な正本であり、RAGScopeアプリケーションのHaskell実装とは別の変更理由を持つ。次の設計更新で、共有JSON Contractとfixtureを更新する独立した後続Ticketを作成する。

#### RAGScopeアプリケーションのHaskell実装

RS-0015で実装済みの`ragscope-logging`は、`ExecutionId`・`EventId`・`EventContext`・`OperationName`、通常イベントと失敗イベントの直和、`LogErrorCategory`・`ErrorCode`・`SafeMessage`を持つ旧論理モデルを現在も表現している。JSON backendも同じ構造を既存Schemaへ投影している。この部分はADR-0005と現在の論理契約へ**実装追随が必要**である。

追随では、少なくともTraceId・SpanIdによる関連付け、イベント名と重要度の独立、`fatal`を含む重要度、任意のmessage、attributes、失敗時の`error_type`属性へ移行し、`operation`、固定`failed`、重要度と失敗の結合、旧EventContextを現在のログ論理モデルから除く必要がある。`AppError`に残るcategory・code・message・contextなどは、共通エラー契約の確定を待つ対象とはせず、Haskell実装の移行で現在の`error_type`設計と各利用境界の責務に合わせて再評価する。

一方、共通ログ基盤をprivate sublibraryとして機能実装から分離すること、機能固有の閉じたイベントから共通ログへ変換する境界、時刻やSinkを注入するRuntime、JSON serializationをCoreから分離する境界、stderr・memoryなどSinkを差し替える構造、ログ基盤自身の失敗を同じ経路へ再帰的に記録しない方針は、新しい論理契約と衝突しないため維持候補とする。

RS-0015は完了済みTicketであり、履歴を現在用語へ書き換えない。Haskell実装の移行は、共有JSON Contractの更新とは別の後続Ticketとして作成する。

#### AI推論サービスのPython実装

正本リポジトリにはAI推論サービスのproduction Python実装はまだ存在せず、現在の`.py`ファイルはJSON・SQLite投影Experimentの試作だけである。RS-0018も`planned`であり、Python実装の移行対象は存在しない。

一方、RS-0018の目的・完了条件は、`Envelope`・`EventContext`・`EventSpec`、`execution_id`、`operation`、通常・失敗イベントの直和、既存v1 JSON Schemaへの適合を前提としており、実装前に現在の契約へ追随させる必要がある。したがってPythonについて別の移行Ticketは作らず、次の設計更新でRS-0018を現在の論理契約・JSON Contractを実装するTicketへ更新する。

#### 後続作業の境界

比較結果から、次の境界で作業を分ける。

1. 本Ticketの次の設計更新では、`error_type`を含む実行追跡・構造化ログ、共通外部表現、JSON・SQLite表現と、各コンポーネントのコード・設定・テストとの正本分担を現在仕様として確定し、ADRの状態と説明を最終確認する。
2. 同じ設計更新で、共有JSON Schemaとfixtureを現在のJSON表現へ更新する後続Ticketと、RAGScopeアプリケーションのHaskell実装を現在の`error_type`・実行追跡・構造化ログ契約へ追随させる後続Ticketを作成する。共有Contractとコンポーネント実装は別の正本・変更理由を持つため、1つの実装Ticketへまとめない。
3. RS-0018は実装未着手なので移行Ticketを追加せず、既存のplanned Ticketを現在の契約に合わせて更新してから実装する。
