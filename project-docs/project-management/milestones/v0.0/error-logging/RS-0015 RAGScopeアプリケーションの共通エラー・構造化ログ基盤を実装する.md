# RS-0015 RAGScopeアプリケーションの共通エラー・構造化ログ基盤を実装する

## 目的

RS-0014で定義した共通エラー契約と構造化ログを、文書処理以降のRAGScopeアプリケーション実装から実際に利用できる最小基盤として提供する必要がある。

このTicketでは、共通エラーの表現、構造化ログイベント、実行との関連情報、JSON出力、ローカル環境向けの出力処理、テスト用の出力処理をRAGScopeアプリケーションへ実装する。特定機能のエラーやログを作り込むのではなく、共通のJSON Schemaと検証用データ（fixture）へ適合し、RS-0011、RS-0001および後続機能が共通契約に従って具体化できる土台を完成させる。

## 前提

- [RS-0014 共通エラーと構造化ログを設計する](<./RS-0014 共通エラーと構造化ログを設計する.md>)が完了している
- `design/エラー設計.md`に、v0.0で実装する共通エラーの意味と公開境界が記載されている
- `design/構造化ログ基本設計.md`に、v0.0で実装する共通ログ契約とローカル出力方針が記載されている
- `design/構造化ログ詳細設計.md`に、Haskell側のコンポーネント境界、モジュール責務、依存方向、実行時の流れが記載されている
- 共通ログイベントのJSON Schemaと、Schemaへ適合する例・適合しない例を表す代表的な検証用データが作成されている

## 完了条件

### 共通エラーとログ構造

- [x] 設計に従った共通エラーのHaskell型と、正常結果から失敗を区別して扱うための境界が実装されている
- [x] 共通項目（Envelope）、実行との関連情報（Context）、イベント固有情報（Payload）、エラー情報（Error）を表現できる構造化ログのHaskell型が実装されている
- [x] 1回の実行に属するログイベントとサービスの状態変化に属するログイベントを、`context.scope`と対応する構造によって区別できる
- [x] ログイベント（`event`）、ログレベル（`level`）、コンポーネント（`component`）、処理種別（`operation`）、エラーコード、エラーの補助情報を設計に従って表現できる
- [x] 通常イベントと失敗イベントの生成経路が分かれ、失敗イベントでは`event = failed`、`level = error`、`error`必須が同じ生成経路で保証されている
- [x] 各機能が定義した`operation`と`event`を閉じた型で表現し、通常の機能処理から任意の識別子、ログレベル、任意のpayloadを渡せない
- [x] ログイベント1件を識別する情報と、同じローカル実行に属するログイベントを識別する`execution_id`を生成・引き継ぎできる

### コンポーネントとモジュールの境界

- [x] 共通ログ基盤が同一パッケージ内のprivate sublibraryとして分離され、main libraryからのみ一方向に依存している
- [x] 通常の機能処理、機能ログ定義、composition root、テストが、それぞれ用途に対応するFacadeを通して共通ログ基盤を利用している
- [x] 共通ログ基盤の内部モジュールと内部表現がmain libraryへ公開されていない
- [x] 機能固有の`operation`、`event`、`payload`、アプリケーションエラーから安全なログ情報への投影をmain library側が所有し、private sublibraryが機能モジュールへ逆依存していない

### JSON変換と共通契約への適合

- [x] 構造化ログを、ログイベント1件につき1行のJSONへ変換できる
- [x] RAGScopeアプリケーションが出力するログイベントがJSON Schemaへ適合することを自動テストで確認できる
- [x] 共通の適合例をJSON変換またはSchema適合テストの入力として利用し、不適合例が拒否されることを確認できる
- [x] 該当しない任意項目が設計に従って省略され、異なるログイベントの項目を1つの大きなnullable recordへ集約していない
- [x] 完成したログイベントからJSON値への変換がtotalな純粋変換として実装され、通常の入力値に対する回復可能なJSON変換失敗経路を持たない
- [x] JSON契約への不適合を、実行時の回復処理ではなく、型、変換テスト、Schema適合テストで検出できる

### 機能処理と出力処理の分離

- [x] ローカル環境向けの出力処理が構造化ログを標準エラー出力へ出力し、利用者へ返す正常結果を標準出力へ出力できる
- [x] 機能処理が具体的な標準エラー出力の処理へ直接依存せず、出力処理を差し替えられる
- [x] 自動テストから出力したログイベントを検査できる、メモリへ保存する出力処理または同等のテスト用出力処理が実装されている
- [x] 文書本文、秘密情報、認証情報など、設計で記録対象外とした情報を不用意に出力しない

### ログ出力が失敗した場合の挙動

- [x] 出力処理の失敗を元の機能処理の失敗と区別して扱い、元の失敗を上書きせず、失敗した出力処理へ再帰的にログイベントを書き込まない
- [x] JSON値の生成後に発生する標準エラー出力などのIO失敗をSinkの失敗として扱い、JSON変換失敗とは区別する
- [x] 失敗する出力処理を使用し、ログ受付処理が失敗した場合の挙動を自動テストで確認できる

- [x] 標準出力と標準エラー出力が混在しないことを、テストまたは代表的な実行によって確認できる

## 実装メモ

- 共通ログ基盤は、RAGScopeアプリケーションと同じパッケージ内のprivate sublibraryとして実装する。独立パッケージには分離しない
- 通常の機能処理、機能ログ定義、composition root、test-suiteに用途別のFacadeを提供し、低水準のイベント定義APIは機能ログ定義モジュールだけが使用する
- 正確なモジュール名、型名、コンストラクター、JSON項目名、export listは、設計との整合を保ちつつコードとCabal設定を正本とする
- 共通ログ基盤は`operation`と`event`を含む共通構造を提供するが、具体的な組、観測点、イベント固有情報は各機能設計と機能側の閉じた型を正本とする
- 機能処理は閉じた機能固有イベントをログ受付処理へ渡し、JSONへの変換、時刻付与、ID生成、出力先の処理を境界へ分離する
- ゴールデンテストを採用する場合は、時刻や生成IDなど、実行ごとに変化する値を安定して検査できる方法を用意する
- JSONオブジェクトの項目順に依存せず、Schema適合性と意味を検査する
- JSON値への変換はtotalな純粋変換とし、標準エラー出力などで発生するIO失敗だけをSinkの失敗として扱う

## 結果

### 実装した基盤

- アプリケーション共通エラー`AppError`と、機能処理結果・必須ログ記録結果を独立に保持して`AppAction`へ解釈する実行境界を実装した。
- 共通ログ基盤を同一パッケージ内のprivate sublibrary `ragscope-logging`として分離し、通常利用、機能ログ定義、production設定、テスト向けのFacadeを提供した。
- `LogEvent`をEnvelope、`context`、`spec`で構成し、通常イベントと失敗イベントの生成経路、ログレベル、エラー情報、optional fieldの不変条件を型と生成関数で表現した。
- JSON変換を`Backend.Json`、stderrへの1行出力とIO failure処理を`Backend.Stderr`へ分離し、`Setup`でproduction Sinkとして合成した。

### 利用できる出力処理と実行との関連情報

- productionでは構造化ログをstderrへ1イベント1行のJSONとして出力し、正常なCLI結果をstdoutと分離できる。
- `Sink`を差し替え可能とし、テストではメモリSink、常に失敗するSink、呼び出し回数を計測するfailure Sinkを利用できる。
- `ExecutionContext`では1回のCLI実行で共有する`execution_id`を保持し、`ServiceContext`ではサービス状態変化を表現できる。各ログイベントには個別の`event_id`とUTC時刻を付与する。

### 確認

- `make check`を実行し、Fourmoluのformat check、`cabal build all`、`cabal test all`、`cabal haddock all`が成功した。
- テストは66 examples、0 failures。valid / invalid fixtureとHaskell生成`LogEvent`のJSON Schema適合、JSON変換、実行結果合成、stdout / stderr分離、Sink failure時の挙動を確認した。
- 公開モジュールのHaddock coverageは100%を確認した。

### 設計への反映

- `構造化ログ基本設計.md`をADR-0003の`spec`構造、optional fieldの省略規則、totalなJSON変換、Sink failureの現在契約へ同期した。
- `構造化ログ詳細設計.md`を`Backend.Json`、`Backend.Stderr`、`Runtime`、`Setup`、`Execution.Result`、`Execution.Observation`の現在の責務境界と実行フローへ同期した。
- `エラー設計.md`へ、機能処理結果と必須ログ記録結果を独立に扱い、両方が失敗しても元の`AppError`を保持する実行結果合成の規則を反映した。

### 後続機能へ残る適用事項

- 各機能固有のエラーコード、`operation`、`event`、観測点、payload、安全な`AppError`からログ情報への投影は、各機能の設計と実装で具体化する。
- 同一CLI実行の`execution_id`をコンポーネント境界で引き継ぐ正確なHTTP表現は、後続のAPI設計とOpenAPIで具体化する。
- AI推論サービス側の共通エラー・構造化ログ実装は、対応する別Ticketで同じ共通契約へ適合させる。

### 既知の制約

- 再試行・タイムアウト、CloudWatch送信、本格的な分散追跡、PostgreSQLへの実験状態・エラー永続化は本Ticketの対象外である。
- Haddock生成時にprivate sublibraryや生成内部表現へのlink destination warningが残るが、ドキュメント生成は成功し、公開モジュールのcoverageは100%である。
