# RS-0015 RAGScopeアプリケーションの共通エラー・構造化ログ基盤を実装する

## 目的

RS-0014で定義した共通エラー契約と構造化ログを、文書処理以降のRAGScopeアプリケーション実装から実際に利用できる最小基盤として提供する必要がある。

このTicketでは、共通エラーの表現、構造化ログイベント、実行との関連情報、JSON出力、ローカル環境向けの出力処理、テスト用の出力処理をRAGScopeアプリケーションへ実装する。特定機能のエラーやログを作り込むのではなく、共通のJSON Schemaと検証用データ（fixture）へ適合し、RS-0011、RS-0001および後続機能が共通契約に従って具体化できる土台を完成させる。

## 前提

- [RS-0014 共通エラーと構造化ログを設計する](<./RS-0014 共通エラーと構造化ログを設計する.md>)が完了している
- `design/エラー設計.md`に、v0.0で実装する共通エラーの意味と公開境界が記載されている
- `design/構造化ログ設計.md`に、v0.0で実装するログ契約とローカル出力方針が記載されている
- 共通ログイベントのJSON Schemaと、Schemaへ適合する例・適合しない例を表す代表的な検証用データが作成されている

## 完了条件

### 共通エラーとログ構造

- [ ] 設計に従った共通エラーのHaskell型と、正常結果から失敗を区別して扱うための境界が実装されている
- [ ] 共通項目（Envelope）、実行との関連情報（Context）、イベント固有情報（Payload）、エラー情報（Error）を表現できる構造化ログのHaskell型が実装されている
- [ ] 1回の実行に属するログイベントとサービスの状態変化に属するログイベントを、`context.scope`と対応する構造によって区別できる
- [ ] ログイベント（`event`）、ログレベル（`level`）、コンポーネント（`component`）、処理種別（`operation`）、エラーコード、エラーの補助情報を設計に従って表現できる
- [ ] 各機能が定義した`operation`と`event`を閉じた型で表現し、任意の識別子を呼び出し側から渡せない
- [ ] ログイベント1件を識別する情報と、同じローカル実行に属するログイベントを識別する`execution_id`を生成・引き継ぎできる

### JSON変換と共通契約への適合

- [ ] 構造化ログを、ログイベント1件につき1行のJSONへ変換できる
- [ ] RAGScopeアプリケーションが出力するログイベントがJSON Schemaへ適合することを自動テストで確認できる
- [ ] 共通の適合例をJSON変換またはSchema適合テストの入力として利用し、不適合例が拒否されることを確認できる
- [ ] 該当しない任意項目が設計に従って省略され、異なるログイベントの項目を1つの大きなnullable recordへ集約していない

### 機能処理と出力処理の分離

- [ ] ローカル環境向けの出力処理が構造化ログを標準エラー出力へ出力し、利用者へ返す正常結果を標準出力へ出力できる
- [ ] 機能処理が具体的な標準エラー出力の処理へ直接依存せず、出力処理を差し替えられる
- [ ] 自動テストから出力したログイベントを検査できる、メモリへ保存する出力処理または同等のテスト用出力処理が実装されている
- [ ] 文書本文、秘密情報、認証情報など、設計で記録対象外とした情報を不用意に出力しない

### ログ出力が失敗した場合の挙動

- [ ] JSON変換の失敗と出力処理の失敗を設計どおりに扱い、元の処理種別の失敗をログ受付処理の失敗で上書きせず、失敗した出力処理へ再帰的にログイベントを書き込まない
- [ ] 失敗する出力処理を使用し、ログ受付処理が失敗した場合の挙動を自動テストで確認できる

### 設計反映と検証

- [ ] 共通エラーと主要な構造化ログイベントについて、JSON出力、実行との関連情報、ログレベル、エラー情報、任意項目の扱いを自動テストで確認できる
- [ ] 標準出力と標準エラー出力が混在しないことを、テストまたは代表的な実行によって確認できる
- [ ] 実装で具体化または変更された現在設計が`design/エラー設計.md`と`design/構造化ログ設計.md`へ反映されている
- [ ] 実装と両設計書に解消していない差異がない
- [ ] プロジェクトで定めたRAGScopeアプリケーション側のテストコマンドを実行し、追加したテストを含めて成功する

## 対象外

- 文書処理、Embedding生成、DB処理など、各機能固有のエラー分類、処理種別、ログ観測点、イベント固有情報の実装
- AI推論サービス側のエラー型とログ受付処理の実装
- HTTP APIの正確なエラーレスポンス
- 再試行・タイムアウトの方針と実行機構
- CloudWatchへの送信、AWS SDKへの依存、ロググループや保持期間の設定
- 本格的な分散追跡（tracing）、性能集計、バッチ処理、非同期ジョブ固有の関連付け情報
- 実験状態とエラーのPostgreSQLへの永続化
- 独立した共通パッケージへの分離

## 実装メモ

- 最初はRAGScopeアプリケーション内部に、責務の明確な共通モジュールとして実装する。利用実態が生じる前に独立したパッケージへ分離しない。
- 正確なモジュール名、型名、コンストラクター、JSON項目名は、設計との整合を保ちつつコードを正本とする。
- 共通ログ基盤は`operation`と`event`を含む共通構造を提供するが、具体的な組、観測点、イベント固有情報は各機能設計と機能側の閉じた型を正本とする。
- 機能処理は意味のある`operation`、`event`、イベント固有情報を渡し、JSONへの変換、時刻付与、ID生成、出力先の処理を可能な範囲で境界へ分離する。
- ゴールデンテストを採用する場合は、時刻や生成IDなど、実行ごとに変化する値を安定して検査できる方法を用意する。
- JSONオブジェクトの項目順に依存せず、Schema適合性と意味を検査する。
