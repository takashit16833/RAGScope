# RS-0005 PostgreSQLに文書チャンクとEmbeddingを保存するデータ構造を作成する

## 目的

v0.0で質問に近い文書チャンクをdense検索するためには、文書チャンクの本文と、その文書チャンクから生成したEmbeddingを、対応関係を保ったままPostgreSQLへ永続化できるデータ構造が必要である。

このTicketでは、RS-0012で作成したデータモデル設計に従い、ローカル環境のPostgreSQLでpgvector拡張を利用できるようにする。v0.0の検索対象となる文書チャンクとEmbeddingを保存する最小のDBスキーマを、正確な定義の正本となるマイグレーションとして作成する。

RAGScopeアプリケーションが実際の文書チャンクとEmbeddingを保存する処理はRS-0006で扱う。

## 前提

- [RS-0012 文書チャンクのEmbedding生成と保存を設計する](<./RS-0012 文書チャンクのEmbedding生成と保存を設計する.md>)が完了している
- [RS-0003 AI推論サービスで文書チャンクのEmbeddingを生成する](<./RS-0003 AI推論サービスで文書チャンクのEmbeddingを生成する.md>)が完了し、実際のベクトル次元を確認できる
- `design/データモデル設計.md`に、保存対象の責務、関係、不変条件が記載されている

## 完了条件

### PostgreSQLとマイグレーション

- [ ] ローカル環境でPostgreSQLを起動し、RAGScopeから接続するためのDBを用意できる
- [ ] 対象DBでpgvector拡張を有効化できる
- [ ] 空のDBへ適用できるマイグレーションとして、文書チャンクとEmbeddingを保存するDBスキーマが定義されている
- [ ] マイグレーションを空のDBへ適用し、必要なpgvector拡張とDBスキーマを再現できる

### 保存するデータと制約

- [ ] DB上の各検索対象チャンクについて、元文書を識別する情報、0始まりの`chunkIndex`、文書チャンク本文、対応するEmbeddingを保持できる
- [ ] 元文書を識別する情報と`chunkIndex`の組み合わせなど、データモデル設計で定めた方法によってv0.0の各文書チャンクを一意に識別できる
- [ ] Embedding列がRS-0003で確認した固定ベクトル次元に対応し、異なる次元のベクトルを保存できない
- [ ] 必須となる本文、元文書を識別する情報、`chunkIndex`、Embeddingが欠落した不完全な検索対象を保存できない
- [ ] `chunkIndex`に負の値を保存できない
- [ ] 文書チャンクとEmbeddingの一対一の対応を、単一レコードまたはDB制約によって維持できる
- [ ] HNSW / IVFFlatなどの近似検索インデックスが作成されていない

### 設計反映と検証

- [ ] DBスキーマの構造と制約をマイグレーションまたはDB結合テストで確認できる
- [ ] 正しい次元のベクトルを持つテストデータを保存でき、異なる次元、負の`chunkIndex`、必須項目欠落などの不正なデータが拒否されることを確認できる
- [ ] マイグレーションの実装結果に合わせて、データの責務、関係、不変条件が`design/データモデル設計.md`へ反映されている
- [ ] マイグレーションとデータモデル設計に解消していない差異がない
- [ ] プロジェクトで定めたマイグレーションまたはDBテストのコマンドを実行し、追加した確認を含めて成功する

## 実装メモ

- 正確なテーブル名、カラム名、型、主キー、外部キー、`unique`制約、`check`制約はマイグレーションを正本とする。
- Markdownの設計書にはDBスキーマを複製せず、保存対象の責務、文書チャンクとEmbeddingの関係、不変条件、後続Milestoneで拡張する境界を記載する。
- v0.0では、固定Markdown文書と固定チャンク条件、固定Embeddingモデルによる最小の検索対象だけを保存する。
- 文書チャンクとEmbeddingを同じテーブルへ保存するか、関連する複数のテーブルへ分けるかは、初期設計の責務と制約を満たす範囲でマイグレーションにより具体化する。
- Embedding列はRS-0003で確認したモデルの固定出力次元に合わせたpgvectorの`vector(n)`型とする。
- マイグレーションは、既存環境へ手作業でSQLを追加しなくても、定めたコマンドから再現できるようにする。
- DB接続情報やパスワードをソースコード、マイグレーション、Git管理対象の平文ファイルへ直接記載しない。
- 初期設計を変更する必要が生じた場合は、後続の保存・検索処理への影響を確認してから`データモデル設計.md`を更新する。
