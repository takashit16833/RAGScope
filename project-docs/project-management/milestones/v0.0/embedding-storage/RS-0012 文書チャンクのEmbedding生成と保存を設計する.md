# RS-0012 文書チャンクのEmbedding生成と保存を設計する

## 目的

このEpicでは、AI推論サービスによるEmbedding生成、RAGScopeアプリケーションとのHTTP / JSON通信、PostgreSQL / pgvectorのデータ構造、文書チャンクとEmbeddingの保存を複数の実装Ticketで構築する。これらは、採用するEmbeddingモデル、生成条件、API契約、ベクトル次元、保存するデータの関係を共有している。

このTicketでは、RS-0003からRS-0006へ着手する前に、文書チャンクのEmbedding生成から保存までの初期設計を行う。現在設計の正本としてEmbedding生成と保存に必要な機能設計を作成し、AI推論サービスの文書チャンクEmbedding生成APIについてOpenAPIなどの機械可読な初期定義を作成する。

RAGScopeアプリケーションからAI推論サービスへ処理を依頼するときは、[実行追跡・構造化ログ契約設計](../../../../design/実行追跡・構造化ログ契約設計.md)に従ってTrace Contextを通信で引き継ぎ、AI推論サービス側でも同じ`trace`を継続する。このTicketでは文書チャンクEmbedding生成APIの通信契約を設計するため、その通信でTrace Contextを渡す正確な場所、形式、必須条件、検証方法も機械可読な契約へ落とす。旧`execution_id`を新しい通信契約として維持しない。

文書チャンクEmbedding要求の具体的な再試行・タイムアウト方針と実行機構はRS-0016とRS-0017で別に設計・実装する。このTicketでは、後続設計が判断できるよう処理境界、副作用、主要な失敗、HTTP契約を定義するが、具体的な試行回数や待機方式は固定しない。

正確なRAGScopeアプリケーション・AI推論サービスの型、SQL、migrationは、それぞれのコード・OpenAPI・migrationなどの機械可読な正本で実装時に確定する。

- [ ] 文書用と質問用のEmbeddingを比較可能に保つ互換条件が記載されている
- [ ] 生存確認、推論可能状態、使用中のモデル・リビジョン・出力次元を確認する方法が設計されている

### API契約・Trace Context・失敗境界

- [ ] RAGScopeアプリケーションからAI推論サービスへ文書チャンクEmbeddingを要求する処理の開始・終了、1回のHTTPリクエスト、AI推論サービス側のEmbedding計算の境界が記載されている
- [ ] 文書チャンクEmbedding生成APIの入力、出力、入力とEmbeddingの対応方法、主要な失敗条件が設計されている
- [ ] RAGScopeアプリケーションがcurrent Trace Contextを通信へ載せ、AI推論サービスが受け取ったTrace Contextから同じ`TraceId`の新しい子`span`を開始する責務境界が記載されている
- [ ] Trace Contextを引き継ぐ正確な場所、形式、必須条件、検証方法と、欠落・不正な値の扱いがOpenAPIまたは対応する機械可読な通信契約に定義されている
- [ ] `execution_id`を現在の実行追跡識別子としてAPIへ残していない
- [ ] AI推論サービスの処理失敗、HTTP失敗、不正レスポンス、入力・契約違反を区別し、機能が所有する失敗理由を現在の`error_type`契約へ対応付ける方針が記載されている
- [ ] リクエスト検証、Webフレームワーク、モデル、Tokenizer、AIライブラリで発生する具体的な失敗のうち、この機能が扱うものと、それをどの境界で安全な外部表現へ変換するかが記載されている
- [ ] 文書チャンクEmbedding生成APIの正確なリクエスト・レスポンスがOpenAPIなどの機械可読な初期定義として作成されている

### 実行追跡・構造化ログとの境界

- [ ] 文書チャンクEmbedding生成で作成する具体的な子`span`とその`Error`条件を、機能設計で必要な範囲だけ定義している
- [ ] 機能固有のログイベント、属性、`error_type`を記録する場合は、[実行追跡・構造化ログ契約設計](../../../../design/実行追跡・構造化ログ契約設計.md)の共通規則に従って機能設計へ記載している
- [ ] AI推論サービス側の内部Tracing実装や構造化ログ基盤の共通責務を、この機能設計で再定義していない

### データモデルと保存

- [ ] 文書チャンクとEmbeddingを保存する最小のデータ構造について、保持する情報、責務、関係、不変条件が記載されている
- [ ] 元文書を識別する情報と`chunkIndex`によってv0.0の文書チャンクを一意に扱い、文書チャンク本文とEmbeddingの対応を維持する方針が記載されている
- [ ] Embedding列が選定モデルの固定出力次元と一致し、不完全な検索対象や負の`chunkIndex`を許可しない方針が記載されている
- [ ] 複数の文書チャンクを保存するtransaction境界と、Embedding生成中にDB transactionを保持しない方針が記載されている
- [ ] 同じ固定文書の取り込みを再実行した場合に、識別不能な重複を残さない初期方針が記載されている

### 再試行・タイムアウトとの境界

- [ ] 後続のRS-0016が再試行対象と再試行安全性を判断できるよう、処理の副作用と失敗時に成立する条件が記載されている

## 実装メモ

- モデル選定は精度比較ではなく、v0.0のローカル環境で実行できること、文書用と質問用のEmbeddingを互換に生成できること、リビジョンを固定できること、ライセンス上の問題がないことを満たす1モデルの確定を目的とする。
- 質問Embeddingの生成処理自体は後続Epicで実装するが、文書チャンクEmbeddingとの互換性を確保するため、質問用の入力規則はこの時点で設計する。
- OpenAPIの初期定義はRS-0003で実装する文書チャンクEmbedding生成の契約を対象とする。質問Embeddingに必要な契約は、後続Epicの初期設計Ticketで追加または更新する。
- データモデル設計にはmigrationを複製せず、保存対象の責務、関係、不変条件、transactionと再実行の方針を記載する。
- Trace Contextの通信表現は一般論から推測せず、このTicketで作成・更新する通信契約へ機械可読に定義する。
