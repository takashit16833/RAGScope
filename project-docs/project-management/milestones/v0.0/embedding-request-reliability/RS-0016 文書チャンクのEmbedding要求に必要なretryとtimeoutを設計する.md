# RS-0016 文書チャンクのEmbedding要求に必要なretryとtimeoutを設計する

## 目的

[ADR-0002](<../../../../adr/ADR-0002 共通実行基盤の契約とコンポーネント実装を分離する.md>)では、再試行を一時的失敗かつ再試行しても安全な場合だけ適用し、処理種別（`operation`）固有の方針と実装を具体的な利用箇所へ着手する段階で決定する方針を採用している。

このTicketでは、RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求する処理種別を最初の対象として、必要な再試行・タイムアウトの現在設計を`design/リトライ・タイムアウト設計.md`に定義する。RS-0012で設計したAPI契約と主要な失敗を基に、どの失敗を何の根拠で再試行するか、再実行しても安全な条件は何か、どの時間範囲を制限するかを明確にし、RS-0017とRS-0004が実装へ着手できる判断基準を整える。

## 前提

- [RS-0015 RAGScopeアプリケーションの共通エラー・構造化ログ基盤を実装する](<../error-logging/RS-0015 RAGScopeアプリケーションの共通エラー・構造化ログ基盤を実装する.md>)が完了している
- [RS-0012 文書チャンクのEmbedding生成と保存を設計する](<../embedding-storage/RS-0012 文書チャンクのEmbedding生成と保存を設計する.md>)が完了している
- `design/Embedding生成設計.md`と文書チャンクのEmbedding生成APIのOpenAPI初期定義から、処理種別の境界と主要な失敗を確認できる

## 完了条件

### 処理種別と再試行安全性

- [ ] `design/リトライ・タイムアウト設計.md`が`note_type: design`の機能設計書として作成されている
- [ ] 対象の処理種別が「RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求し、応答を受け取る処理」として明確に定義されている
- [ ] 1回の論理的な処理、1回の試行、HTTPリクエスト、AI推論サービス側のEmbedding計算の境界が区別されている
- [ ] この処理が永続的な外部副作用を生成しないこと、または再試行を安全に行うために必要な条件が記載されている
- [ ] 再試行の判断を共通エラー全体へ固定せず、この処理種別のエラー分類と実行Contextから決定する方針が記載されている

### 失敗分類と再試行方針

- [ ] 接続失敗、通信中断、タイムアウト、HTTPステータス、AI推論サービスの明示的な失敗、不正なJSON、契約違反、入力不正、ベクトル検証失敗などを、再試行対象と非対象へ分類する判断基準が記載されている
- [ ] 判断不能な失敗を安易に再試行対象へ含めない方針と、最終的に返すエラーの扱いが記載されている
- [ ] 最大試行回数が初回試行を含むかどうかと、試行上限へ達した場合の挙動が曖昧なく定義されている
- [ ] 待機方式、バックオフ、ジッター、最大待機、全体時間上限、HTTPレスポンスの再試行指示を扱うかどうかが、採否と理由を含めて定義されている
- [ ] 再試行方針の具体値と単位、設定の供給方法、v0.0で採用する初期値が記載されている

### タイムアウト

- [ ] タイムアウトを適用する範囲と種類、時間の起算点、タイムアウト発生時の中断・後処理・エラー変換が定義されている

### ログと実行追跡

- [ ] 再試行を予定した時、再試行後に成功した時、試行上限へ達した時、タイムアウトした時に出力する構造化ログイベントと必要な補助情報が定義されている
- [ ] 同じ論理的な処理に属する各試行を、v0.0の実行との関連情報を用いて追跡する方法が定義されている

### 実装境界・テスト・整合

- [ ] RS-0017が実装する実行機構の責務と、RS-0004が担当するHTTPリクエスト・レスポンス変換、Embedding対応検証の責務が区別されている
- [ ] 正常成功、一時的失敗後の成功、再試行しない失敗、試行上限到達、各タイムアウトを確認するテスト方針が記載されている
- [ ] テストが長い実待機や不安定な実時間へ過度に依存しないための境界が記載されている
- [ ] 後続の処理種別へ適用する際は、副作用と再試行安全性を個別に再評価することが明記されている
- [ ] バッチ処理・非同期ジョブやDB更新に固有の再実行・重複防止方式を、この処理種別へ先回りして導入していない
- [ ] 正確なHaskell型、関数、設定形式はコード、具体的なテストケースはテストコードを正本とすることが明記されている
- [ ] 所属EpicとEmbedding生成Epicの`関連文書`から`リトライ・タイムアウト設計.md`を参照できる状態になっている
- [ ] 関連する要求定義、システムアーキテクチャ、ADR、エラー・ログ設計、Embedding生成設計、OpenAPIに矛盾しないことを確認できる

## 対象外

- Haskellの実HTTPクライアントとリクエスト・レスポンス変換

- 分散追跡（tracing）の正確なSpan構造と処理間の関連付け規則
- CloudWatch固有の収集・監視設定

## 実装メモ

- 本設計は対象の処理種別に対する安全な実行制御を正本とし、一般的な再試行の解説書にはしない。
- 共通化はRS-0004で直ちに利用する範囲に限定し、将来の処理種別を想定した未使用の選択肢を増やさない。
- API固有のHTTPステータスとエラー内容はOpenAPI・Embedding生成設計を参照し、同じ定義を重複して正本化しない。
- 方針の値は根拠なく一般的な推奨値を採用せず、ローカルのAI推論サービス、モデル処理時間、v0.0の処理量を踏まえて決定する。
