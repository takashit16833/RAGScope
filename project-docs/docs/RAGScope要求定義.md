# RAGScope要求定義

> [!abstract] この文書の役割
> RAGScopeが満たすべき機能、品質、制約、対象範囲、対象外を定義する。  
> システムの目的と価値は[RAGScope概要](./RAGScope概要.md)、実現方法は[システムアーキテクチャ](./design/システムアーキテクチャ.md)、段階的な実現計画は[ロードマップ](../project-management/ロードマップ.md)を参照する。

## 1. 要求の前提

RAGScopeは、RAGの検索、回答生成、評価、実験管理を一連の流れとして扱い、評価結果を根拠に設計判断を説明できる状態を目指す。

本書では「何を満たすか」を定義する。コンポーネント、通信方式、データベース、型、ライブラリなどの実現方法は設計書または機械可読な実装を正本とする。

## 2. 機能要件

### 2.1 文書の取り込みと追跡

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-DOC-001` | Markdown / TXT形式の技術文書を取り込めること。 | 対象形式の文書を登録し、本文が保存されることを確認する。 |
| `REQ-DOC-002` | 文書を検索に使用する単位へ分割できること。 | 取り込んだ文書から複数の文書チャンクが生成されることを確認する。 |
| `REQ-DOC-003` | 各文書チャンクを、元文書、文書バージョン、元文書内の位置へ追跡できること。 | 文書チャンクから対応する元本文の範囲を特定できることを確認する。 |
| `REQ-DOC-004` | 文書、文書集合、分割条件をバージョンまたは識別可能な条件として管理できること。 | 異なる文書内容または分割条件を混同せず参照できることを確認する。 |
| `REQ-DOC-005` | 文書または分割条件を更新した場合、対応する検索用データを再生成できること。 | 更新前後のデータが識別され、更新後の条件で検索できることを確認する。 |

### 2.2 検索

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-RET-001` | キーワードを利用する全文検索をbaselineとして実行できること。 | 質問に対する順位付き検索結果を取得できることを確認する。 |
| `REQ-RET-002` | 文書と質問の意味的な近さを利用するdense検索を実行できること。 | 質問に対する順位付き検索結果を取得できることを確認する。 |
| `REQ-RET-003` | 全文検索とdense検索の結果を統合するhybrid検索を実行できること。 | 両方式の候補から統合された順位結果を取得できることを確認する。 |
| `REQ-RET-004` | 検索候補を別の基準またはモデルで再評価し、並べ替えられること。 | 並べ替え前後の順位を比較できることを確認する。 |
| `REQ-RET-005` | 全文検索、dense検索、hybrid検索、reranking、context選択を別の処理段階として記録できること。 | 1つの質問について各段階の結果を個別に取得できることを確認する。 |
| `REQ-RET-006` | 検索結果と、回答生成へ実際に渡したcontextを区別できること。 | 検索候補とcontextの内容・順位・件数を別に確認できることを確認する。 |

### 2.3 回答生成と引用

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-GEN-001` | 検索した文書をcontextとして回答を生成できること。 | 質問、context、生成された回答を同じ実行結果として確認する。 |
| `REQ-GEN-002` | 自分の管理する環境で動作する学習済みモデルを、主要な回答生成手段として使用できること。 | 外部LLM APIを必須とせず回答生成を実行できることを確認する。 |
| `REQ-GEN-003` | 回答と、回答の根拠として参照したsourceを構造化して取得できること。 | 回答とsource IDの一覧を機械的に区別して取得できることを確認する。 |
| `REQ-GEN-004` | 存在しないsourceの引用を検出できること。 | 不正なsource IDを含む結果を評価で識別できることを確認する。 |
| `REQ-GEN-005` | 文書から回答できない質問に対して、回答を拒否する動作を扱えること。 | no-answerの評価問題で回答または拒否結果を確認する。 |
| `REQ-GEN-006` | 回答生成結果が引用したsourceと、評価問題が正解根拠として保持するsourceを区別して管理できること。 | 任意の評価問題について、生成結果の引用sourceと正解根拠sourceを別に取得できることを確認する。 |

### 2.4 評価データ

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-DATASET-001` | 質問、reference answer、回答可能性、正解根拠を評価問題として管理できること。 | 保存した評価問題の各要素を取得できることを確認する。 |
| `REQ-DATASET-002` | 正解根拠を、正規化後の元文書内の範囲として指定できること。 | 指定した根拠範囲と元本文が一致することを確認する。 |
| `REQ-DATASET-003` | 根拠文字列から元文書内の位置を計算し、位置を手作業で数えずに評価問題を作成できること。 | CLI等から根拠文字列を指定し、位置が自動計算されることを確認する。 |
| `REQ-DATASET-004` | 評価問題をdevとtestに分けて管理できること。 | 各splitだけを選択して実験できることを確認する。 |
| `REQ-DATASET-005` | 初期のanswerableな評価問題では、1問につき1つの連続した正解根拠を扱えること。 | 1つの根拠範囲を持つ評価問題を登録・評価できることを確認する。 |

### 2.5 実験条件と実行結果

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-EXP-001` | 文書分割、検索、reranking、回答生成、評価の条件を実験条件として保存できること。 | 実験結果から使用した各条件を特定できることを確認する。 |
| `REQ-EXP-002` | 条件の異なる実験を識別し、同じ評価データに対する結果を比較できること。 | 2つ以上の実験を指定して評価値と質問ごとの結果を比較する。 |
| `REQ-EXP-003` | 1問ごとに、各検索段階の結果、context、prompt、回答、引用、評価結果、処理時間、状態、エラーを追跡できること。 | 任意の評価問題について各情報を取得できることを確認する。 |
| `REQ-EXP-004` | 実験全体の集計結果だけでなく、評価に使用した生データを保存できること。 | 集計値の元となる質問ごとの結果を取得できることを確認する。 |
| `REQ-EXP-005` | 保存済みの生データから、検索または回答生成を再実行せずに評価指標を再集計できること。 | 評価ロジック変更後に生データから指標を再計算できることを確認する。 |
| `REQ-EXP-006` | 実行の成功、失敗、開始、終了を記録できること。 | 正常終了と異常終了の両方で状態とエラーを確認する。 |

### 2.6 評価

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-EVAL-001` | answerableな質問について、検索結果を`Hit@k`、`MRR`、`EvidenceCoverage@k`、`EvidenceDensity@k`で評価できること。 | 既知の検索結果に対する各指標を計算し、期待値と一致することを確認する。 |
| `REQ-EVAL-002` | 必要に応じて`Recall@k`と`Precision@k`を補助指標として計算できること。 | 同一の関連チャンク定義に対して各指標を計算できることを確認する。 |
| `REQ-EVAL-003` | retrieval結果と、回答生成に使用したcontextを別に評価できること。 | 同じ質問に対して両者のCoverageとDensityを別に取得できることを確認する。 |
| `REQ-EVAL-004` | reranking前後の検索品質と追加処理時間を比較できること。 | 同じ候補集合に対する前後の指標と処理時間を確認する。 |
| `REQ-EVAL-005` | 回答のfaithfulness、正確性、関連性、引用の正確性を評価できること。 | 評価問題ごとに回答・引用の評価結果を取得できることを確認する。 |
| `REQ-EVAL-006` | answerable / no-answerの判定結果を、正解率、precision、recall、F1、誤回答率、誤拒否率で確認できること。 | answerableとno-answerを含む評価データで各値を集計する。 |
| `REQ-EVAL-007` | 検索、reranking、回答生成などの処理時間、成功率、timeout率、実行資源を記録・評価できること。 | 実験結果から各処理の時間・状態・実行条件を取得できることを確認する。 |
| `REQ-EVAL-008` | 回答内の引用が正しいかだけでなく、根拠を必要とする主張に必要な引用が付いているかを評価できること。 | 必要な引用を欠く回答を評価し、引用完全性の不足を識別できることを確認する。 |

### 2.7 実行とレポート

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-USE-001` | 主要な処理をCLIから実行できること。 | 文書登録、検索、実験、比較、レポート生成の主要操作をCLIから実行する。 |
| `REQ-USE-002` | 主要な処理をAPIとして提供できること。 | 定義されたAPIから主要処理を呼び出せることを確認する。 |
| `REQ-RPT-001` | 実験結果をMarkdown / CSV形式で出力できること。 | 同じ実験結果から両形式のレポートを生成する。 |
| `REQ-RPT-002` | レポートから実験条件、集計結果、質問ごとの結果、失敗例を確認できること。 | 生成されたレポートに必要な情報が含まれることを確認する。 |
| `REQ-RPT-003` | 条件の異なる実験結果を比較するレポートを生成できること。 | 2つ以上の実験を指定して比較結果を出力する。 |

## 3. 非機能要件

### 3.1 追跡可能性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-TRACE-001` | 回答から、使用したcontext、検索結果、元文書、実験条件へ遡れること。 | 任意の回答から各情報を参照できることを確認する。 |
| `REQ-NF-TRACE-002` | 文書チャンクと正解根拠を、同じ文書バージョンと位置情報で比較できること。 | 文書更新前後を混同せず重なりを計算できることを確認する。 |

### 3.2 再現性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-REP-001` | 使用したコード、データ、実験条件、モデル、実行環境を記録できること。 | 実験結果から各情報を取得できることを確認する。 |
| `REQ-NF-REP-002` | 再現性を出力文章の完全一致ではなく、同じ条件と手順による比較可能な実験の再実行として扱うこと。 | 記録した条件を用いて再実行し、比較対象として扱える結果が得られることを確認する。 |
| `REQ-NF-REP-003` | 第三者がREADMEに従ってローカル環境を構築し、sample dataの取り込みから実験レポート生成まで実行できること。 | 新しい環境で公開手順を実行し、一連の処理が完了することを確認する。 |

### 3.3 信頼性と保守性

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-REL-001` | 主要な正常系と異常系をテストで確認できること。 | 自動テストを実行し、主要経路と代表的な失敗を確認する。 |
| `REQ-NF-REL-002` | 外部プロセス、モデル処理、データベース処理の失敗を、処理状態とエラーとして記録できること。 | 意図的に失敗を発生させ、状態と原因を確認する。 |
| `REQ-NF-REL-003` | timeoutと、再試行可能な処理のretryを扱えること。 | timeoutと一時的失敗を発生させ、規定した挙動を確認する。 |
| `REQ-NF-REL-004` | 設定をコードへ埋め込まず、実行条件として管理できること。 | 条件変更をコード変更なしで反映できることを確認する。 |
| `REQ-NF-REL-005` | 処理の進行、失敗、実験識別子を追跡できるログを出力できること。 | 1回の実験に関係するログを識別して確認する。 |

### 3.4 性能の観測

| ID | 要求 | 確認方法 |
|---|---|---|
| `REQ-NF-PERF-001` | 検索、reranking、回答生成などの処理時間を段階別に計測できること。 | 実験結果から段階ごとの処理時間を取得する。 |
| `REQ-NF-PERF-002` | 回答生成では、最初のtokenが得られるまでの時間、生成token数、生成時間を計測できること。 | 回答生成結果から各値を取得する。 |
| `REQ-NF-PERF-003` | 実行環境のCPU / GPU、memory、device、dtypeなど、性能比較に必要な条件を記録できること。 | 実験結果から実行環境を確認する。 |

具体的な性能目標値は、対象コーパスとモデルを決定し、実測可能になった段階で定める。

## 4. 制約

### 4.1 技術・実行方針

- モデルの事前学習や基盤モデルの研究は行わず、既存の学習済みモデルを使用する。
- RAG本体はローカル環境で実行可能な構成を優先する。
- 文書、検索、評価、実験の流れを制御するRAGScopeアプリケーションは、Haskellで実装する。
- AIモデルとAIライブラリを扱うAI推論サービスは、Pythonで実装する。
- 外部のLLM APIは主要な実行手段とせず、必要になった場合に比較対象として追加する。
- v1.0まではAPIとCLIを主な利用手段とし、結果はMarkdown / CSVで出力する。
- AWSへの配置はRAG本体の完成条件へ含めず、独立した検証段階として扱う。

### 4.2 初期データ

| 項目 | 制約 |
|---|---|
| 文書形式 | Markdown / TXT |
| 言語 | 最初は英語。日本語は第2コーパス |
| 規模 | 数十〜数百文書 |
| 分野 | ライセンスが明確な1つの技術分野 |
| 正解根拠 | v0.1ではanswerableな1問につき1つの連続範囲 |

## 5. 対象外

初期版からv1.0までは、次を対象外とする。

- PDF、OCR、画像
- 複雑なレイアウト解析
- 大量データ
- 複数箇所の根拠を統合するmulti-hop評価
- マルチテナント
- 本格的なWeb UI
- 認証
- ストリーミング
- エージェント
- Kubernetes
- 複数ノードの分散推論
- 高可用構成
- vLLM
- HNSW / IVFFlat

## 6. 主張しないこと

RAGScopeだけによって、次を実現したとはみなさない。

- 本番環境での高可用性や大規模トラフィック対応
- 複数ノードの分散推論
- 完成されたLLMOps基盤
- 商用クラウド環境の長期運用
- 特定企業の実務要件の充足

## 7. 未決定事項

次の内容は、必要なMilestoneまたは機能設計に着手する時点で決定する。

- 最初の文書コーパス
- 評価用質問の具体的な作成方針
- 最初のEmbedding model
- 最初のgeneration model
- `evidence_overlap_threshold`の初期値

未決定事項は、決定前に特定の値を要求として固定しない。
