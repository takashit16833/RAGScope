# Pythonコーディング規約

> [!abstract] この文書の役割
> AI推論サービスのPythonコードへ適用する、モジュール、関数、クラス、型、例外、副作用、テスト、整形、検証の規約を定義する。  
> 言語に共通する方針は[RAGScopeコーディング規約](./RAGScopeコーディング規約.md)に従う。

## 1. 適用範囲

本規約は、`ai-service/`配下のPythonソースコードとテストコードへ適用する。

JSON、HTTP、モデル入出力などの外部契約は、対応するJSON Schema、OpenAPI、設計、実装を正本とする。Pythonコードでは、外部形式を内部表現へ無制限に持ち込まず、境界でRAGScopeが扱う意味へ変換する。

本規約はPythonを特定のプログラミングパラダイムへ寄せることを目的としない。Pythonの標準的な機能を使って、責務、型、状態、副作用、失敗の境界を明確にすることを優先する。

## 2. 設定、整形、検証

### 2.1 機械可読な正本

| 内容 | 正本 |
|---|---|
| Pythonバージョン、依存、Ruff、Pyright、pytestの設定 | [`ai-service/pyproject.toml`](../../ai-service/pyproject.toml) |
| 解決済み依存バージョン | [`ai-service/uv.lock`](../../ai-service/uv.lock) |
| 文字コード、改行、インデント | [`.editorconfig`](../../.editorconfig) |
| Python開発環境 | [`.devcontainer/ai-service/`](../../.devcontainer/ai-service/) |
| 具体的な型と関数 | Pythonソースコード |
| 具体的なテストケース | Pythonテストコード |
| 整形と品質検査の実行入口 | [`Makefile`](../../Makefile) |

Ruff formatterによる整形結果を正規形とし、Ruff linter、Pyright、pytestの判定を現在の自動検査として扱う。具体的なバージョンや設定値を本規約へ重複して固定しない。

整形と検証は、リポジトリルートの`Makefile`を再現可能な入口とする。Pythonコードの整形は`make format-ai`、非破壊の整形・lint検査は`make format-check-ai`、型検査とテストを含む品質検査は`make check-ai`を使用する。

### 2.2 責務が重複するツールを増やさない

formatter、linter、型検査、テストの同じ責務を担当するツールを、明確な不足がないまま追加しない。

現在のツールで検査できない具体的な問題が発生した場合は、その問題、既存ツールで代替できない理由、追加後の責務境界を確認してから導入する。Black、isort、Flake8、mypyなどを、一般的に使われているという理由だけで併用しない。

## 3. モジュール、関数、クラス、データ

### 3.1 モジュールと型付き関数を基本とする

処理は、まず責務のまとまりをモジュールとして分け、その中を型注釈付きの関数で表現できないか検討する。

入力の検証、値の変換、判断、組み立てなど、状態を保持する必要がない処理をクラスへ機械的に包まない。

次のような、インスタンス状態を持たず単に関数をまとめただけのクラスを作らない。

```python
class ErrorConverter:
    @staticmethod
    def convert(exc: Exception) -> AppError:
        ...
```

この場合は、責務を表すモジュールと通常の関数を基本とする。

### 3.2 クラスを使う条件

クラスは、次のいずれかを明確に担当する場合に使用する。

- 複数の操作が共有する状態を保持する
- 生成後に維持すべき不変条件がある
- モデル、ファイル、接続など、生成・利用・解放のライフサイクルを持つ
- 呼び出し側から隠すべき状態と操作を1つの責務としてまとめる

「関連する関数をまとめたい」「将来拡張しそう」という理由だけでクラスを作らない。

`Manager`、`Service`、`Helper`、`Utils`のような広い名前のクラスへ異なる責務を集約しない。クラス名だけで担当範囲を説明できない場合は、責務を見直す。

継承は、実際に代替可能な関係があり、共通実装を継承することが構成による委譲より明確な場合に限定する。深い継承階層を作らない。

### 3.3 データを意味のある形で表す

複数の値が1つの概念を構成し、同じ組み合わせで受け渡される場合は、裸の`dict`やtupleを広範囲へ渡す前に、`dataclass`などの明示的な型で表現できないか検討する。

値として扱うデータは、変更する理由がない場合、`@dataclass(frozen=True)`などを使って不必要な変更を防ぐ。

閉じた名前付き選択肢には`Enum`など、複数の異なる構造を持つ閉じた選択肢にはunion型など、Pythonの標準的な型表現を優先する。

`dict[str, Any]`や多数のnullableフィールドを、異なる意味の状態をまとめる万能表現として使用しない。JSONなど動的な外部形式を受け取る場合は、境界で検証・変換し、内部では意味のある型へ移す。

### 3.4 抽象化は必要な境界だけに置く

呼び出し側が具体実装ではなく「提供される操作」だけへ依存する必要がある場合は、`Protocol`などのstructural typingを使用できる。

ただし、すべてのクラスや関数に対応する`Protocol`を先行して作らない。差し替え、テスト用実装、複数実装などの具体的な利用目的がある境界だけに置く。

抽象基底クラス、factory、repository、providerなどのパターンを、名前を揃えるためだけに導入しない。

### 3.5 他言語の構造を移植しない

Haskell側と共通するのは契約と意味であり、Haskell固有の型構造、モナド、型クラス、関数合成の形をPythonへそのまま再現しない。

同様に、Javaなどのクラス中心の設計を前提として、単純な処理までinterface、abstract class、service classへ分解しない。

`Result`、`Either`、`Maybe`に相当する独自抽象を、関数型らしさを目的として導入しない。成功と失敗を独立した値として保持することがRAGScopeの契約上必要であり、Pythonでもその表現が境界を明確にする場合は、その要件に合わせて最小の型を設計する。

## 4. 命名

Pythonコードでは次を基本とする。

| 対象 | 形式 | 例 |
|---|---|---|
| モジュール、パッケージ | 小文字の`snake_case` | `log_event.py`、`ragscope_ai_service` |
| 関数、メソッド、変数 | `snake_case` | `encode_log_event`、`execution_id` |
| クラス、型、Protocol、Enum | `UpperCamelCase` | `AppError`、`LogSink` |
| 定数 | `UPPER_SNAKE_CASE` | `DEFAULT_TIMEOUT_SECONDS` |
| 型変数 | 意味が明確な短い名前 | `T`、`ErrorT` |

RAGScopeの要求、設計、Contract、Schemaに存在する概念は、Pythonでも対応関係が分かる語を使用する。

外部JSONの`snake_case`とPython内部の名前が同じでも、外部形式の構造そのものを内部データ構造として共有する必要はない。境界での変換と内部の責務を分ける。

`data`、`item`、`obj`、`manager`、`helper`など、広すぎて役割を特定できない名前を、文脈で意味が明らかな狭い局所変数以外に使用しない。

## 5. 型

### 5.1 型注釈を実装境界として扱う

`src/`配下のモジュールレベル関数、クラスのメソッド、外部から利用する値の境界には型注釈を付ける。テストコードもPyrightの検査対象として、fixtureやhelperを含めて必要な型を明示する。

局所変数は、推論された型で意図が明確な場合に機械的な注釈を追加しない。型注釈は記述量を増やすためではなく、入力、出力、状態、失敗の意味を明確にするために使う。

### 5.2 `Any`で型検査を回避しない

`Any`を、型設計を省略するための既定値として使用しない。

外部ライブラリや動的な入力によって`Any`を避けられない場合は、その値を扱う範囲を境界へ限定し、検証、型ガード、変換によって可能な限り早く具体的な型へ絞り込む。

広範囲へ`Any`を伝播させるより、外部依存のadapterだけが動的な値を扱う構成を優先する。

### 5.3 `cast`と型検査抑制を限定する

`cast`は、実行時または契約上の根拠によって型が保証されているが、型検査器だけではその事実を導出できない場合に限定する。単に型エラーを消すために使用しない。

`# type: ignore`などで型検査を抑制する場合は、対象を最小範囲に限定し、可能であれば抑制する診断を明示する。理由がコードから明らかでない場合はコメントを付ける。

型検査の抑制が複数箇所へ広がる場合は、個別に抑制を増やす前に、型、依存ライブラリ、境界設計を見直す。

### 5.4 型を技巧のために複雑化しない

型エイリアス、generic、Protocol、overloadなどは、利用側の誤用を防ぎ、意味を明確にする場合に使う。

型検査を通すためだけに、実装より理解が難しい型パズルを作らない。Pythonの型システムで自然に表現しにくい制約は、必要に応じて生成関数や実行時検証と役割を分担する。

## 6. 状態、副作用、例外、境界

### 6.1 変換と副作用を分ける

検証、変換、判断、データの組み立ては、可能な範囲で外部状態を変更しない関数として実装する。

ファイル、標準入出力、時計、UUID生成、ネットワーク、モデル、DBなどの副作用は、その副作用を担当する境界へ寄せる。

```text
外部入力・I/O → 境界で検証・変換 → 通常のPython値による処理 → 境界でI/O
```

Functional Core / Imperative Shellの分離は、処理を理解・テストしやすくするために採用し、純粋性そのものを目的にしない。

### 6.2 mutableな状態を広げない

変更可能なcollectionやオブジェクトを複数モジュールから共有し、どこからでも変更できる状態を避ける。

状態変更が必要な場合は、その状態を所有する関数またはクラスを明確にし、変更箇所を限定する。

モジュールglobalへ実行中に変化する状態を置かない。キャッシュやモデルなどプロセス寿命の状態が必要になった場合も、所有者、初期化、利用、破棄の責務を明確にする。

### 6.3 例外を境界で意味へ変換する

下位ライブラリの例外や想定外例外を、RAGScopeの公開境界、JSON、構造化ログへそのまま流さない。現在のエラー設計に従って、責務を持つ境界でRAGScopeが扱う意味へ変換する。

`except Exception`による広い捕捉は、想定外例外を共通エラーへ変換する最外側の境界など、すべての例外を扱う責務が明確な場所に限定する。

例外を捕捉して無視したり、成功値へ置き換えたりしない。再送出、変換、記録など、その例外を捕捉する理由がコードから分かるようにする。

元の例外メッセージやstack traceを利用者向け情報や構造化ログへ含めるかどうかは、現在のエラー設計と構造化ログ設計を正本とする。

### 6.4 予想可能な失敗の表現を一律化しない

Pythonのすべての処理へ1種類の独自`Result`型や例外方式を機械的に適用しない。

呼び出し側が成功と失敗を同時に値として保持・合成する必要がある場合、通常のPython例外として境界まで伝播させる方が自然な場合など、現在の契約と責務に応じて表現を選ぶ。

同じ責務内で同じ種類の失敗を複数方式へばらつかせない。

## 7. モジュール、依存、Python固有機能

### 7.1 1モジュール1責務を基本とする

モジュール名から担当する概念または処理を説明できる構成にする。異なる変更理由を持つ型、変換、I/O、設定を1ファイルへ集約しない。

`utils.py`、`helpers.py`、`common.py`のような何でも置けるモジュールを作らない。共通化する場合も、何を共通化したのかを表す責務名を付ける。

`__init__.py`を大量のre-exportや初期化処理の置き場にしない。パッケージの公開入口として実際に必要なものだけを置く。

循環importが生じた場合は、遅延importや巨大な共通モジュールで隠す前に、型と責務の配置、依存方向を見直す。

### 7.2 importを明示する

`from module import *`を使用しない。

import先がRAGScopeのどの責務か分かる形を保ち、import時にネットワークアクセス、モデル読み込み、ファイル書き込みなど重い副作用を実行しない。

型注釈のためだけの循環依存が生じる場合は、`TYPE_CHECKING`などを利用できるが、実行時の責務循環を型検査用の仕組みで隠さない。

### 7.3 依存パッケージを最小化する

標準ライブラリで責務を自然に満たせる場合は、依存追加によって明確な利点が得られるか確認する。

依存パッケージを追加・更新する場合は、`pyproject.toml`と`uv.lock`を正本として再現可能な状態を保つ。`uv.lock`を手作業で編集しない。

開発時だけ利用するツールと実行時依存を混同しない。

### 7.4 Python固有の高度な機能を必要時だけ使う

comprehension、generator、pattern matchingは、通常のloopや条件分岐より処理の意味が明確になる場合に使用する。複数段の複雑なcomprehensionへ処理を詰め込まない。

decoratorは、対象関数の主要な制御フローや失敗条件を隠さない範囲で使用する。処理を追うために複数のdecorator実装を横断する必要がある構成を避ける。

metaclass、descriptor、monkey patch、動的な属性生成、実行時コード生成、過度なreflectionは、通常の関数、クラス、compositionでは要件を自然に満たせない具体的な理由がある場合に限定する。

`async` / `await`は、実際の非同期I/Oや並行処理の要件がある境界へ導入する。将来HTTPサービスになるという理由だけで、同期処理まで先行してasync化しない。

特殊メソッドや演算子overloadは、その型に対してPython利用者が自然に期待できる意味がある場合だけ定義する。

## 8. docstringとコメント

[RAGScopeコーディング規約](./RAGScopeコーディング規約.md)のコメント方針をPythonにも適用する。

### 8.1 docstringは契約を説明する

別モジュールから利用する関数、クラス、メソッドで、型注釈と名前だけでは意味、不変条件、副作用、失敗条件が十分に分からない場合はdocstringを記述する。

引数名や戻り値の型を型注釈から機械的に言い換えない。次のような、利用側の判断に必要な情報を優先する。

- 何を表す処理または型か
- 入力に必要な前提
- 保証する不変条件
- 発生する副作用
- 呼び出し側が扱うべき失敗
- 使用してはいけない状況

短い内部helperなど、名前、型、実装だけで責務が明らかなものへ形式的なdocstringを追加しない。

### 8.2 通常コメントは実装上の理由を説明する

docstringは利用側との契約、通常コメントは処理内部の理由や制約を説明する。

外部Schemaとの対応、情報保護、順序依存、意図的な例外処理など、単純化すると壊れやすい箇所には通常コメントを置く。

コメントとdocstringの説明文は日本語を基本とし、Python識別子、RAGScopeの正式用語、技術用語は必要に応じて原表記を使用する。

## 9. テスト

pytestを使用し、テスト対象の契約と振る舞いを確認する。

- テスト名から対象条件と期待結果を判断できるようにする。
- 準備、実行、確認の流れが読める構成にし、単純なテストへ形式的なコメントを追加しない。
- 純粋な変換や判断は、入力と出力を直接検査する。
- 時刻、UUID、標準入出力、ファイル、ネットワーク、モデルなどの副作用は、責務境界を差し替えてテストする。
- mockは外部境界や観測したい相互作用へ限定し、内部実装の呼び出し順を細かく固定するテストを避ける。
- 同じ意味の入力パターンを列挙する場合は、読みやすさが上がる範囲でparameterizeを使用する。
- fixtureは、複数テストで同じ意味を持つ準備を共有する場合に使う。巨大な共通fixtureや`conftest.py`へ異なる責務を集約しない。
- 外部契約は、文字列の完全一致やJSON項目順だけに依存せず、対応するSchemaと意味を検査する。
- テストを通すためだけに本番コードへ不要な公開APIや条件分岐を追加しない。

## 10. レビュー時の確認

- 状態を持たない処理が、理由なくクラスへ包まれていない
- クラスが状態、不変条件、ライフサイクルなど説明可能な責務を持っている
- Haskell固有の抽象やJava的な階層をPythonへ機械的に移植していない
- 内部データを`dict[str, Any]`やnullableな万能構造へ集約していない
- Pyrightの型エラーを`Any`、`cast`、型検査抑制で安易に回避していない
- 変換・判断とI/O、副作用の境界が分かる
- mutableな状態の所有者と変更箇所が限定されている
- 下位ライブラリの例外を公開境界や構造化ログへそのまま流していない
- `utils.py`など責務の曖昧な共通モジュールを作っていない
- Protocol、継承、decorator、async、高度な動的機能を必要性なく導入していない
- docstringと通常コメントが、それぞれ契約と実装上の理由を説明している
- テストが内部実装ではなく契約と振る舞いを確認している
- `make check-ai`を実行し、Ruff、Pyright、pytestの検査を確認している
- Contract、Schema、設計とPython実装が矛盾していない
