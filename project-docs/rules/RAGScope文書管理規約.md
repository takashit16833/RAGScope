# RAGScope文書管理規約

> [!abstract] この文書の役割
> RAGScopeにおける文書の配置、責務、正本、参照関係を定義する。  
> 「何をどこへ記載するか」を統一し、文書間の重複や矛盾を防ぐ。

## この規約の読み方

| 確認したいこと | 主な参照先 |
|---|---|
| 情報ごとの正本と履歴の分け方 | 第2章 |
| 文書とフォルダの配置 | 第3章 |
| 各文書に何を記載するか | 第4章 |
| 機能設計書の種類、選択基準、粒度 | 第4.5節 |
| ADR・実験記録を作成する条件 | 第4.6節・第4.7節 |
| コードに共通する規約と言語別規約 | [RAGScopeコーディング規約](./RAGScopeコーディング規約.md)・[Haskellコーディング規約](./Haskellコーディング規約.md) |
| 文書間で確認する整合 | 第5章 |
| ファイル名、本文、リンク、Markdown表記 | 第6章 |
| Frontmatterの定義 | [Obsidianメタデータ規約](./Obsidianメタデータ規約.md) |
| Roadmap・Milestone・Epic・Ticketの運用 | [RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md) |

## 1. 適用範囲

### 対象となる文書

本規約は、RAGScopeリポジトリで人が作成・管理し、利用者または開発者が読む文書、および文書として管理する成果物へ適用する。

本規約で`rules/`、`design/`、`adr/`、`experiments/`、`project-management/`、`templates/`、Vault直下のMarkdownと記載する場合は、Obsidian Vaultである`project-docs/`を基準とする。`README.md`と`.github/`は、リポジトリルートを基準とする。

主な対象は次のとおりとする。ここに列挙されていない文書でも、同じ性質を持つものには本規約を適用する。

- リポジトリルートの`README.md`
- Vault直下の`RAGScope概要.md`、`RAGScope要求定義.md`、`RAGScope開発運用ガイド.md`
- `rules/`配下の各種規約文書
- `design/`配下のシステム・機能設計
- `adr/`配下の設計判断
- `experiments/`配下の実験記録
- `project-management/`配下のRoadmap、Milestone、Epic、Ticket
- `templates/`配下のObsidianテンプレート
- リポジトリルートの`.github/pull_request_template.md`

### 対象外

ソースコード、テストコード、migration、OpenAPIなどのAPI定義、設定ファイル、依存関係のロックファイル、CI/CD定義、ローカル開発環境・エディタ設定、ビルド生成物、一時ファイルには適用しない。

ただし、それらの正確な定義とMarkdownの説明を重複させないための扱いは、第2.3節に従う。

一般的なAI・LLM・RAGの学習ノートは、本リポジトリへ置かない。

### 関連規約

Frontmatterは[Obsidianメタデータ規約](./Obsidianメタデータ規約.md)、Roadmap・Milestone・Epic・Ticketの運用は[RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md)に従う。

## 2. 基本原則

### 2.1 1つの情報に1つの正本を設ける

| 情報 | 正本 |
|---|---|
| RAGScopeの目的、価値、想定利用方法、主な能力の概要 | `RAGScope概要.md` |
| 機能・品質・制約・対象範囲・対象外の詳細 | `RAGScope要求定義.md` |
| 現在採用しているシステム・機能の設計 | `design/` |
| 重要な設計判断の背景、選択肢、理由 | `adr/` |
| 仮説、検証条件、結果、考察 | `experiments/` |
| バージョン計画と作業の進行記録 | `project-management/` |
| 正確な実装、型、Schema、テスト | コード、migration、OpenAPI、テストなど |

同じ情報を複数の文書で正本として管理しない。別の文書で触れる場合は簡潔に要約し、詳細の正本へ相対リンクする。

`README.md`は入口と要約であり、アプリケーション概要の正本ではない。

### 2.2 現在仕様と履歴を分ける

| 記録する内容 | 記録先 |
|---|---|
| 現在有効な要求 | 要求定義 |
| 現在採用している設計 | 設計書 |
| 重要な判断の背景、選択肢、決定、影響 | ADR |
| 実際に行った検証と得られた結果 | 実験記録 |
| 個別の変更作業、完了条件、実施結果 | Ticket |
| ファイルの変更履歴 | Git |

現在仕様を理解するために、過去のTicketやMilestoneを読むことを必須にしない。

### 2.3 機械可読な仕様を優先する

正確な定義をコードや専用形式で表現できる場合は、それを正本とする。

| 内容 | 正本 |
|---|---|
| DBのテーブル・カラム・制約 | migration |
| APIの正確なSchema | OpenAPIなどのAPI定義 |
| Haskell・Pythonの型 | ソースコード |
| CLIの正確な選択肢 | 実装と`--help` |
| 具体的なテストケース | テストコード |
| パッケージのバージョン | ロックファイル・設定ファイル |

Markdownには、実装だけでは分かりにくい責務、理由、契約、不変条件、処理フロー、変更時の注意を記載する。機械可読な定義をそのまま複製しない。

### 2.4 必要な文書だけを作る

- 具体的な内容と利用目的が生じた時点で文書を作成する。
- 将来必要になる可能性だけを理由に、空文書や空フォルダを作らない。
- 既存文書で責務を満たせる場合は、新しい文書を作らない。
- 1つの文書が異なる問いや責務を扱うようになった場合に分割する。

## 3. 文書構成

### 配置の全体像

```text
RAGScope/
├── README.md
├── .github/
│   └── pull_request_template.md
└── project-docs/
    ├── RAGScope概要.md
    ├── RAGScope要求定義.md
    ├── RAGScope開発運用ガイド.md
    ├── rules/
    │   ├── Haskellコーディング規約.md
    │   ├── Obsidianメタデータ規約.md
    │   ├── RAGScopeコーディング規約.md
    │   ├── RAGScope文書管理規約.md
    │   └── RAGScopeプロジェクト管理規約.md
    ├── design/
    │   ├── システムアーキテクチャ.md
    │   └── <必要になった機能設計>.md
    ├── adr/
    │   └── ADR-0001 <判断の題名>.md
    ├── experiments/
    │   └── <実施した検証>.md
    ├── project-management/
    │   ├── ロードマップ.md
    │   └── milestones/
    └── templates/
        ├── 設計書テンプレート.md
        ├── 処理・振る舞い設計書テンプレート.md
        ├── 構造・契約設計書テンプレート.md
        ├── ADRテンプレート.md
        ├── Milestoneテンプレート.md
        ├── Epicテンプレート.md
        └── Ticketテンプレート.md
```

### 配置上の原則

- `experiments/`は、最初の内容が生じた時点で作成する。
- `RAGScope開発運用ガイド.md`は、プロジェクト管理規約に基づく具体的な操作の入口として使用する。
- `templates/`とリポジトリルートの`.github/pull_request_template.md`は、開発運用ガイドに従ってノート作成・Pull Request作成に使用する。
- 機能別設計書は、技術要素ではなく設計対象となる機能・責務で分ける。
- Roadmap、Milestone、Epic、Ticketの詳細な構成は、RAGScopeプロジェクト管理規約を正本とする。

## 4. 文書ごとの責務

### 4.1 `README.md`

#### 記載する内容

リポジトリの入口として、次を簡潔に記載する。

- RAGScopeの短い説明
- 主な能力
- 現在利用できる機能と最新リリースの概要
- 最小限のセットアップ・実行方法
- 簡略化した構成
- 代表的な生成結果
- 詳細文書への導線

#### 記載しない内容

RAGScopeの目的・価値・対象範囲は、`RAGScope概要.md`の内容を要約し、詳細は同文書へリンクする。

READMEには、作業中のMilestone名や一時的な`status`を手作業で転記しない。開発予定はRoadmapへリンクし、作業中のMilestoneはMilestoneノートの`status`とBases・検索から確認する。READMEの状態説明は、現在利用できる機能と最新リリースの内容を中心とする。

詳細な設計、要求一覧、Ticket一覧、実験の生データを記載しない。

### 4.2 `RAGScope概要.md`

RAGScopeというアプリケーションの概要の正本とする。

#### 記載する内容

- 解決する問題
- 提供する価値
- 想定する利用方法
- 主な能力
- 対象範囲の概要
- 対象外・主張しないことの概要

#### 記載しない内容

主な能力、対象範囲、対象外は高い粒度で要約し、詳細かつ検証可能な定義は`RAGScope要求定義.md`を正本とする。

詳細な機能要件、技術選定、設計、バージョン計画は記載しない。

### 4.3 `RAGScope要求定義.md`

RAGScopeが満たすべき内容の正本とする。

#### 記載する内容

- 機能要件
- 非機能要件
- 制約
- 対象外
- 必要に応じて、要件の識別子と確認方法

#### 記載しない内容

要求定義には「何を満たすか」を記載する。「どのコンポーネント、型、DB、ライブラリで実現するか」は設計書へ記載する。

### 4.4 `design/`

`design/`全体をRAGScopeのシステム設計とする。

#### `システムアーキテクチャ.md`

システム全体に関する次の内容を記載する。

- コンポーネント構成
- 各コンポーネントの責務
- 依存方向
- コンポーネント間の通信
- システム全体の処理・データフロー
- 配置・実行環境の基本方針

`システムアーキテクチャ.md`はシステム全体を扱う特別な文書であり、第4.5節の2種類の機能別設計テンプレートへ機械的に合わせない。

#### 機能別設計書

機能別設計書は、対象機能について現在採用している設計の正本とする。新しい機能の作成または既存機能の変更により、完了後も有効な設計情報が生じる場合に、対象機能の設計書を作成または更新する。

例：

```text
文書処理設計.md
データモデル設計.md
検索設計.md
評価設計.md
API設計.md
```

Ticketごとに新しい設計書を作ることは必須としない。既存の機能設計書で責務を自然に扱える場合は、その設計書を更新する。異なる機能・責務を扱うようになった場合に、新しい設計書へ分ける。

各設計書は、過去のTicketや変更記録を読まなくても、現在採用している設計を理解できる状態にする。判断理由を詳しく残す必要がある場合はADRへリンクする。

### 4.5 機能設計の種類と構成

#### 基本設計と詳細設計の扱い

基本設計と詳細設計を、`basic-design/`と`detailed-design/`のような別フォルダや文書体系へ機械的に分けない。

対象機能の同じ設計書に、全体像から、実装が守る規則、不変条件、エラー処理、境界条件まで必要な粒度を記載する。

基本設計と詳細設計は情報の粒度であり、必ずしも固定の章名ではない。処理・振る舞い型で分ける意味がない小規模な機能では統合してよい。構造・契約型では、読者の問いごとに情報をまとめ、「基本設計」「詳細設計」を固定見出しとして使用しなくてよい。

#### 2種類のテンプレート

機能別設計書を新規作成する場合は、[設計書テンプレートの選択](../templates/設計書テンプレート.md)から、次のいずれかを選ぶ。

| 種類 | 中心となる問い | 判断材料 | テンプレート |
|---|---|---|---|
| 処理・振る舞い設計書 | 何が、どの順序で、どの条件に従って処理されるか | 入力から出力までの流れ、複数の処理段階や分岐、正常系・異常系、状態遷移、後続処理への受け渡しが重要 | [処理・振る舞い設計書テンプレート](../templates/処理・振る舞い設計書テンプレート.md) |
| 構造・契約設計書 | 何を共有し、それぞれが何を意味し、どの規則を守るか | 項目、語彙、形式、識別子、複数機能で共有する意味、不変条件、公開範囲、機械可読な正本が重要 | [構造・契約設計書テンプレート](../templates/構造・契約設計書テンプレート.md) |

両方の性質を持つ場合は、文書を読む人が最初に答えを得たい問いを基準に、主となるテンプレートを1つ選ぶ。必要な節だけ、もう一方のテンプレートから追加してよい。

2つのテンプレートを単純に結合し、すべての章を持つ巨大な設計書にしない。テンプレートへ適合させるために責務の異なる内容を混在させる場合は、文書の分割または設計対象の再定義を検討する。

どちらにも自然に適合しない設計対象が実際に生じた場合は、既存テンプレートへ無理に押し込まず、その時点で構成を見直す。将来の可能性だけを理由に3つ目のテンプレートを先行作成しない。

#### テンプレートの使い方

テンプレートは帳票ではなく、読み手が必要な情報へ到達するための骨組みである。

- 設計対象に不要な見出しを残さない。
- 内容のない見出しや、形式を満たすためだけの「該当なし」を残さない。
- 最も頻繁に確認される代表例、主要項目、全体像を文書の前半へ置く。
- 責務分担、対象外、正本、Ticket、将来事項を、主要な設計内容より前に大量に置かない。
- Ticket、Milestone、作業記録を現在設計の本文へ複製しない。
- 関連する要求と上位設計は確認するが、導線を本文の中心にせず、必要最小限のリンクにする。
- テスト観点、将来事項、変更時の注意、未決定事項は、本文と異なる設計固有の情報がある場合だけ追加する。
- 同じ規則を概要、詳細、テスト、変更時の注意で繰り返さない。
- 正確な型、Schema、OpenAPI、migration、テストケースをMarkdownへ複製しない。

#### 読みやすい設計書の表現

本項の表現方針は、`システムアーキテクチャ.md`と機能設計書の両方に適用する。

設計書は、文章を最初から順番に読まなくても、見出しと視覚表現から全体像、情報の階層、必要な規則の場所を把握できる構成にする。

| 内容 | 優先する表現 |
|---|---|
| 処理の順序、分岐、コンポーネント間の流れ | Mermaidまたは簡潔なフロー |
| 項目の対応、条件ごとの差、責務の比較 | 表 |
| データの代表的な形、識別子の組み立て | JSONやテキストなどのコード例 |
| 特に重要な制約、注意、補足 | Callout |
| 背景、理由、表や図だけでは伝わらない意味 | 短い文章 |

表現を選ぶときは、次を守る。

- 小さな節へ分け、見出しだけでも情報の階層が分かるようにする。
- 表や図が何を説明し、どの問いに答えるものかを、見出しまたは直前の短い導入から理解できるようにする。
- 表や図の目的がすでに明らかな場合は、見出しや内容を言い換えるだけの導入を追加しない。
- フロー図の要素名だけで意味が分からない場合は、要素名を具体化するか、図の直後に短い説明を置く。
- 具体的な値やアルゴリズムを図へ詰め込まず、詳細の正本へリンクする。
- 採用済みの設計、現在のMilestoneで具体化した規則、未決定事項を区別する。
- 未決定の選択肢を、採用済みの仕様と同じ断定表現で記載しない。
- 長い段落が続く場合は、見出し、表、図、コード例、Calloutで構造を示せないか検討する。
- 文章を機械的に分割したり、すべてを表へ変換したりしない。
- 同じ情報を文章、表、図、コード例で繰り返さない。
- 行数や文字数を目標にしない。必要な説明は残し、機械可読な正本の複製と意味のない言い換えを削る。
- ObsidianとGitHubの両方で、見出し、表、図、Callout、コード例の関係を追える状態にする。

この表現方針は、設計内容の厳密さを弱めるものではない。正確な規則と責務境界を保ったうえで、読み手が構造を先に理解できる形へ整理する。

#### 作業記録との分離

今回の変更目的、作業範囲、完了条件、実施結果はEpic・Ticketへ記録し、機能設計書には完了後も有効な現在設計を記載する。

重要な設計判断の理由はADR、実測や比較を伴う検証はExperimentへ記録する。

### 4.6 `adr/`

重要な設計判断について、背景、検討した選択肢、決定、結果と影響を記録する。

#### 作成する条件

ADRは、次のいずれかに該当する場合に作成する。

- 複数の現実的な選択肢がある。
- 変更コストが高い。
- 複数の機能やシステム全体へ影響する。
- 判断理由を残さなければ、同じ議論を繰り返す可能性がある。

局所的な実装詳細や、容易に変更できる小さな判断までADRにしない。

#### 構成と更新

最小構成：

```markdown
# ADR-0001 — 判断の題名

## 背景

## 決定

## 検討した選択肢

## 結果と影響
```

ADRを新規作成する場合は、原則として[ADRテンプレート](../templates/ADRテンプレート.md)を使用する。テンプレートのコメントは記載内容を検討するための作業支援であり、作成したADRには判断の記録として必要な本文だけを残す。

判断が変わった場合は、採用済みADRを黙って書き換えて履歴を消さない。新しいADRを作成し、旧ADRを`superseded`へ変更する。

### 4.7 `experiments/`

仮説を実際に検証した記録を置く。

#### 記載する内容

- 仮説
- 条件
- 手順
- 結果
- 失敗例
- 解釈
- 次の判断

例えば、チャンク条件、検索方式、Embeddingモデル、`reranking`などを、同一の評価データで比較した記録を置く。

#### 記載しない内容

一般知識の解説や、単なる実装作業の記録は置かない。実験結果が重要な設計判断につながった場合は、ADRから該当する実験記録へリンクする。

### 4.8 `rules/`

RAGScopeの文書管理、Obsidianメタデータ、プロジェクト管理、コーディングに関する規約を置く。

| 規約 | 定義する内容 |
|---|---|
| `RAGScope文書管理規約.md` | 文書の配置、責務、正本、参照関係 |
| `Obsidianメタデータ規約.md` | Frontmatterのプロパティ、型、許容値 |
| `RAGScopeプロジェクト管理規約.md` | Roadmap、Milestone、Epic、Ticketの運用 |
| `RAGScopeコーディング規約.md` | 言語に共通するコード品質、コメント、構成、命名、検証の原則 |
| `Haskellコーディング規約.md` | RAGScopeアプリケーションのHaskell固有規約 |

コーディング規約は、設定ファイルやソースコードで表現できる正確な値と定義を複製せず、設定だけでは表せない意図と判断基準を扱う。言語固有の実装が始まり、共通規約だけでは判断できない内容が生じた時点で、対応する言語別規約を作成する。

### 4.9 `project-management/`

Roadmap、Milestone、Epic、Ticketなど、開発作業の計画と進行記録を管理する。

要求や設計の現在内容を、プロジェクト管理文書だけに記載しない。具体的な運用は[RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md)に従う。

### 4.10 `RAGScope開発運用ガイド.md`

RAGScopeのプロジェクト管理に関する具体的な操作手順を一元的に記載する。

#### 記載する内容

- Obsidianテンプレートの初回設定と挿入方法
- Milestone・Epic・Ticketの作成順序
- Ticketへの着手、ブランチ作成、Pull Request、完了確認
- Epicの完了とMilestoneのリリース
- Ticketの移動・中止などの例外操作

#### 規約との境界

定義、状態遷移、完了条件、命名規則などのルールは複製せず、各規約の該当箇所へリンクする。

ツールや操作方法が変わった場合は本ガイドを更新し、規約には操作手順を追加しない。

### 4.11 `templates/`とリポジトリルートの`.github/`

#### テンプレートの役割

`templates/`には、設計書、ADRおよびMilestone・Epic・Ticketノートへ挿入するObsidianテンプレートを置く。

テンプレートは、記載漏れを防ぎ、読み手が同じ種類の情報を探しやすくする作業支援ファイルである。テンプレートファイル自体を、実際の設計書、ADR、Milestone、Epic、Ticketとして扱わない。

`設計書テンプレート.md`は、処理・振る舞い型と構造・契約型のどちらを使用するか選ぶ入口とする。実際に挿入する雛形は、`処理・振る舞い設計書テンプレート.md`と`構造・契約設計書テンプレート.md`を正本とする。

設計書テンプレートは帳票としてすべての見出しを強制せず、設計対象に不要な節を削除できる構成にする。選択基準と使用規則は第4.5節を正本とする。

ADRテンプレートは、Frontmatterと、背景、決定、検討した選択肢、結果と影響の記載漏れを防ぐ最小限の雛形とする。判断内容に不要な節を追加せず、現在仕様の詳細は設計書または機械可読な正本へ委ねる。

#### Pull Requestテンプレートの役割

リポジトリルートの`.github/pull_request_template.md`には、Pull Request作成時に記載する項目と完了確認を置く。規約本文の説明を複製せず、実際の作業時に確認する最小限の入力欄とチェック項目だけを記載する。

#### 正本の分担

設計書テンプレートとADRテンプレートで必要とする構成と使用規則は本規約、Milestone・Epic・Ticketテンプレートは[RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md)を正本とする。

具体的な操作方法は[RAGScope開発運用ガイド](../RAGScope開発運用ガイド.md)、実際に挿入される雛形は各テンプレートファイルを正本とする。

## 5. 文書間の整合

| 文書 | 確認する整合 |
|---|---|
| 要求定義 | RAGScope概要に示した目的、価値、対象範囲と矛盾しない |
| 設計書 | 関連する要求を実現し、上位設計と機械可読な正本に矛盾しない |
| 文書間リンク | ナビゲーションまたは根拠の参照であり、リンク元がリンク先の情報の正本にならない |

## 6. 命名・リンク・表記規則

### 6.1 ファイル・フォルダ名

- 人が管理・閲覧するMarkdownノートには、内容を直接理解できる日本語ファイル名を使用する。
- 構造を表すフォルダ、コード、設定ファイル、機械生成物には英語名を使用する。
- 外部ツールが認識するファイル名は、そのツールの規約を優先する。
- 英語のフォルダ名は、原則として小文字のkebab-caseとする。
- ADRは`ADR-<4桁の連番> <日本語タイトル>.md`とする。
- Milestone、Epic、Ticketの命名はRAGScopeプロジェクト管理規約に従う。

### 6.2 見出し・本文

- MarkdownのH1は、その文書の名称を明確に表す。原則としてファイル名に対応させるが、README、ADR、Milestoneなど、別規約またはテンプレートで形式を定める文書は、その形式に従う。
- 説明文は日本語を基本とする。
- APIパス、コード上の識別子、製品名、規格名、機械可読な定義の項目名、原表記によって意味を区別する必要がある技術用語は、原表記を使用してよい。
- 一般的な英語の設計用語を日本語文中へ置くだけでは意味が伝わりにくい場合は、対象、動作、結果が分かる具体的な日本語へ置き換える。
- 原表記を残す必要がある場合は、初出時に日本語で意味を説明する。
- 「処理」「情報」「管理」「基盤」などの抽象語だけでは責務や動作が曖昧になる場合は、誰が何を受け取り、何を行い、何を返すかが分かる表現を優先する。
- 読者が複数の英単語を頭の中で翻訳しなければ理解できない文章を避ける。ただし、無理な直訳によって正確さを損なわない。
- RAGScope固有のコンポーネント名と領域用語は、[システムアーキテクチャ「1.1 RAGScope固有の正式用語」](<../design/システムアーキテクチャ.md#1.1 RAGScope固有の正式用語>)を正本とし、人が読む文書では同じ意味に同じ正式用語を使用する。
- 実装言語は実装技術として記載し、コンポーネント名の代わりに使用しない。
- 正式用語の別名一覧を各文書へ複製しない。
- 新しいRAGScope固有の用語を定義する場合や既存用語の意味を変更する場合は、システムアーキテクチャの正式用語を更新する。

### 6.3 リンク

- 本文中のノート間リンクには、標準Markdownの相対リンクを使用する。
- リンクの解決はObsidianを優先し、GitHub上でも少なくともリンク先ファイルを参照できる形式を維持する。
- ファイル内の見出しへリンクする場合は、GitHubが生成するアンカーへ変換せず、`#`の後に実際の見出し名を見出し番号も含めて記載する。
- パスまたは見出し名に空白を含む場合は、リンク先全体を`<...>`で囲む。
- ファイルまたは見出しを移動・改名する場合は、同じ変更内で参照リンクを更新する。
- `milestone`・`epic`プロパティ内のリンク形式は、Obsidianメタデータ規約に従う。

例：

```markdown
[RAGScope概要](<../RAGScope概要.md>)
[文書処理設計](<../design/文書処理設計.md>)
[親子状態の整合](<./RAGScopeプロジェクト管理規約.md#6.1 親子状態の整合>)
```

### 6.4 Markdown表記

- FrontmatterはObsidianメタデータ規約に従う。
- Mermaid図内の改行には`<br>`を使用する。
- Callout、Mermaid、数式、Basesなどを使用する場合は、Obsidianで解釈できる形式にする。
- Obsidian固有の記法を使用する場合も、GitHub上の可読性を著しく損なわないようにする。
