# RAGScope文書管理規約

> [!abstract] この文書の役割
> RAGScopeにおける文書の配置、責務、正本、参照関係を定義する。  
> 「何をどこへ記載するか」を統一し、文書間の重複や矛盾を防ぐ。

## この規約の読み方

| 確認したいこと | 主な参照先 |
|---|---|
| 情報ごとの正本と履歴の分け方 | 第2章 |
| 文書とフォルダの配置 | 第3章 |
| 各文書に何を記載するか | 第4章 |
| 機能設計書の種類、構成、テンプレートの使い方 | 第4.5節 |
| 文書間で確認する整合と変更時の扱い | 第5章 |
| ファイル名、本文、リンク、Markdown表記 | 第6章 |
| Frontmatterの定義 | [Obsidianメタデータ規約](./Obsidianメタデータ規約.md) |
| Roadmap・Milestone・Epic・Ticketの運用 | [RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md) |

## 1. 適用範囲

### 対象となる文書

本規約は、RAGScopeリポジトリで人が作成・管理し、利用者または開発者が読む文書、および文書として管理する成果物へ適用する。

主な対象は次のとおりとする。ここに列挙されていない文書でも、同じ性質を持つものには本規約を適用する。

- リポジトリルートの`README.md`
- `project-docs/`直下の概要、要求定義
- `project-docs/rules/`
- `project-docs/design/`
- `project-docs/adr/`
- `project-docs/experiments/`
- `project-docs/project-management/`
- `project-docs/templates/`
- リポジトリルートの`.github/pull_request_template.md`

### 対象外

ソースコード、テストコード、migration、OpenAPIなどのAPI定義、設定、依存関係のロックファイル、CI/CD定義、ローカル開発環境・エディタ設定、ビルド生成物、一時ファイルには適用しない。

ただし、それらを機械可読な正本としてMarkdownと分担する方法は、第2.3節に従う。

一般的なAI・LLM・RAGの学習ノートは、本リポジトリへ置かない。

### 関連規約

- Frontmatterは[Obsidianメタデータ規約](./Obsidianメタデータ規約.md)に従う。
- Roadmap・Milestone・Epic・Ticketの運用は[RAGScopeプロジェクト管理規約](./RAGScopeプロジェクト管理規約.md)に従う。
- コードに共通する方針は[RAGScopeコーディング規約](./RAGScopeコーディング規約.md)、Haskell固有の方針は[Haskellコーディング規約](./Haskellコーディング規約.md)に従う。

## 2. 基本原則

### 2.1 1つの情報に1つの正本を設ける

| 情報 | 正本 |
|---|---|
| RAGScopeの目的、価値、想定利用方法、主な能力の概要 | `RAGScope概要.md` |
| 機能・品質・制約・対象範囲・対象外の詳細 | `RAGScope要求定義.md` |
| 現在採用しているシステム・機能の設計 | `design/` |
| 重要な設計判断の背景、選択肢、理由 | `adr/` |
| 仮説、検証条件、結果、考察 | `experiments/` |
| バージョン計画と作業の進行記録 | `project-management/` |
| 正確な実装、型、Schema、テスト | コード、migration、OpenAPI、JSON Schema、テストなど |

同じ情報を複数の文書で正本として管理しない。別の文書で触れる場合は、必要な要約と正本への相対リンクだけを置く。

`README.md`は、リポジトリまたは文書領域の入口と索引であり、要求、設計、判断、実験結果、進捗の正本ではない。

### 2.2 現在仕様と履歴を分ける

| 記録する内容 | 記録先 |
|---|---|
| 現在有効な要求 | 要求定義 |
| 現在採用している設計 | 設計書 |
| 重要な判断の背景、選択肢、決定、影響 | ADR |
| 実際に行った検証と得られた結果 | 実験記録 |
| 個別の変更作業、完了条件、実施結果 | Ticket |
| ファイルの変更履歴 | Git |

現在仕様を理解するために、過去のTicket、Milestone、変更履歴を読むことを必須にしない。

### 2.3 機械可読な仕様を優先する

正確な定義をコードや専用形式で表現できる場合は、それを正本とする。

| 内容 | 正本 |
|---|---|
| DBのテーブル・カラム・制約 | migration |
| APIの正確なSchema | OpenAPIなどのAPI定義 |
| Haskell・Pythonの型 | ソースコード |
| CLIの正確な選択肢 | 実装と`--help` |
| JSON契約の項目、型、必須条件 | JSON Schema |
| 具体的なテストケース | テストコード |
| パッケージのバージョン | ロックファイル・設定ファイル |

Markdownには、実装やSchemaだけでは分かりにくい責務、意味、理由、契約、不変条件、処理フロー、変更の影響を記載する。機械可読な定義を逐語的に複製しない。

### 2.4 必要な文書と情報だけを残す

- 具体的な内容と利用目的が生じた時点で文書を作成する。
- 将来必要になる可能性だけを理由に、空文書、空フォルダ、未使用の管理階層を作らない。
- 既存文書で責務を自然に扱える場合は、その文書を更新する。
- 1つの文書が異なる読者の問いや責務を扱うようになった場合に分割する。
- 見出し数、行数、文字数を目標にしない。
- 内容の薄い節、正本への導線だけの節、別の節の言い換えだけの節を残さない。

## 3. 文書の配置

| 場所 | 置く文書・成果物 |
|---|---|
| リポジトリルート | `README.md` |
| `.github/` | Pull RequestなどGitHubが直接利用するテンプレート |
| `project-docs/`直下 | 概要、要求定義 |
| `project-docs/rules/` | 文書、メタデータ、プロジェクト管理、コードに関する規約 |
| `project-docs/design/` | `README.md`による索引、システムアーキテクチャ、機能別設計書 |
| `project-docs/adr/` | 重要な設計判断 |
| `project-docs/experiments/` | 実際に行った検証の記録 |
| `project-docs/project-management/` | プロジェクト運用ガイド、Roadmap、Milestone、Epic、Ticket |
| `project-docs/templates/` | Obsidianへ挿入する文書の雛形 |

配置では次を守る。

- 上表の`project-docs/`配下の各フォルダには、複数の文書を読み分ける必要が生じた場合、`README.md`を配置してよい。READMEはそのフォルダの索引とし、各文書の責務、関係、参照順を必要最小限に示す。
- 機能別設計書は、技術要素ではなく設計対象となる機能・責務で分ける。
- `experiments/`は、最初の実験記録が生じた時点で作成する。
- Roadmap、Milestone、Epic、Ticketの配置と構成は、RAGScopeプロジェクト管理規約を正本とする。
- テンプレートと`.github/pull_request_template.md`の具体的な利用手順は、`project-management/RAGScopeプロジェクト運用ガイド.md`へ記載する。

## 4. 文書ごとの責務

### 4.1 `README.md`

READMEは、配置された範囲の入口と索引を担当する。README自身に要求、設計、判断、実験結果、進捗を正本として持たせない。

#### リポジトリルートの`README.md`

リポジトリ全体の入口として、次を簡潔に示す。

- RAGScopeの短い説明
- RAGScopeについて知りたい読者を、概要と要求定義へ案内する導線
- RAGScopeを開発したい読者を、システムアーキテクチャ、コンポーネントREADME、Roadmap、プロジェクト運用ガイド、コーディング規約へ案内する導線
- リポジトリ内の主要コンポーネントと文書領域の概要

目的、価値、対象範囲は`RAGScope概要.md`、詳細な要求は`RAGScope要求定義.md`を正本とし、READMEには必要な要約と導線だけを置く。

コンポーネント固有の開発環境、実行、整形、テスト、品質検査の手順は各コンポーネントのREADMEへ記載し、リポジトリルートのREADMEへ重複させない。

作業中のMilestone名や一時的な`status`を手作業で転記しない。開発予定はRoadmap、現在状態は各ノートのFrontmatterとBases・検索から確認する。

#### `project-docs/`配下の`README.md`

文書を配置したフォルダの索引として、次を必要最小限に示す。

- 各文書が答える中心的な問いまたは責務
- 文書同士の関係
- 読む順序がある場合の参照順

リンク先の要求、設計、判断、実験結果、進捗をREADMEへ複製せず、標準Markdownの相対リンクで正本へ案内する。文書同士の関係を俯瞰するために、表またはMermaidを使用してよい。

### 4.2 `RAGScope概要.md`

RAGScopeというアプリケーションの概要の正本とし、次を高い粒度で記載する。

- 解決する問題
- 提供する価値
- 想定する利用方法
- 主な能力
- 対象範囲と対象外の概要

詳細かつ検証可能な要求は`RAGScope要求定義.md`、技術選定と実現方法は設計書、バージョン計画はRoadmapを正本とする。

### 4.3 `RAGScope要求定義.md`

RAGScopeが満たすべき内容の正本とし、機能要件、非機能要件、制約、対象外、必要な識別子と確認方法を記載する。

要求定義には「何を満たすか」を記載し、「どのコンポーネント、型、DB、ライブラリで実現するか」は設計書または機械可読な正本へ委ねる。

### 4.4 `design/`

`design/`全体を、現在採用しているRAGScopeのシステム・機能設計の正本とする。`design/README.md`は設計書を読み分けるための索引とし、設計内容は各設計書を正本とする。

#### `システムアーキテクチャ.md`

システム全体のコンポーネント構成、責務、依存方向、通信、主要な処理・データフロー、配置・実行環境の基本方針を記載する。

システム全体を扱う特別な文書であり、第4.5節の機能別設計テンプレートへ機械的に合わせない。

#### 機能別設計書

対象機能について、完了後も有効な現在設計を記載する。Ticketごとに新しい設計書を作らず、既存文書で責務を自然に扱える場合は更新する。異なる機能または異なる中心的な問いを扱う場合に分割する。

過去のTicketや変更記録を先に読まなくても、現在採用している設計を理解できる状態にする。判断理由を詳しく残す必要がある場合はADRへリンクする。

### 4.5 機能設計の種類と構成

#### テンプレートの選択

機能別設計書を新規作成する場合は、[設計書テンプレートの選択](../templates/設計書テンプレート.md)から、読者が最初に答えを得たい問いに合うテンプレートを1つ選ぶ。

| 種類 | 中心となる問い | 主な対象 | テンプレート |
|---|---|---|---|
| 処理・振る舞い設計書 | 何が、どの順序で、どの条件に従って処理されるか | 入出力、処理段階、分岐、状態変化、正常系・異常系、後続処理への受け渡し | [処理・振る舞い設計書テンプレート](../templates/処理・振る舞い設計書テンプレート.md) |
| 構造・契約設計書 | 何を共有し、それぞれが何を意味し、どの規則を守るか | 項目、語彙、形式、識別子、公開範囲、不変条件、機械可読な正本 | [構造・契約設計書テンプレート](../templates/構造・契約設計書テンプレート.md) |

両方の性質を持つ場合は、主となるテンプレートへ、もう一方から必要な節だけを加える。2つを単純に結合した全部入りの文書にしない。

どちらにも自然に適合しない設計対象が実際に生じた場合は、文書の分割または設計対象の再定義を検討する。将来の可能性だけを理由に3つ目のテンプレートを先行作成しない。

#### 必要な情報と章立て

機能別設計書には、設計対象に該当する次の情報を含める。

| 情報 | 読者が判断できること |
|---|---|
| 文書の役割と主要な結果 | 何の設計で、何を可能にするか |
| 現在の適用範囲と明示的な対象外 | どこまでが現在設計か |
| 責務と境界 | 誰が何を担当し、どこで他機能へ引き渡すか |
| 関連する要求・上位設計への導線 | 何を実現し、どの上位方針に従うか |
| 設計対象の中心となる処理または契約 | 実装がどの規則を守るか |
| 必要な不変条件、失敗時の扱い、受け渡し | 正常・異常時に何を保証するか |
| 機械可読な正本への導線 | 正確な型、Schema、設定、テストをどこで確認するか |

これらは**必要な情報**であり、独立した章、固定の章名、固定の章番号を要求するものではない。関連する要求と上位設計も、本文の理解を中断する独立章へ機械的に集約せず、冒頭の短い表、関係する節、または末尾の関連文書など、最も自然な場所へ必要最小限置く。

基本設計と詳細設計は設計の粒度として扱い、固定の章名や文書構成を要求しない。基本設計と詳細設計で、主な読者、責務、利用目的または中心となる問いが異なる場合は、別の設計書として分離する。詳細設計は必要な基本設計を前提として参照し、同じ設計内容を重複して正本化しない。分離する意味がなく、同じ読者の問いへ一続きに答える方が自然な場合は、同じ文書または節で扱う。

#### テンプレートの使い方

テンプレートは帳票ではなく、構成を検討し、記載漏れを防ぐための骨組みである。

- テンプレートを挿入した後、設計対象に不要な見出しを削除する。
- 近接して読む必要がある情報は統合し、章を往復させない。
- 最も頻繁に確認される全体像、代表例、主要な規則を文書の前半へ置く。
- 責務分担、対象外、正本、Ticket、将来事項を、主要な設計内容より前へ大量に置かない。
- Ticket、Milestone、作業記録を現在設計の本文へ複製しない。
- テスト観点、将来事項、変更時の注意、未決定事項は、本文と異なる設計固有の情報がある場合だけ追加する。
- 同じ規則を概要、詳細、表、図、テスト、変更時の注意で繰り返さない。
- 正確な型、Schema、OpenAPI、migration、設定、テストケースをMarkdownへ複製しない。

#### 読みやすい表現

設計書は、最初から順番に読まなくても、見出しと視覚表現から全体像、情報の階層、必要な規則の場所を把握できる構成にする。

| 内容 | 優先する表現 |
|---|---|
| 処理の順序、分岐、コンポーネント間の流れ | Mermaidまたは簡潔なフロー |
| 項目の対応、条件ごとの差、責務の比較 | 表 |
| データの代表的な形、識別子の組み立て | JSONやテキストなどのコード例 |
| 特に重要な制約、注意、補足 | Callout |
| 背景、理由、表や図だけでは伝わらない意味 | 短い文章 |

表や図の目的が明らかな場合は、内容の言い換えだけの導入を追加しない。具体的な値やアルゴリズムを図へ詰め込まず、詳細の正本へ委ねる。文章を機械的に分割したり、すべてを表へ変換したりしない。

#### 作業記録との分離

今回の変更目的、作業範囲、完了条件、実施結果はEpic・Ticketへ記録し、機能設計書には完了後も有効な現在設計を記載する。

重要な設計判断の理由はADR、実測や比較を伴う検証はExperimentへ記録する。

### 4.6 `adr/`と`experiments/`

#### ADR

ADRは、重要な設計判断の背景、決定、検討した選択肢、結果と影響を記録する。

次のいずれかに該当する場合に作成する。

- 複数の現実的な選択肢がある。
- 変更コストが高い。
- 複数の機能やシステム全体へ影響する。
- 判断理由を残さなければ、同じ議論を繰り返す可能性がある。

局所的で容易に変更できる実装詳細までADRにしない。新規作成時は[ADRテンプレート](../templates/ADRテンプレート.md)を使用する。

判断が変わった場合は採用済みADRを黙って書き換えず、新しいADRを作成して旧ADRを`superseded`へ変更する。

#### Experiment

Experimentは、仮説、条件、手順、結果、失敗例、解釈、次の判断を伴う実際の検証記録とする。

一般知識の解説や単なる実装作業の記録は置かない。結果が重要な設計判断につながった場合は、ADRから該当する実験記録へリンクする。

### 4.7 規約、プロジェクト管理、プロジェクト運用ガイド、テンプレート

| 場所・文書                                       | 責務                                                     |
| ------------------------------------------- | ------------------------------------------------------ |
| `rules/`                                    | 文書管理、Obsidianメタデータ、プロジェクト管理、コードに関する判断基準を定義する           |
| `project-management/`                       | Roadmap、Milestone、Epic、Ticketによる計画と進行記録を管理する           |
| `project-management/RAGScopeプロジェクト運用ガイド.md` | ノート作成、Ticket着手、ブランチ、Pull Request、リリースなどの具体的な操作手順を一元化する |
| `templates/`                                | Obsidianへ挿入する設計書、ADR、Milestone、Epic、Ticketの雛形を置く       |
| `.github/pull_request_template.md`          | Pull Request作成時に入力・確認する最小限の項目を置く                       |

規約には判断基準を記載し、操作手順はプロジェクト運用ガイドへ委ねる。要求や設計の現在内容をプロジェクト管理文書だけに記載しない。

テンプレートは記載漏れを防ぐ作業支援ファイルであり、実際の設計書、ADR、Milestone、Epic、Ticketとして扱わない。選択基準と使用規則は本規約、実際に挿入する雛形は各テンプレート、具体的な操作方法はプロジェクト運用ガイドを正本とする。

Milestone・Epic・Ticketテンプレートの構成は、RAGScopeプロジェクト管理規約を正本とする。

## 5. 文書間の整合と更新

### 5.1 確認する整合

| 文書 | 確認すること |
|---|---|
| README | 配置された範囲の索引に限定し、リンク先の正本内容を複製していない |
| 概要 | 要求定義の詳細と矛盾せず、高い粒度の入口になっている |
| 要求定義 | 概要に示した目的、価値、対象範囲と矛盾しない |
| 設計書 | 関連する要求を実現し、上位設計と機械可読な正本に矛盾しない |
| ADR | 現在設計から参照でき、決定内容が設計書と矛盾しない |
| Experiment | 実際の条件と結果を記録し、推測を結果として扱っていない |
| プロジェクト管理文書 | 要求・設計の現在内容を複製せず、作業の目的・状態・結果を記録している |
| 文書間リンク | ナビゲーションまたは根拠の参照であり、リンク元がリンク先の正本を奪っていない |

### 5.2 作成・更新時の確認

文書を作成または更新するときは、変更前に対象文書、参照元、参照先、関連する正本を確認する。変更後は少なくとも次を確認する。

- 文書の責務が他の文書と重複していない。
- 現在仕様と作業記録を混在させていない。
- 関連する要求、設計、ADR、Experiment、Milestone、Epic、Ticketと矛盾しない。
- コード、テスト、Contract、Schema、migration、設定などの正本と矛盾しない。
- ファイルまたは見出しの移動・改名に伴う参照リンクを同じ変更内で更新している。
- 内容の薄い節、重複した説明、不要になった導線を残していない。
- 依頼と無関係な文書を変更していない。

既存ファイルを削除して同名ファイルを新規作成する方法は原則として使用せず、パスとGit履歴の連続性を保つ。

## 6. 命名・リンク・Markdown表記

### 6.1 ファイル・フォルダ名

- 人が管理・閲覧するMarkdownノートには、内容を直接理解できる日本語ファイル名を使用する。
- 構造を表すフォルダ、コード、設定ファイル、機械生成物には英語名を使用する。
- 外部ツールが認識するファイル名は、そのツールの規約を優先する。
- 英語のフォルダ名は、原則として小文字のkebab-caseとする。
- ADRは`ADR-<4桁の連番> <日本語タイトル>.md`とする。
- Milestone、Epic、Ticketの命名はRAGScopeプロジェクト管理規約に従う。

### 6.2 見出し・本文

- H1は文書の名称を明確に表し、原則としてファイル名に対応させる。
- README、ADR、Milestoneなど、別規約またはテンプレートで形式を定める文書は、その形式に従う。
- 説明文は日本語を基本とする。
- APIパス、コード上の識別子、製品名、規格名、機械可読な項目名、原表記で意味を区別する技術用語は、原表記を使用してよい。
- 一般的な英語の設計用語を置くだけで意味が伝わりにくい場合は、対象、動作、結果が分かる日本語を優先する。
- 「処理」「情報」「管理」「基盤」などの抽象語だけで責務が曖昧になる場合は、誰が何を受け取り、何を行い、何を返すかが分かる表現にする。
- RAGScope固有のコンポーネント名と領域用語は、[システムアーキテクチャ「1.1 RAGScope固有の正式用語」](<../design/システムアーキテクチャ.md#1.1 RAGScope固有の正式用語>)を正本とする。
- 新しいRAGScope固有の用語を定義する場合や既存用語の意味を変更する場合は、システムアーキテクチャの正式用語を更新する。

### 6.3 リンク

- 本文中のノート間リンクには、標準Markdownの相対リンクを使用する。
- Obsidianで解決でき、GitHub上でも少なくともリンク先ファイルを参照できる形式を維持する。
- 見出しへリンクする場合は、`#`の後に実際の見出し名を見出し番号も含めて記載する。
- パスまたは見出し名に空白を含む場合は、リンク先全体を`<...>`で囲む。
- ファイルまたは見出しを移動・改名する場合は、同じ変更内で参照リンクを更新する。
- `milestone`・`epic`プロパティ内のリンク形式は、Obsidianメタデータ規約に従う。

例：

```markdown
[RAGScope概要](<../RAGScope概要.md>)
[文書処理設計](<../design/文書処理設計.md>)
[親子状態の整合](<./RAGScopeプロジェクト管理規約.md#6.1 親子状態の整合>)
```

### 6.4 Markdown表記

- FrontmatterはObsidianメタデータ規約に従う。
- Mermaid図内の改行には`<br>`を使用する。
- Callout、Mermaid、数式、Basesなどを使用する場合は、Obsidianで解釈できる形式にする。
- Obsidian固有の記法を使用する場合も、GitHub上の可読性を著しく損なわないようにする。
