# Haskellコーディング規約

> [!abstract] この文書の役割
> RAGScopeアプリケーションのHaskellコードへ適用する、モジュール、型、関数、Haddock、エラー、`IO`、整形、検証の規約を定義する。  
> 言語に共通する方針は[RAGScopeコーディング規約](./RAGScopeコーディング規約.md)に従う。

## 1. 適用範囲

本規約は、`ragscope-app/`配下のHaskellソースコードとテストコードへ適用する。

JSON、HTTP、DBなどの外部契約は、対応するJSON Schema、OpenAPI、migrationを正本とする。Haskellコードでは、外部契約と対応する意味を型で表現し、文字列やJSONへの変換を境界へ集める。

## 2. 設定と整形

### 2.1 機械可読な正本

| 内容 | 正本 |
|---|---|
| Haskellコードのレイアウト | [`ragscope-app/fourmolu.yaml`](../../ragscope-app/fourmolu.yaml) |
| 文字コード、改行、インデント | [`.editorconfig`](../../.editorconfig) |
| 言語、依存、warning、公開モジュール | [`ragscope-app/ragscope.cabal`](../../ragscope-app/ragscope.cabal) |
| 具体的な型と関数 | Haskellソースコード |
| 具体的なテストケース | Haskellテストコード |
| 整形、ビルド、テスト、Haddockの実行入口 | [`Makefile`](../../Makefile) |

Fourmoluによる整形結果を正規形とする。手作業で特定のレイアウトを維持するためにformatterと競合しない。

`FOURMOLU_DISABLE`などで自動整形を無効化するのは、外部生成コードなど、整形すると目的を満たせない場合に限定する。使用する場合は、無効化する理由と最小範囲をコメントで説明する。

整形と検証は、リポジトリルートの`Makefile`を再現可能な入口とする。`make format`で整形し、`make format-check`で差分を発生させずに整形状態を検査する。`make check`は、整形検査、ビルド、テスト、Haddock生成をまとめて実行する。

### 2.2 warningを放置しない

プロジェクトで有効にしたGHC warningは、原則として解消する。warningを無効化する場合は、対象を最小限にし、コードまたは設定から理由を追跡できるようにする。

## 3. 命名

Haskellの一般的な慣習へ従い、RAGScope内で統一する。

| 対象 | 形式 | 例 |
|---|---|---|
| モジュール | `UpperCamelCase`を`.`で区切る | `RAGScope.Logging.Types` |
| 型、型クラス、データコンストラクタ | `UpperCamelCase` | `ExecutionId`、`ServiceContext` |
| 関数、変数、レコードフィールド | `lowerCamelCase` | `encodeLogEvent`、`executionId` |
| 型変数 | 短い小文字 | `a`、`err` |

名前は意味を優先するが、すべての条件を名前へ埋め込んで長文化しない。型とモジュールで文脈が明確な場合は、重複する接頭辞を避ける。

1文字名は、短いラムダ、局所的な変換、慣習的な型変数など、意味を失わない狭い範囲に限定する。

独自演算子は、演算子として表すことが問題領域に自然で、通常の関数名より読みやすい場合だけ定義する。

## 4. Haddockとコメント

本規約における公開APIとは、原則として`ragscope.cabal`の`exposed-modules`に指定したライブラリモジュールと、そこからexportする要素を指す。

executable、test-suite、`other-modules`に置く内部モジュールは利用者向けAPIとして扱わない。これらには、[RAGScopeコーディング規約](./RAGScopeコーディング規約.md)に従い、責務や非自明な制約を説明するために必要なコメントを記述する。`main`であることだけを理由に利用者向けHaddockを要求しない。

### 4.1 モジュールコメント

`exposed-modules`に指定するライブラリモジュールには、モジュール宣言の直前へHaddockコメントを記述する。

モジュールコメントでは、必要に応じて次を説明する。

- モジュールが担当する責務
- モジュールが担当しない責務
- 主な型や処理の関係
- 利用時に守る不変条件または境界

```haskell
-- | RAGScopeアプリケーションの構造化ログで共通利用する基本型を定義する。
--
-- ログイベントの組み立て、JSON変換、出力は別の責務として扱う。
module RAGScope.Logging.Types (...) where
```

### 4.2 公開要素のHaddock

公開APIとしてexportするモジュール、型、型クラス、データコンストラクタ、レコードフィールド、関数にはHaddockコメントを記述する。

コメントでは、型シグネチャだけでは伝わらない次の内容を優先する。

- 値または処理が表す意味
- 生成、引き継ぎ、単位、時刻、順序などの規則
- 引数と戻り値の関係
- 失敗条件と副作用
- 使用してはいけない状況

データコンストラクタやレコードフィールドも、同じ型のほかの選択肢との違いが分かるようにする。

### 4.3 Haddockと通常コメントを使い分ける

Haddockは公開APIの説明であり、処理内部の意図を説明する通常コメントの代わりではない。

非公開関数や処理内部でも、次の場合は通常コメントを記述する。

- 自明でない不変条件がある
- 外部仕様に合わせるための変換がある
- 意図的に一般的な実装と異なる
- 複数段階の処理を視覚的に区切る必要がある
- 将来の単純化で壊れやすい理由がある

長い`do`ブロックをコメントだけで区切るのではなく、各段階を名前の付いた関数へ分割できないか検討する。

### 4.4 Haddockを検証する

Haddockの参照、コード表記、箇条書きが解釈でき、ドキュメントを生成できることを確認する。

型や関数を改名、移動、非公開化した場合は、関連するHaddock参照とモジュール説明を同じ変更で更新する。

## 5. 型と公開API

### 5.1 不正な状態を表現しにくくする

文字列、真偽値、複数の`Maybe`を組み合わせて状態を表す前に、`newtype`、直和型、直積型、スマートコンストラクタで意味と制約を表現できないか検討する。

例：

```haskell
newtype ExecutionId = ExecutionId UUID

data EventContext
  = ExecutionContext ExecutionId
  | ServiceContext
```

この形では、`execution`なのに`execution_id`がない状態と、`service`なのに`execution_id`がある状態を通常の値として作らない。

### 5.2 プリミティブな値を役割ごとに区別する

同じ基礎型でも意味が異なる値は、取り違えの可能性と利用範囲を考慮して`newtype`などで区別する。

外部契約の識別子、時刻、単位付き数値、エラーコードを、生の`Text`、`String`、`Int`として広範囲へ渡さない。

### 5.3 公開APIを最小化する

モジュールのexport listを明示し、利用側が必要とする型と関数だけを公開する。

不変条件を守るために生成経路を限定する必要がある型は、コンストラクタを非公開にし、スマートコンストラクタまたは専用の組み立て関数を公開する。

将来使うかもしれない関数や内部表現を先行して公開しない。

### 5.4 型シグネチャを明示する

トップレベル関数には型シグネチャを記述する。型シグネチャを、実装の確認だけでなく、責務と境界を示す設計の一部として扱う。

局所関数の型が複雑、推論しにくい、または意図を明確にする場合は、局所的にも型シグネチャを記述する。

### 5.5 derivingを必要な範囲に限定する

`Eq`、`Ord`、`Show`、`Enum`、`Bounded`などは、利用目的があるものだけを導出する。便利そうという理由だけで、意味の適合を確認せずに追加しない。

特に`Show`の結果を、永続化形式、外部契約、利用者向け表示、構造化ログとして使用しない。専用の変換を定義する。

## 6. 関数、純粋処理、IO

### 6.1 純粋な中心と副作用の境界を分ける

検証、変換、判断、組み立てなどは、可能な範囲で純粋関数として実装する。ファイル、時計、乱数、ネットワーク、DB、標準入出力などの副作用は境界へ集める。

```text
外部入力・IO → 境界で変換 → 純粋な処理 → 境界で出力・IO
```

純粋処理と`IO`を分けることで、失敗条件とテスト対象を明確にする。

### 6.2 小さな責務へ分割する

関数は、名前で説明できる1つの責務を持たせる。長い`do`ブロック、深いcase式、複数の変換段階は、意味のある関数へ分割する。

ただし、1回しか使わない小さな式を機械的にトップレベル関数へ移し、処理の流れをかえって追いにくくしない。分割後の名前が処理の意味を増やすかを判断する。

### 6.3 宣言的な表現を優先する

`map`、`fold`、関数合成、パターンマッチ、代数的データ型などが処理を自然に表す場合は採用する。

ポイントフリースタイル、過度な演算子、抽象度の高い型クラスを使うことで読み手が型とデータの流れを追いにくくなる場合は、引数と中間値を明示する。

Haskellらしさは、技巧的な短さではなく、型、純粋性、合成可能性によって問題の構造を明確にすることとして扱う。

### 6.4 パターンマッチを網羅する

直和型の分岐は、可能な範囲で網羅的に扱う。将来コンストラクタが追加されたときに見落としを検出できるよう、意味のないワイルドカードで分岐をまとめない。

ワイルドカードが適切な場合は、その範囲のすべてを同じ意味で扱えることが明らかな場所に限定する。

## 7. エラーと部分関数

### 7.1 予想できる失敗を型で表す

入力不正、資源不足、依存先失敗など、呼び出し側が処理すべき失敗は、`Either`などの戻り値で表現する。

`Maybe`は値がないこと自体が十分な意味になる場合に使用する。失敗理由を呼び出し側が必要とする場合は`Either`を使用する。

例外は、外部ライブラリや`IO`境界から発生する予期しない失敗、またはHaskellの慣習上例外で通知される失敗を受け取るために使用する。責務の境界でRAGScopeのエラー型へ変換する。

### 7.2 部分関数を原則として使用しない

`head`、`tail`、`init`、`last`、`!!`、`fromJust`、`read`、`error`、`undefined`など、通常の入力で実行時失敗を起こし得る部分関数は原則として使用しない。

代わりに、パターンマッチ、安全な変換関数、`NonEmpty`などの型、`Maybe`、`Either`を使用する。

内部不変条件により失敗しないことを証明でき、代替が著しく複雑になる場合だけ例外を検討する。その場合は次を満たす。

- 不変条件を型または直前の検証で確認できる
- なぜ安全かをコメントで説明する
- 不変条件を確認するテストがある
- 利用範囲を最小限に限定する

### 7.3 例外を握りつぶさない

広い例外を捕捉して成功扱いにしたり、情報を失ったまま別の値へ置き換えたりしない。

捕捉する例外の範囲、RAGScopeのエラーへの変換、利用者へ公開する情報、ログへ記録する情報を分ける。

`SomeException`などの広い型を捕捉する場合も、非同期例外を通常の失敗へ変換または握りつぶさない。必要なクリーンアップを行った後、非同期例外を再送出する。広い例外捕捉を共通化する場合は、同期例外だけを処理することがAPIと実装から分かる形にする。

## 8. モジュールと依存関係

### 8.1 責務でモジュールを分ける

モジュールは、型、組み立て、変換、境界、出力処理など、説明可能な責務で分ける。

`Utils`、`Common`などの広い名前へ、変更理由の異なる処理を集めない。共通化する場合も、共通であることではなく、何を担当するかをモジュール名で表す。

### 8.2 ファイルの長さを確認する

[RAGScopeコーディング規約「4.3 行数を分割検討の信号として使う」](<./RAGScopeコーディング規約.md#4.3 行数を分割検討の信号として使う>)の目安を使用する。

Haskellモジュールでは、次の場合に行数にかかわらず分割を検討する。

- 型定義と`IO`実装が増え、モジュールの責務を一文で説明できない
- export listから利用方法を把握しにくい
- importが異なる技術領域へ広がる
- テスト対象を責務ごとに分離しにくい
- Haddockの節が複数の独立した目的を説明している

### 8.3 依存方向を守る

純粋な型とドメイン処理から、標準エラー出力、HTTP、DBなどの具体的な境界実装へ依存しない。

循環importを避けるためだけの巨大な共通モジュールを作らず、型と責務の配置を見直す。

### 8.4 言語拡張を限定する

プロジェクトの既定言語を基準とし、追加の言語拡張は、型安全性または可読性を明確に改善する場合だけ使用する。

モジュール固有の拡張をプロジェクト全体へ広げる前に、ほかのモジュールでも同じ理由があるか確認する。高度な拡張を使用する場合は、必要性がコードとコメントから理解できるようにする。

## 9. テスト

- 純粋関数は、入力と出力、境界値、失敗値を直接検査する。
- `IO`を伴う処理は、時計、ID生成、出力先などを必要に応じて差し替え、意味のある結果を検査する。
- 型で排除した不正状態は、無理に実行時テストで再現せず、型の生成境界と変換をテストする。
- JSONなどの外部契約は、文字列比較や項目順だけに依存せず、対応するSchemaと意味を検査する。
- テストコードにも型シグネチャ、分かりやすい名前、必要なコメントを記述する。

## 10. レビュー時の確認

- `exposed-modules`に指定したモジュールに責務を説明するモジュールHaddockがある
- 公開APIとしてexportする型、コンストラクタ、フィールド、関数にHaddockがある
- 内部の自明でない処理へ通常コメントがあり、Haddockだけで済ませていない
- 長い関数や`do`ブロックを、意味のある関数へ分割できないか検討している
- 型によって不正な状態や値の取り違えを防いでいる
- export listが必要最小限になっている
- トップレベル関数に型シグネチャがある
- 純粋処理と`IO`の境界が分かる
- 部分関数を避け、失敗を`Maybe`、`Either`、共通エラーなどで表現している
- `make check`を実行し、Fourmolu、GHC warning、ビルド、テスト、Haddock生成を確認している
- Contract、Schema、設計とHaskell実装が矛盾していない
