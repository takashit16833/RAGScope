# RAGScopeコーディング規約

> [!abstract] この文書の役割
> RAGScopeのソースコードに共通して適用する、読みやすさ、責務分離、コメント、命名、ファイル構成、検証の原則を定義する。  
> 言語固有の構文、命名形式、formatter、型、例外処理は、言語別コーディング規約と機械可読な設定を正本とする。

## この規約の読み方

| 確認したいこと | 主な参照先 |
|---|---|
| 規約と設定ファイルの優先関係 | 第2章 |
| コメントをどこへ何のために書くか | 第3章 |
| 関数・処理・ファイルの分割 | 第4章 |
| 名前の付け方 | 第5章 |
| エラー、境界、依存関係の扱い | 第6章 |
| テストとレビュー | 第7章・第8章 |
| Haskell固有の規約 | [Haskellコーディング規約](./Haskellコーディング規約.md) |

## 1. 適用範囲

本規約は、RAGScope正本リポジトリのソースコード、テストコード、補助スクリプトへ適用する。

Haskellには[Haskellコーディング規約](./Haskellコーディング規約.md)を併せて適用する。Pythonなど、別の言語で具体的な実装が始まった場合は、実際に採用したformatter、linter、型検査、テスト構成に基づいて言語別規約を追加する。

## 2. 基本原則と正本

### 2.1 優先する品質

コードは、次の順序を基本として判断する。

1. 要求、設計、Contract、Schemaを満たし、正しく動作する
2. 不正な状態や誤用を作りにくい
3. 読み手が責務、処理の流れ、失敗条件を把握しやすい
4. 変更の影響範囲を限定できる
5. 必要な性能と資源条件を満たす

短さ、抽象度の高さ、技巧的な表現だけを目的にしない。関数的・宣言的な表現や抽象化は、処理の意味を明確にし、安全性と保守性を高める場合に採用する。

### 2.2 機械可読な設定を正本とする

次の内容は、対応する設定ファイルとツールの実行結果を正本とする。

| 内容 | 主な正本 |
|---|---|
| 文字コード、改行、インデント | [`.editorconfig`](../../.editorconfig) |
| 言語固有の整形 | formatterの設定 |
| warning、lint、型検査 | ビルド設定、linter、型検査設定、CI |
| 具体的な型と公開API | ソースコード |
| 具体的なテストケース | テストコード |

本規約には、設定値を逐語的に複製せず、設定だけでは表せない意図、判断基準、責務を記載する。

formatterまたはlinterによる正規形と、手作業のレイアウトを競合させない。例外的に自動整形を無効化する場合は、その必要性と範囲をコード上のコメントで説明する。

## 3. コメント

### 3.1 必要なコメントを必ず記述する

実装上の責務または非自明な処理を持つソースファイルには、コードだけでは把握しにくい責務、意図、制約、処理のまとまりを伝えるコメントを必ず記述する。

処理を別の関数やモジュールへ委譲するだけの数行のentry pointなど、ファイル名、型、関数名と構造だけで責務が明らかな場合は、内容を言い換えるだけのファイルコメントを機械的に追加しない。非自明な責務、制約、処理が加わった時点で必要なコメントを追加する。

少なくとも次を対象とする。

- ファイルまたはモジュールが担当する責務と境界
- 公開する型、関数、クラス、主要な構成要素の意味
- 自明でない前提条件、不変条件、失敗条件
- 設計上の理由があり、単純化や削除を誤って行いやすい処理
- 外部仕様、Schema、時刻、ID、順序、副作用などに関する注意
- 複数段階からなる長い処理の区切り

> [!important] コメントの目的
> コメントの量を増やすことではなく、コード単体よりも、コードとコメントを併せて読んだ方が責務と流れを明らかに理解できる状態を作る。

### 3.2 コメントへ書く内容

コメントは、コードの構文を日本語へ置き換えるのではなく、主に「なぜそうするか」「何を守るか」「どこまで担当するか」を説明する。

適切な例：

```text
同じ実行に属するログへ同じexecution_idを引き継ぐため、
コマンド境界で一度だけ生成する。
```

避ける例：

```text
execution_idを生成する。
```

変数名や関数名だけで十分に意味が分かる単純な1行へ、同じ内容のコメントを機械的に追加しない。

### 3.3 長い処理をコメントで構造化する

処理が複数の意味ある段階から成る場合は、短いコメントで段階を示し、読み手が上から流れを追えるようにする。

ただし、1つの関数内へ多数の見出しコメントが必要になる場合は、コメントだけで長さを覆い隠さず、各段階を名前の付いた関数へ分割できないか先に検討する。

### 3.4 コメントをコードと同期する

コード変更によって責務、前提、順序、エラー条件が変わった場合は、同じ変更でコメントを更新する。

古い説明、実装と異なる説明、未確定の予定を現在の動作として残さない。コメントが誤解を生む場合は、コメントがない場合より危険である。

## 4. 関数、処理、ファイルの構成

### 4.1 意味のある単位へ分割する

関数は、可能な範囲で1つの説明可能な責務を持たせる。長い一連の処理は、入力の検証、変換、判断、副作用、結果の組み立てなど、意味のある段階へ分割する。

分割した関数には、処理内容を読み手が推測できる名前を付ける。単に行数を減らすためだけの、責務が説明できない細切れ関数は作らない。

### 4.2 見通しを良くする

次の状態を避ける。

- 深いネストが続き、正常系の流れを追いにくい
- 1つの関数が検証、I/O、変換、ログ、エラー表示をすべて担当する
- 同じ条件分岐や変換が複数箇所へ重複する
- 呼び出し元が実装詳細を知りすぎる
- 関数名より本体を読まなければ処理段階が分からない

トップレベルの処理は、詳細を並べるのではなく、主要な段階を名前の付いた関数として並べ、全体の流れを把握できる構成を優先する。

### 4.3 行数を分割検討の信号として使う

行数だけを合否基準にはしない。ただし、長さは責務の混在や読みづらさを発見する信号として確認する。

| 対象 | 分割を検討する目安 |
|---|---|
| 1つの関数・メソッド | 40行前後を超える、または複数の処理段階を持つ |
| 1つのソースファイル | 300行前後を超える、または複数の独立した責務を持つ |

コメント、型定義、宣言的な対応表などにより、責務が明確なまま行数が増えることはある。目安を超えたことだけを理由に機械的に分割しない。

行数にかかわらず、次の場合は分割を検討する。

- ファイル名だけでは内容全体を説明できない
- 内部の節を示すコメントが多数必要になる
- 変更理由の異なる処理が同居する
- 公開APIが増え、利用側が必要な機能を見つけにくい
- テストの準備や依存関係が責務ごとに大きく異なる

分割は技術分類や行数ではなく、責務、変更理由、依存方向を基準に行う。

## 5. 命名

### 5.1 分かりやすさを優先する

関数名、変数名、型名、モジュール名には、対象または役割を推測できる名前を使用する。

短すぎて意味が失われる略語と、文のように長くなり読みづらい名前の両方を避ける。名前だけで全条件を説明しようとせず、型、関数分割、コメントと役割を分担する。

### 5.2 同じ概念へ同じ名前を使う

RAGScopeの要求、設計、Contract、Schemaで定義された概念は、コード上でも対応関係が分かる名前を使用する。同じ概念へ複数の類義語を割り当てたり、異なる概念へ同じ名前を使ったりしない。

一般的でない略語は避ける。RAGScope内で広く共有され、文脈上明確な略語だけを使用する。

### 5.3 言語の慣習に従う

大文字・小文字、`camelCase`、`snake_case`、モジュール名などの形式は、各言語の一般的な慣習と言語別規約に従う。

外部のJSON、DB、APIなどが別の命名形式を要求する場合は、内部表現と境界での変換を分ける。言語の内部コードへ外部形式を無制限に持ち込まない。

プロジェクト内では、同じ種類の識別子へ同じ命名形式を使用する。

## 6. 境界、エラー、依存関係

### 6.1 境界を明確にする

入力検証、外部I/O、データ変換、ドメイン判断、ログ、利用者向け出力を区別する。機能処理から、具体的な出力先、通信方式、永続化方式などの詳細を必要以上に参照しない。

### 6.2 正常結果と失敗を区別する

予想できる失敗を正常値や特別な文字列へ混ぜない。言語の型、戻り値、例外の慣習を用いて、呼び出し側が失敗を認識し処理できる形にする。

下位ライブラリや外部システムのエラーを、そのままRAGScopeの公開境界へ流さない。責務の境界で、RAGScopeが扱う意味へ変換する。

### 6.3 依存関係を限定する

関数、モジュール、コンポーネントは、担当する責務に必要な依存だけを持つ。循環依存、広すぎる共有モジュール、何でも扱うutilityを避ける。

再利用の可能性だけを理由に先行して共通化しない。複数箇所で同じ意味と変更理由を持つことを確認してから共通化する。

## 7. テストと検証

- 変更した振る舞い、境界条件、主要な異常系を自動テストで確認する。
- 型、Schema、設定、formatter、linterで検査できる内容は、可能な範囲で自動化する。
- テストコードにも本規約を適用し、準備、実行、確認の流れを読み取れる構成にする。
- テスト名は、対象と期待結果が分かる表現にする。
- 時刻、ID、乱数、外部I/Oなど実行ごとに変化する依存は、必要に応じて差し替えられる境界を設ける。

## 8. レビュー時の確認

コードを作成または変更した後は、少なくとも次を確認する。

- コメントが必要なファイルでは、ファイル、公開要素、主要な処理の責務と意図を把握できる
- 必要なコメントが実装と一致し、構文の言い換えだけになっていない
- 長い処理を関数へ分割できないか検討している
- ファイルの長さと責務の数を確認し、必要なら分割している
- 名前が短すぎず長すぎず、同じ概念へ同じ用語を使っている
- 正常結果、失敗、副作用の境界が分かる
- 設定ファイル、formatter、linter、型検査と競合していない
- 関連するテスト、Contract、Schema、設計と矛盾していない
- 依頼と無関係な抽象化やリファクタリングを混入させていない
