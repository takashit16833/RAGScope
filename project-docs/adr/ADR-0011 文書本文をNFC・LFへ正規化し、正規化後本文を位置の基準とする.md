# ADR-0011 — 文書本文をNFC・LFへ正規化し、正規化後本文を位置の基準とする

## 背景

RAGScopeは、同じ文書バージョンに対して本文比較、文書チャンクの分割位置、正解根拠の位置を扱う。

入力文書にはCRLF / LF / CRの差や、Unicodeで同じ文字を合成済み文字と結合文字列で表す差が入り得る。これらを入力表現のまま保持すると、見た目が同じ本文でも同一本文判定やコードポイント位置が変わり、文書チャンクと正解根拠を同じ位置基準で比較しにくい。

一方、互換文字まで変換するNFKCは、入力文書の表記上の差を広く失う。

## 決定

1. 文書取り込み時にUTF-8としてデコードする。
2. 先頭のUTF-8 BOM由来U+FEFFだけを除去する。
3. CRLFと単独CRをLFへ変換する。
4. Unicode正規化形式NFCへ変換する。
5. Markdown記法、空白、インデント、末尾改行など、それ以外の本文は変更しない。
6. 文書バージョンへ保存する本文は正規化後本文とする。
7. 文書チャンク、正解根拠、本文同一性判定で使用する位置と文字列は、正規化後本文を基準にする。
8. 元入力のコードポイント位置をRAGScope内部の正規位置として保持しない。

## 検討した選択肢

### 正規化しない

入力との1対1対応は保ちやすいが、改行コードやUnicodeの等価表現の差を本文同一性と位置へ持ち込む。RAGScopeの追跡基準が入力環境へ依存するため採用しない。

### NFCを採用する

Unicodeの正準等価な表現を揃えつつ、NFKCほど互換文字を広く変換しない。正規化後本文をRAGScope内部の基準と明示すれば、チャンクと正解根拠の位置を同じ本文上で扱えるため採用する。

### NFKCを採用する

検索前処理として有効な場合はあるが、互換文字の表記差まで失う。RAGScopeが保存する基準本文としては変換範囲が広いため採用しない。

## 結果と影響

- 元入力と正規化後本文でコードポイント列や長さが変わる場合がある。
- RAGScope内部の位置は元入力ファイルのoffsetではなく、正規化後本文のUnicodeコードポイント位置である。
- 文書更新時の本文同一性も正規化後本文で判定する。
- 評価データの正解根拠は正規化後本文に対して指定する。
- 将来、元ファイルのbyte offsetを必要とする場合は、正規化後位置とは別の対応情報として設計する。
