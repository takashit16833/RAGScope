# ADR-0004 — 構造化ログの内部イベントモデルを通常イベントと失敗イベントの直和として表現する

## 背景

構造化ログの共通`EventSpec`は、現在`operation`、`event`、`level`、`payload`、`Maybe LogError`を独立した値として保持している。公開する生成関数は通常イベントと失敗イベントの組み立てを分けているが、型そのものは`event = failed`なのに`error`がない、通常イベントなのに`level = error`である、といった意味上不正な状態を表現できる。

JSON Schemaも`event = failed`の場合に`level = error`と`error`必須を要求する一方、通常イベントの`level = error`を禁止していない。意味モデル、コンポーネント内部の型、外部JSON表現のそれぞれで、`event`、`level`、`error`の相関を独立した値の組み合わせとして扱っている。

[ADR-0003](<./ADR-0003 構造化ログのJSON構造をログモデルの型構造と整合させる.md>)では、Haskell内部型とJSONの意味上の構造を可能な範囲で揃え、不要な変換を減らす方針を採用した。この方針によりJSON上で`EventSpec`を`spec`へまとめる構造は定着したが、外部表現と内部型を同型に保つこと自体を設計目標にすると、外部表現で必要な項目が内部モデルの独立した状態として入り込み、不変条件を型で表す余地を失う。

構造化ログの意味、各コンポーネントでの実現、外部表現は別の責務である。意味上の不変条件を先に定め、コンポーネント内部の型と外部表現はそれぞれその意味を実現する方向へ依存させる必要がある。

## 決定

1. 構造化ログの共通`EventSpec`は、`operation`と`payload`という共通部分に対し、通常イベントと失敗イベントを直和または同等の意味構造として区別する。
2. 契約を利用する各コンポーネントの内部モデルは、この通常・失敗の区別と不変条件を表現できる型構造を採用する。外部表現の項目構造へ内部モデルを合わせることを優先しない。正確な型名、constructor、レコード構造、関数名、export listは各コンポーネントのコードを正本とする。
3. 通常イベントは通常イベント名と通常レベルを持つ。通常レベルとして許可するのは`debug`、`info`、`warn`に対応する値だけとし、`error` levelや`LogError`を通常イベントの状態として表現できないようにする。
4. 失敗イベントは安全な`LogError`を必須とする。失敗を表す共通イベント名と`error` levelは失敗variantから固定的に導出し、内部モデルの独立した入力として重複保持しない。`Maybe LogError`の有無を通常・失敗の判別手段として使用しない。
5. 外部表現は構造化ログの意味モデルとは別の設計責務とする。内部モデルと外部表現を同型にすることを要求せず、serialization境界で意味モデルから外部契約へ投影する。v1のJSONでは現在の`spec.operation`、`spec.event`、`spec.level`、`spec.payload`、失敗時の`spec.error`という構造を維持する。
6. RAGScopeアプリケーションのRuntimeは、内部イベントから導出した実効ログレベルを使用して出力判定する。Runtimeは外部表現を知らず、JSONへの投影はserialization境界へ限定する。
7. JSON Schemaは引き続きv1の外部JSON契約の正本とし、通常イベントと失敗イベントを相互排他的な許可形として検証する。通常イベントでは`event != failed`、`level = debug | info | warn`、`error`なし、失敗イベントでは`event = failed`、`level = error`、`error`必須とする。
8. Generic serializationは、内部型と外部表現の構造が自然に対応する箇所では利用してよい。ただし、Genericを利用するために意味上の不変条件を弱めたり、コンポーネントのconstructor名や内部構造を外部契約へ露出させたりしない。
9. 本ADRは、内部モデルとJSON構造を可能な範囲で同型にすること自体を目標としたADR-0003の判断を置き換える。ADR-0003で採用したJSON上の`spec`への集約、外部表現をHaskellのconstructor名から独立させること、JSON SchemaをJSON契約の正本とすること、共通契約とコンポーネント実装を分離することは維持する。

## 検討した選択肢

### 現在の直積型を維持し、スマートコンストラクタとSchemaだけで制約する

外部JSONと内部型の構造を揃えたまま実装変更を小さくできる。一方、`event`、`level`、`Maybe LogError`を任意に組み合わせられる状態が型として残り、生成関数や検証を迂回した場合に不正状態を表現できる。RAGScopeのHaskell規約が求める「不正な状態を表現しにくくする」方針にも合わないため採用しない。

### 外部JSONも通常イベントと失敗イベントの直和構造へ変更する

内部モデルと外部契約を一対一に対応させやすいが、既存の`spec`項目構造を変更し、共通契約を利用するコンポーネントへ不要な追随を要求する。今回解消したい問題は意味上の不変条件と、その不変条件を内部モデルで自然に表現できることなので、外部JSONの階層変更は必要ないため採用しない。

### 意味モデルを直和として定め、各実現境界で表現する

共通設計では通常・失敗の意味と不変条件を直和として定め、各コンポーネントはその不変条件を自身の型で表現し、外部形式はserialization境界で別に表現する。コンポーネント内部と外部表現の双方を意味モデルへ従属させられ、片方の都合がもう片方へ逆流しないため採用する。

## 結果と影響

- [構造化ログ設計](../design/structured-logging/構造化ログ設計.md)は、実装技術と外部表現から独立したLogEventの意味、不変条件、実行との関連付けを現在設計として持つ。
- [RAGScopeアプリケーション構造化ログ設計](../design/structured-logging/RAGScopeアプリケーション構造化ログ設計.md)は、その共通設計をHaskellで成立させるパッケージ境界、型の責務、Runtime、Sinkの流れを持つ。
- [構造化ログJSON表現設計](../design/structured-logging/構造化ログJSON表現設計.md)は、共通の意味をv1のJSONへ投影する規則を持ち、正確な契約はJSON Schemaへ委ねる。
- `RAGScope.Logging.Core`は、通常イベントと失敗イベントを型で区別し、固定値を重複保持しない内部モデルへ変更する。
- `RAGScope.Logging.Runtime`は、`EventSpec`の独立した`level`フィールドではなく、内部イベントから導出した実効ログレベルで出力判定する。
- RAGScopeアプリケーションのserialization境界は、`EventSpec`の内部構造をそのまま外部表現とせず、意味上のvariantをv1の外部契約へ投影する。
- `log-event.schema.json`は外部項目構造を維持したまま、通常イベントと失敗イベントの許可形を相互排他的に検証する。
- AI推論サービス側のPython実装は、本判断と更新後の共通設計・外部契約が確定した後に同じ意味上の不変条件へ追随する。
