# ADR-0001 — 共通実行基盤をv0.0で段階的に導入する

> [!important] 後続ADR
> 本ADRは[ADR-0002 — 共通実行基盤の契約とコンポーネント実装を分離する](<./ADR-0002 共通実行基盤の契約とコンポーネント実装を分離する.md>)によって置き換えられた。
> 以下は、当時の判断と背景を履歴として保持する。

## 背景

当初のロードマップでは、構造化ログとタイムアウト・再試行をv0.5で整備する計画としていた。一方、v0.0の文書処理、AI推論サービスとの通信、PostgreSQL処理を個別に実装してから共通化すると、エラー表現、ログ、再試行判断が機能ごとに分かれ、後から広範囲な修正が必要になる可能性がある。

特に、文書読み込みの実装へ着手する前に、失敗をどのように正常結果と区別し、処理進行と失敗をどのように追跡するかを共通化する必要がある。

ただし、RS-0001の文書読み込みでは、存在しないファイル、不正なUTF-8、空本文など、直ちに再実行しても改善しない失敗を主に扱う。具体的な外部処理が存在しない段階で、回数や待機を備えた汎用的な再試行実行機構まで先行実装すると、利用実態のない過剰設計になる。

## 決定

共通実行基盤をv0.0へ前倒しするが、設計と実装を次の段階へ分ける。

1. RS-0001より前に、共通エラー・構造化ログの設計とRAGScopeアプリケーションの最小基盤を整える。
2. 再試行・タイムアウトについては、RS-0001より前に次の共通原則を確定する。
   - 再試行は、一時的失敗かつ再試行しても安全な場合だけ適用する。
   - 具体的な利用箇所が存在しない汎用的な実行機構を先行実装しない。
   - 処理種別（`operation`）ごとの方針と実装は、その処理へ着手する段階で決定する。
3. 文書読み込みでは自動再試行を行わず、その理由を文書処理設計へ記録する。
4. RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求する処理へ着手する前に、その処理に必要な再試行・タイムアウトの機能別設計を作成し、必要な最小範囲の実行機構を実装する。具体的な回数、待機、タイムアウト、失敗分類、再試行しても安全である条件は、その設計と実装を正本とする。
5. 後続の処理では、副作用と再試行しても安全である条件に応じて個別に適用し、共通化できる実装だけを共通部品へ反映する。
6. ローカルの構造化ログをAWSで収集する検証はv0.1.5で扱う。将来の分散追跡（tracing）へ拡張可能な境界は保つが、同じ実行や処理どうしを結び付ける正確な情報と、処理間関係の規則はv0.5を具体化する時点で決定する。

## 検討した選択肢

### すべてv0.5まで延期する

v0.0を小さく保てる一方、各機能が独自のエラー表現とログを持ち、後から広範囲な修正が必要になる可能性があるため採用しない。

### 各機能で個別実装し、v0.5で共通化する

具体的な利用例を得てから共通化できる一方、エラー・ログの互換性と追跡性がv0.0内でも分かれるため採用しない。

### エラー・ログ・汎用的な再試行実行機構をすべてRS-0001より前に完成させる

共通化を最初から徹底できる一方、具体的な外部処理がない段階で再試行の実装詳細を固定する過剰設計になるため採用しない。

### 変更しにくい契約と原則を先に定め、実装は利用箇所に合わせて段階導入する

エラー・ログの一貫性を確保しつつ、再試行・タイムアウトは具体的な処理に基づいて設計できるため採用する。

## 結果と影響

- v0.0の作業順は、共通エラー・ログ設計、RAGScopeアプリケーションの最小基盤、文書処理への適用、RS-0001の順になる。
- RS-0001は共通エラー・ログ基盤を利用するが、再試行・タイムアウトの機能別設計や実行機構を前提としない。
- RAGScopeアプリケーションからAI推論サービスへ文書チャンクのEmbeddingを要求する処理は、処理種別ごとの再試行・タイムアウト設計と最小限の実行機構の完成後に実装する。
- v0.0の範囲は増えるが、後続機能での独自実装と大規模な置き換えを抑えられる。
- 再試行・タイムアウトの共通原則は早期に固定する一方、具体的な実装値と方式は利用箇所が明確になるまで固定しない。
- 分散追跡の正確な規則は本ADRでは決定せず、v0.5の具体化時に改めて判断する。
