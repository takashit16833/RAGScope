# ADR-0012 — 初期文書分割にUnicodeコードポイント固定長方式を採用する

## 背景

RAGScopeは分割条件を変えた検索品質を比較する。初期の分割方式には、同じ本文と条件から同じチャンクを再現でき、文書バージョン上の位置を直接説明できることが必要である。

候補には、Unicodeコードポイント固定長、Tokenizerのtoken数に基づく分割、Markdown見出しなど構造を使う分割がある。

Tokenizer依存の方式はEmbeddingモデルのTokenizerと分割処理を結び付け、構造依存の方式は文書形式固有の解析規則を追加する。初期baselineでこれらを同時に導入すると、検索品質の差が分割方式・Tokenizer・文書解析のどこから生じたかを切り分けにくい。

## 決定

初期の文書分割方式として、正規化後本文をUnicodeコードポイント数で固定長に分割する。

分割条件はチャンクサイズと重複範囲を持ち、文書チャンクは正規化後本文に対するUnicodeコードポイント単位の半開区間`[start, end)`を保持する。

この方式を検索品質上の最適解とは扱わない。別方式を導入する場合は、分割方式自体を分割条件として識別し、既存の固定長方式と混同しない。

## 検討した選択肢

### Unicodeコードポイント固定長

モデルやTokenizerに依存せず、位置計算が単純で決定的である。意味境界を考慮しない欠点はあるが、初期baselineとして他の要因を増やさず比較しやすいため採用する。

### Tokenizerのtoken数で分割

モデル入力長との対応を作りやすいが、Tokenizerとrevisionを分割条件へ含める必要があり、Embeddingモデル変更と文書分割変更が結び付きやすい。初期方式には採用しない。

### Markdown構造で分割

見出しや段落を保ちやすいが、Markdown解析と境界調整の規則が必要になる。TXTとの共通方式としても扱いにくいため初期方式には採用しない。

## 結果と影響

- 結合文字や複数コードポイントからなる絵文字の途中がチャンク境界になることを許容する。
- 分割結果はEmbeddingモデルやTokenizerを変更しても同じ本文・同じ分割条件なら変わらない。
- semantic chunkingやtoken-based chunkingを追加するときは、新しい分割方式として識別・比較する。
- 分割方式ごとの検索品質は実験で比較し、固定長方式の採用理由を検索品質の優位性として解釈しない。
